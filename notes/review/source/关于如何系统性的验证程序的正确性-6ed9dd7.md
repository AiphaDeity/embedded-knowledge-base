# 关于如何系统性的验证程序的正确性

[飞书原文](https://hcn4ticlccda.feishu.cn/docx/S2TVdg0qsom0gbxbNAacSrnEn4c)

作为一个学嵌入式的程序员，当我们写完代码后，应该按照什么样的思路、步骤、主动的去发现它有问题？

# 总体思路

1. 先多次运行，观察有无反常的现象
2. 根据现象缩小范围（哪个函数）
3. 读代码，找出错误模式
4. 加入快速验证，使用GDB调试和printf打印
5. 定位带具体的行，确认错误
6. 再次验证

# 验证方法

多次运行（即重复执行）主要用来发现结果不稳定或偶发崩溃的问题（比如未初始化变量、数据竞争）。但它不能保证程序正确。以下是更全面的验证方法：

| 方法 | 做什么 | 能发现什么 |
|-|-|-|
| 静态代码检查 | 不运行，用工具（如 `gcc -Wall -Wextra`，`clang-static-analyzer`，`cppcheck`）分析代码 | 未初始化变量、数组越界（部分）、类型不匹配 |
| 单元测试 | 编写测试函数，用确定的输入调用被测试函数，检查输出是否符合预期 | 逻辑错误、边界条件错误 |
| 边界值测试 | 针对数组长度为 0、1、最大值等情况测试 | 循环条件错误、除零、空指针 |
| 内存检查工具 | 用 `valgrind` 或 AddressSanitizer（`gcc -fsanitize=address`）运行程序 | 数组越界、使用未初始化内存、内存泄漏 |
| 断言 | 在代码中加入 `assert(i < length);` 和 `assert(sum 初始值已设置);` | 运行时快速暴露逻辑错误 |
| 代码审查 | 让别人仔细阅读代码，对照常见错误清单 | 任何类型错误，尤其是逻辑错误 |

# 验证几次

没有固定数字，但可以遵循一些经验规则：

1. 烟雾测试（Smoke Test）：  
对主要功能运行 1\~3 次，确保程序不崩溃、输出看起来合理。你做的“运行两次发现结果不同”就属于这个阶段。
2. 稳定性/重复性测试：  
对同一组输入，重复运行 10 次、100 次甚至更多（可以用脚本循环）。如果结果稳定，说明没有未初始化变量或随机性错误。如果结果偶尔变化，说明有隐藏的未定义行为。
3. 不同输入多次运行：  
准备多组测试用例（正常值、边界值、异常值），每组运行 1 次 即可，因为输入已经变化。例如：

   - 正常数组 `[1,2,3]`
   - 长度为 1 的数组 `[100]`
   - 空数组（长度 0，看是否处理除零）
   - 大数组（检查性能或栈溢出）
4. 随机输入测试（Fuzzing）：  
自动生成成千上万个随机输入，每个输入运行 1 次，观察是否崩溃。这对于发现隐藏的越界或未初始化非常有效。

一句话总结：

- “验证几次”取决于风险和目的。

  - 快速自测：3\~5 次 + 3\~5 组输入。
  - 可靠交付：单元测试全覆盖 + 内存检查 + 重复运行 1000 次（自动化）。

# 软件测试的局限

那为什么多次运行并不能保证程序正确呢？很好的问题。这触及了软件测试的根本局限：测试只能证明错误存在，不能证明没有错误（Edsger Dijkstra 名言）

具体到“多次运行同一组输入”，它只能验证程序在特定输入、特定环境、特定执行路径下的行为可重复。但很多错误：

- 未初始化变量：虽然多次运行可能暴露结果随机，但如果栈上的残留数据恰好每次都相同（比如程序总是从同样的初始状态启动），两次运行结果可能一致，让你误以为正确。实际上未初始化行为是未定义的，可能在另一个系统、编译器优化等级不同时崩溃。
- 逻辑错误：比如 `sum = sum + arr[i]` 写成 `sum = arr[i]`，结果稳定但错误。多次运行永远发现不了。
- 数组越界：越界访问可能落在未使用的内存区域，程序不会崩溃，每次都给出相同的错误结果。多次运行看不出异常。
- 并发问题：数据竞争导致的错误，可能运行一万次才出现一次。多次运行没遇到不等于没有。
- 输入依赖：你只测了一组输入 `{10,20,30,40,50}`。其他输入如 `{1,2,3}` 或长度 0 的情况可能出错，但多次运行同一组输入测不到。

结论：

多次运行只能提高对程序“在该输入下行为稳定”的信心，但不能保证：

1. 程序正确（因为正确性需要覆盖所有输入和路径）。
2. 没有未定义行为（因为未定义行为的表现可能碰巧符合预期）。
3. 没有隐藏的偶发错误（如数据竞争）。

所以需要结合其他验证方式：静态分析、单元测试、边界值测试、内存检查工具、形式化证明等。

# 完整的验证流程（五步法）

### 第一步：编码阶段 – 预防错误

在写代码时就做对，而不是事后查。

- 启用编译器最高警告：`gcc -Wall -Wextra -Werror`（`-Werror` 把警告当错误，强制修改）
- 使用静态分析工具：`cppcheck`、`clang-static-analyzer`、`scan-build`
- 遵循安全编码规范：

  - 所有局部变量显式初始化
  - 循环用 `i < length` 而不是 `<=`
  - 使用 `sizeof(arr)/sizeof(arr[0])` 计算数组长度，避免手动传 `size`（除非是堆数组）
- 加入断言：在关键点 `assert(i < length);`、`assert(length > 0);`

### 第二步：单元测试 – 覆盖功能

为每个函数编写测试用例，用确定的输入验证输出。

- 测试正常情况：`{10,20,30,40,50}` 期望 30
- 测试边界：`length = 1`（`{100}`）、`length = 0`（应处理除零）
- 测试极端值：负数、大数、空数组
- 自动化运行：使用简单测试框架（如 `minunit` 或 `assert` 宏）

### 第三步：动态内存/未定义行为检测 – 找隐藏错误

运行程序时，用专门的工具检查内存和未定义行为。

- AddressSanitizer（ASan）：编译时加 `-fsanitize=address -g`  
能精确报告数组越界、使用未初始化内存、内存泄漏等。
- Valgrind：`valgrind --tool=memcheck ./program`  
比 ASan 慢，但无需重新编译，且能检测更多未初始化使用场景。
- UndefinedBehaviorSanitizer（UBSan）：`-fsanitize=undefined`  
捕获整数溢出、除零、空指针解引用等。

组合用法：  
开发时使用 `gcc -fsanitize=address,undefined -g -O0`，然后用 `./program` 直接跑测试用例，越界或未初始化会立即报告。

### 第四步：多轮运行 + 随机输入 – 寻找偶发错误

即使单元测试都通过，仍需验证重复稳定性和隐蔽错误。

- 重复稳定性测试：对同一组输入，循环运行 1000 次（写简单 shell 脚本），观察结果是否一致。
- 模糊测试（Fuzzing）：用工具（如 `afl-fuzz`、`libfuzzer`）自动生成海量随机输入，观察是否崩溃或挂起。
- 线程检测（如果有并发）：`-fsanitize=thread`

### 第五步：代码审查 + 形式化方法（可选）

- 同行代码审查：让另一个开发者阅读代码，对照常见错误清单。
- 形式化验证（高安全领域）：使用工具如 `Frama-C`、`TLA+` 证明代码满足规约。

---

### 简化版完整流程（日常开发推荐）

对于普通 C 程序，你可以记住这个三步流程：

1. 编译时：`gcc -Wall -Wextra -Werror -fsanitize=address,undefined -g`
2. 测试时：写几个简单的 `assert` 测试用例，正常运行一遍
3. 交付前：运行一次 `valgrind`（或 ASan 已够）

这个流程能捕获绝大多数内存错误、未定义行为和逻辑错误。
