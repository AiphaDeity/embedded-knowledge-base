~~~text
# Linux网络编程完整知识体系
- 网络基础与分层体系
  - 网络编程发展历程
    - 起源阶段：ARPANET分组交换网络，互联网技术雏形
    - 早期阶段：电话线低速组网，厂商私有标准，设备互通性差
    - 标准化阶段：TCP/IP协议族诞生，成为互联网通用通信标准
    - 理论完善：OSI七层模型发布，成为网络分层设计通用参考标准
  - 网络编程并发模型演进
    - 单进程阻塞IO：串行处理单连接，实现简单，并发能力极差
    - 多进程/多线程模型：每连接对应一个执行流，支撑中等并发，切换开销大
    - IO多路复用模型：单线程监控海量连接，高并发低资源消耗，主流高性能方案
    - 事件驱动异步IO：全异步回调机制，进一步提升资源利用率与并发上限
  - 分层设计核心思想
    - 解耦原则：每层职责单一，独立迭代升级不影响其他层
    - 封装/解封装：发送方自上而下逐层添加头部，接收方自下而上逐层拆解头部
    - 标准化接口：层间通过标准接口交互，兼容不同厂商的硬件与软件实现
  - OSI七层模型（理论参考标准）
    - 物理层：传输原始比特流，定义物理介质与电气特性
    - 数据链路层：局域网帧传输、MAC寻址、差错检测
    - 网络层：跨网段寻址、路由选择、IP转发
    - 传输层：端到端进程通信、可靠性保障、流量控制
    - 会话层：建立、维护、终止会话连接
    - 表示层：数据格式转换、加密解密、压缩编码
    - 应用层：面向用户业务，提供具体网络服务
  - TCP/IP四层模型（工业实际标准）
    - 网络接口层：合并OSI物理层+数据链路层，负责物理传输与链路层帧交付
    - 网络层：IP寻址与路由转发，完全对应OSI网络层
    - 传输层：TCP/UDP端到端传输，完全对应OSI传输层
    - 应用层：合并OSI会话层+表示层+应用层，承载所有具体应用协议
- 三层核心寻址体系
  - IP地址（网络层）
    - 核心作用：跨网段全局寻址，定位互联网中任意主机的位置
    - IPv4：32位二进制，点分十进制表示，总地址数约43亿
    - IPv6：128位二进制，冒分十六进制表示，彻底解决地址枯竭问题
    - 组成结构：网络号（标识所属网段）+ 主机号（标识网段内具体主机）
  - 端口号（传输层）
    - 核心作用：区分同一主机内的不同应用进程，实现端到端进程级通信
    - 数值范围：16位无符号整数，取值 0 ~ 65535
    - 三大分类
      - 公认端口（0~1023）：系统标准服务，绑定需管理员权限
      - 注册端口（1024~49151）：用户自定义应用，可向IANA注册使用
      - 动态端口（49152~65535）：客户端发起连接时自动分配，使用后回收
    - 常见标准端口
      - 22/TCP：SSH 安全远程登录
      - 53/UDP+TCP：DNS 域名解析
      - 80/TCP：HTTP 明文网页传输
      - 443/TCP：HTTPS 加密网页传输
      - 3306/TCP：MySQL 数据库服务
  - MAC地址（数据链路层）
    - 核心作用：局域网内硬件寻址，标识网卡物理身份
    - 结构：48位（6字节），通常用十六进制冒号分隔表示
    - 组成：前24位OUI厂商标识 + 后24位厂商自定义序列号
    - 特性：全球唯一，烧录在网卡ROM中；仅局域网内有效，不可跨路由器转发
  - 通信五元组
    - 组成：源IP + 源端口 + 目的IP + 目的端口 + 传输层协议
    - 作用：内核中唯一标识一条网络连接，用于将数据分发到对应socket缓冲区
- 物理层与数据链路层
  - 物理层
    - 核心职能：在物理介质上传输原始比特流（0/1电信号/光信号）
    - 传输介质
      - 有线介质：双绞线、同轴电缆、光纤
      - 无线介质：无线电波、微波、红外线
    - 关键技术
      - 编码调制：曼彻斯特编码、QAM调制，定义比特与物理信号的映射规则
      - 接口标准：定义引脚定义、电气特性、传输速率规范
    - 特点：只关注信号传输质量，不识别任何地址与数据内容
  - 数据链路层
    - 两大子层
      - MAC子层（介质访问控制）
        - 介质访问控制：解决多设备共享信道的冲突问题
        - 以太网CSMA/CD：载波监听+冲突检测，冲突后执行二进制指数退避
        - Wi-Fi CSMA/CA：载波监听+冲突避免，发送前先预约信道
        - 帧封装：添加源/目的MAC头部 + CRC尾部校验
      - LLC子层（逻辑链路控制）
        - 上层协议标识（SAP服务访问点）
        - 链路层流量控制与差错恢复
    - 以太网帧结构
      - 目的MAC（6字节）+ 源MAC（6字节）+ 类型/长度字段（2字节）
      - 数据载荷（46~1500字节）+ FCS帧校验（4字节）
    - MTU最大传输单元：以太网默认1500字节，超过则IP层执行分片
  - 交换机工作原理
    - 自学习：根据帧的源MAC地址+接收端口，构建MAC地址表
    - 转发：根据目的MAC查表，从对应端口单播转发
    - 未知单播：查表失败则向所有端口广播泛洪
    - 作用：隔离冲突域，所有端口同属一个广播域
  - ARP地址解析协议
    - 功能：IP地址 → MAC地址转换，是局域网IP通信的底层基础
    - 工作流程
      1. 主机A广播ARP请求：查询目标IP对应的MAC地址
      2. 所有主机接收请求，IP匹配的主机B单播回复自身MAC地址
      3. 主机A将IP-MAC映射存入ARP缓存表
    - ARP缓存：临时存储映射关系，有老化时间，减少重复广播开销
    - 配套协议：RARP反向解析（MAC→IP），用于无盘工作站启动，现基本被DHCP取代
  - 冲突域与广播域
    - 冲突域：同一时间只能一台设备发送数据的区域，交换机可隔离冲突域
    - 广播域：广播消息可以覆盖的网络范围，路由器可隔离广播域
- 网络层与IP协议
  - 网络层核心职能
    - 跨网段寻址：通过IP地址定位全网任意主机
    - 路由选择：通过路由算法选择最优传输路径
    - 分片与重组：超过链路MTU的数据包分片，到达目的端后重组
    - 拥塞反馈：通过ICMP等机制反馈网络拥堵与错误状态
  - IP协议核心特性
    - 无连接：发送前不建立专用通道，每个数据包独立选路
    - 不可靠：不保证送达、不保证顺序、不保证不重复
    - 尽力而为：只负责最高效率转发，可靠性由上层TCP协议保障
  - IPv4报文头部详解
    - 版本（4bit）：标识IP协议版本，IPv4对应值为4
    - 首部长度（4bit）：IP头长度，单位为4字节，默认值5（对应20字节标准头）
    - 服务类型TOS（8bit）：定义优先级、延迟、吞吐量、可靠性，现多用于区分服务
    - 总长度（16bit）：整个IP数据包总长度（头部+数据），最大65535字节
    - 标识（16bit）：同一数据包的所有分片共享相同标识，用于目的端重组
    - 标志位（3bit）
      - 第1位：保留未使用
      - 第2位DF：禁止分片位，为1时数据包超过MTU直接丢弃
      - 第3位MF：更多分片位，为1表示后续还有分片，0表示是最后一片
    - 片偏移（13bit）：当前分片在原始数据包中的相对位置，单位为8字节
    - TTL生存时间（8bit）：每经过一个路由器值减1，减到0则丢弃包并回ICMP超时报文，防止路由环路
    - 协议（8bit）：标识上层传输层协议，1=ICMP，6=TCP，17=UDP
    - 首部校验和（16bit）：仅校验IP头部数据完整性，不校验数据部分
    - 源IP地址（32bit）：发送方IPv4地址
    - 目的IP地址（32bit）：接收方IPv4地址
    - 选项字段（可变，最多40字节）：记录路由、时间戳等扩展功能，实际极少使用
  - IPv4地址体系
    - 传统分类地址
      - A类：首字节1~126，8位网络位+24位主机位，用于大型骨干网络
      - B类：首字节128~191，16位网络位+16位主机位，用于中型企业网络
      - C类：首字节192~223，24位网络位+8位主机位，用于小型办公网络
      - D类：首字节224~239，专门用于组播地址
      - E类：首字节240~255，保留用于科研
      - 特殊地址：127.0.0.0/8 为本地回环地址，用于本机内部通信
    - 私有IP地址段
      - A类私网：10.0.0.0 ~ 10.255.255.255，大型企业内网
      - B类私网：172.16.0.0 ~ 172.31.255.255，中型机构内网
      - C类私网：192.168.0.0 ~ 192.168.255.255，家庭与小型办公
    - 子网掩码
      - 核心作用：划分网络位与主机位的边界，判断两个IP是否属于同一网段
      - 二进制特征：连续的1对应网络位，连续的0对应主机位
      - 默认掩码：A类255.0.0.0，B类255.255.0.0，C类255.255.255.0
      - 计算规则：IP地址 按位与 子网掩码 = 网络地址
      - CIDR表示法：IP/前缀长度，如192.168.1.0/24，表示前24位为网络位
    - 子网划分
      - 原理：借用主机位作为子网位，将一个大网段拆分为多个小子网
      - 计算步骤
        1. 根据需求子网数，计算需借用的位数n：2^n ≥ 子网数
        2. 新掩码长度 = 原掩码长度 + n
        3. 单子网可用主机数 = 2^(剩余主机位) - 2（减去网络地址和广播地址）
        4. 按块大小依次划分每个子网的网络地址、可用IP范围、广播地址
      - 作用：节省IP资源、隔离广播域、提升网络安全性与管理性
  - IPv6协议
    - 地址长度：128位，地址总数约3.4×10^38，彻底解决IPv4地址枯竭问题
    - 报文优势：固定40字节基本首部，取消首部校验和，提升路由器转发效率
    - 地址类型：单播、组播、任播
    - 表示方法：冒分十六进制，连续的0可缩写为::
  - 路由原理
    - 路由表核心条目：目标网段 + 下一跳地址 + 出接口
    - 转发原则：最长前缀匹配，优先选择掩码最长的匹配条目
    - 路由分类
      - 直连路由：路由器直连的网段，自动生成
      - 静态路由：人工手动配置，适合小型稳定网络
      - 动态路由：通过路由协议自动学习更新，适合大型复杂网络
        - 内部网关协议IGP：OSPF（链路状态型）、RIP（距离矢量型）
        - 外部网关协议EGP：BGP，用于自治系统之间的路由交换
  - NAT网络地址转换
    - 核心作用：私网IP ↔ 公网IP转换，让多台内网设备共享少量公网IP访问互联网
    - 常见类型
      - 静态NAT：一对一固定地址映射
      - 动态NAT：从公网地址池动态分配映射
      - PAT端口多路复用：多个私网IP映射到同一个公网IP的不同端口，家用路由器默认模式
  - 配套网络层协议
    - ICMP互联网控制报文协议
      - 功能：网络错误报告、连通性探测、路径追踪
      - 典型应用：ping（回显请求/应答）、traceroute（TTL超时+ICMP报文追踪路径）
      - 常见报文类型：目标不可达、超时、重定向、回显请求/应答
    - IGMP互联网组管理协议
      - 功能：管理组播组成员，主机加入/离开组播组
      - 应用场景：IPTV、直播、视频会议，实现一对多高效数据传输
- 传输层核心协议
  - 传输层核心定位
    - 端到端逻辑通信：为不同主机上的应用进程提供直接通信能力
    - 多路复用：发送方多个进程的数据，统一封装后交给网络层发送
    - 多路解复用：接收方根据目标端口号，将数据分发到对应的应用进程
  - TCP传输控制协议
    - 核心三大特性
      - ① 面向连接
        - 通信前必须通过三次握手建立连接，通信结束通过四次挥手断开
        - 内核维护连接状态结构体，记录序列号、窗口、缓冲区等状态
        - 三次握手流程与状态变迁
          1. 客户端发送SYN报文，进入SYN_SENT状态
          2. 服务端回复SYN+ACK报文，进入SYN_RCVD状态
          3. 客户端回复ACK报文，双方进入ESTABLISHED状态，连接正式建立
        - 四次挥手流程与状态变迁
          1. 主动关闭方发送FIN报文，进入FIN_WAIT_1状态
          2. 被动关闭方回复ACK，进入CLOSE_WAIT状态，主动方进入FIN_WAIT_2
          3. 被动关闭方发送FIN报文，进入LAST_ACK状态
          4. 主动关闭方回复ACK，进入TIME_WAIT状态，被动方收到后关闭连接
        - TIME_WAIT状态详解
          - 持续时间：2MSL（两倍报文最大生存时间）
          - 作用1：保证最后一个ACK能送达对端，避免对方重传FIN报文
          - 作用2：隔绝旧连接的延迟报文，防止新复用的连接收到脏数据
          - 工程解决方案：通过setsockopt设置SO_REUSEADDR端口复用
      - ② 可靠传输
        - 确认应答机制：接收方收到数据必须回复ACK确认
        - 超时重传：超时未收到ACK，发送方自动重传对应数据
        - 乱序重组：按报文序列号排序，保证交付给应用层的数据有序
        - 去重校验：重复到达的报文直接丢弃，校验出错报文直接丢弃
      - ③ 流量控制（滑动窗口）
        - 接收方通过TCP头部窗口字段，告知自身接收缓冲区剩余大小
        - 发送方根据窗口大小动态调整发送速率，防止接收方缓冲区溢出
        - 滑动窗口大小 = 接收缓冲区剩余可用空间
    - 拥塞控制核心机制
      - 慢启动：连接建立初期指数增长发送速率，探测网络带宽
      - 拥塞避免：达到慢启动阈值后线性增长，平稳提升发送速率
      - 快重传：收到三次重复ACK立即重传，无需等待超时
      - 快恢复：丢包后快速降低速率，避免降到最低，提升传输效率
    - 字节流特性
      - 无天然数据边界，仅视为连续的字节流
      - 粘包/拆包问题：发送方合并发送、接收方分批次读取导致
      - 解决方案：固定长度包、长度字段头、特殊分隔符
    - 全双工特性
      - 同一连接同时拥有独立的读、写内核缓冲区
      - 两端可同时收发数据，互不干扰
    - TCP报文头部关键字段
      - 源端口号、目的端口号
      - 序号、确认号
      - 数据偏移、标志位（SYN/FIN/ACK/RST等）
      - 窗口大小、校验和、紧急指针
  - UDP用户数据报协议
    - 核心特性
      - 无连接：无需提前建立连接，每个报文独立封装地址信息
      - 不可靠：无确认、无重传、无序保证，丢包不重发
      - 面向报文：一次发送对应一个完整报文，有明确边界，无粘包问题
      - 头部开销小：仅8字节头部，传输效率高、延迟低
    - 适用场景
      - 实时性优先：直播、语音通话、在线游戏
      - 短报文交互：DNS查询、SNMP网络管理
      - 广播/组播通信场景
  - TCP与UDP核心对比
    - 连接性：TCP面向连接；UDP无连接
    - 可靠性：TCP可靠有序；UDP不可靠无序
    - 传输形式：TCP字节流无边界；UDP数据报有明确边界
    - 资源开销：TCP头部大、连接维护成本高；UDP轻量化、开销小
    - 传输速度：TCP慢；UDP快
    - 适用场景：TCP适合文件传输、网页浏览；UDP适合实时音视频、游戏
- 应用层与架构模式
  - 应用层核心职能
    - 直接面向用户业务，定义数据格式与交互规则
    - 封装底层网络细节，为用户提供可直接使用的网络服务
  - 经典应用层协议
    - HTTP/HTTPS
      - HTTP：超文本传输协议，明文传输，默认80端口，Web服务基础
      - HTTPS：HTTP+SSL/TLS加密，防窃听防篡改，默认443端口
    - FTP文件传输协议
      - 功能：文件上传与下载
      - 默认端口：21控制端口，20数据端口
    - DNS域名系统
      - 功能：域名与IP地址的互相转换
      - 默认53端口，UDP为主，大报文使用TCP
    - SMTP简单邮件传输协议
      - 功能：邮件发送
      - 默认25端口
    - SSH安全外壳协议
      - 功能：加密远程登录服务器
      - 默认22端口
  - C/S架构（客户端-服务器）
    - 核心模式：客户端安装专用软件，主动向服务器发起请求
    - 优点
      - 性能高：客户端可分担计算与渲染压力
      - 定制化强：可深度优化界面与功能，用户体验更好
      - 功能丰富：可直接调用本地硬件资源，不受浏览器限制
    - 缺点
      - 开发维护成本高：需适配多平台（Windows/macOS/移动端）
      - 升级麻烦：用户需手动更新客户端版本
    - 典型应用：大型网游、桌面办公软件、专业工具软件
  - B/S架构（浏览器-服务器）
    - 核心模式：浏览器作为统一客户端，通过HTTP/HTTPS访问服务端
    - 优点

      - 易维护：服务端更新即全网生效，用户无感知
      - 部署简单：仅需部署服务端，客户端零成本

      - 性能受限：复杂计算依赖服务端，渲染能力弱于原生客户端

    - 微服务架构：按业务拆分为多个独立服务，通过网络调用协作
- Socket编程核心API
  - Socket本质
    - 是应用层与TCP/IP协议栈之间的抽象编程接口
    - Linux下是特殊的文件描述符，遵循万物皆文件设计思想
    - 封装底层网络细节，开发者无需直接操作内核协议栈
  - 套接字三大类型
    - SOCK_STREAM 流式套接字
      - 对应TCP协议
      - 面向连接、可靠、双向字节流
      - 适用场景：网页、文件传输等绝大多数可靠通信场景
    - SOCK_DGRAM 数据报套接字
      - 对应UDP协议
      - 无连接、不可靠、独立报文
      - 适用场景：实时音视频、DNS、广播通信
    - SOCK_RAW 原始套接字
      - 可直接构造IP层及以下报文
      - 适用场景：网络诊断工具、安全扫描器
  - TCP编程标准流程
    - 服务端（被动监听）
      1. socket()：创建套接字文件描述符
      2. bind()：绑定本机IP+端口，INADDR_ANY表示绑定所有网卡
      3. listen()：设置为监听状态，创建半连接队列与全连接队列
         - backlog参数：全连接队列的最大长度
      4. accept()：阻塞取出已完成三次握手的连接，返回新的通信fd
         - 监听fd仅负责接收新连接，不参与业务数据收发
      5. send()/recv()：通过通信fd读写业务数据
      6. close()：关闭文件描述符，触发四次挥手流程
    - 客户端（主动连接）
      1. socket()：创建套接字文件描述符
      2. connect()：向服务端IP+端口发起三次握手
      3. send()/recv()：进行业务数据交互
      4. close()：关闭连接
  - UDP编程标准流程
    - 服务端：socket() → bind() → recvfrom()/sendto() → close()
    - 客户端：socket() → sendto()/recvfrom() → close()
    - 无需listen、accept步骤，无连接建立过程
  - 网络字节序
    - 产生原因：不同CPU架构字节序不同，跨平台通信需统一标准
    - 网络标准：TCP/IP规定所有多字节数据统一使用大端序
    - 主机字节序：x86/ARM多为小端序，低位字节存放在低地址
    - 标准转换函数（头文件 arpa/inet.h）
      - htons()：主机序 → 网络序（16位，用于端口号）
      - htonl()：主机序 → 网络序（32位，用于IP地址）
      - ntohs()：网络序 → 主机序（16位）
      - ntohl()：网络序 → 主机序（32位）
    - 大小端判断：可通过共用体、指针方式判断当前平台的字节序
  - IP地址格式转换
    - inet_addr()：点分十进制字符串 → 网络字节序32位整型
    - inet_ntoa()：网络字节序32位整型 → 点分十进制字符串
      - 注意：返回静态内存指针，不可重入，多线程环境下不安全
    - 进阶函数：inet_pton / inet_ntop，同时支持IPv4/IPv6，线程安全
  - 核心编程注意点
    - send成功返回 ≠ 对端应用收到数据，仅代表数据进入内核发送缓冲区
    - recv返回0表示对端正常关闭了连接
    - 对端异常崩溃、网络断开，TCP层无法自动感知，需应用层心跳机制检测
- IO模型与高并发演进
  - 五大IO模型（Unix标准分类）
    - 阻塞IO
      - 数据未就绪时，进程挂起休眠，直到数据就绪后唤醒
      - 优点：实现简单；缺点：并发能力极低
    - 非阻塞IO
      - 数据未就绪时，立即返回错误，不阻塞进程
      - 需要轮询查询，CPU利用率低，很少单独使用
    - IO多路复用
      - 单线程同时监控多个文件描述符，批量等待事件就绪
      - 就绪后逐个处理IO操作，是高并发网络服务的核心方案
    - 信号驱动IO
      - 注册信号处理函数，数据就绪时内核发送SIGIO信号通知
      - 异步通知机制，但处理逻辑复杂，实际工程应用少
    - 异步IO（AIO）
      - 发起IO请求后立即返回，内核完成整个IO（数据拷贝到用户态）后通知
      - 真正的全异步IO，实现复杂度高
  - IO多路复用三剑客对比
    - select
      - 存储：fd_set位图结构，默认最大支持1024个fd
      - 机制：每次调用全量拷贝fd集合到内核，内核线性遍历查找就绪项
      - 缺点：fd数量上限低、全量拷贝开销大、线性扫描效率随连接数下降
      - 优点：跨平台兼容性好
    - poll
      - 存储：pollfd结构体数组，无fd数量硬上限
      - 机制：同select，仍需全量拷贝+内核线性遍历
      - 缺点：本质性能无提升，仅解决了fd数量限制
    - epoll（Linux独有，当前最优方案）
      - 核心数据结构
        - 红黑树：内核维护待监控的fd集合，增删改查高效
        - 就绪链表：存放已经就绪的fd事件
      - 核心接口
        - epoll_create：创建epoll实例
        - epoll_ctl：增删改监控的fd，仅调用时拷贝一次数据
        - epoll_wait：等待事件，仅拷贝就绪链表数据
      - 两种触发模式
        - LT水平触发（默认）：数据未处理完会持续通知，编程简单不易出错
        - ET边缘触发：仅状态变化时通知一次，效率更高，需一次性读完数据
      - 高性能原因：无fd数量上限、无需全量拷贝、无需线性遍历全部fd
      - 典型应用：Nginx、Redis、各类高性能网络服务
  - 高并发架构演进路径
    - 单进程单连接：串行处理，仅教学演示使用
    - 多进程并发：每接入一个连接fork一个子进程，资源开销大
    - 多线程并发：每接入一个连接创建一个线程，开销小于多进程，仍有上下文切换成本
    - 单线程Reactor：epoll+事件循环，单线程处理所有连接，代表：Redis
    - 多线程Reactor：主Reactor负责接入连接，子Reactor负责IO处理，代表：Nginx
    - Proactor：全异步IO模型，理论性能更高，实现复杂度高
- 网络编程第一性原理
  - 核心公理
    - Linux万物皆文件，socket本质是特殊的文件描述符
    - 所有网络通信都通过内核缓冲区中转，进程不直接操作网卡硬件
  - 内核双缓冲区机制
    - 发送缓冲区
      - 位置：内核空间，每个socket独立拥有
      - 流程：send系统调用将用户态数据拷贝到内核发送缓冲区即返回
      - 后续：内核协议栈+网卡驱动异步将数据封装后通过网卡发出
    - 接收缓冲区
      - 位置：内核空间，每个socket独立拥有
      - 流程：网卡收到数据，通过硬件中断存入内核接收缓冲区
      - 读取：recv系统调用将内核数据拷贝到用户态内存
    - 缓冲区的核心作用
      - 解耦：应用层读写速率与硬件发送速率解耦
      - 平滑流量：应对突发数据，减少系统调用次数
      - 支撑协议特性：TCP的重传、排序、流量控制都依赖缓冲区实现
  - 核心底层认知
    - send成功 ≠ 对端应用收到数据，仅代表数据进入内核发送缓冲区
    - TCP是字节流，无天然包边界，应用层必须自定义协议实现分包
    - 正常关闭：recv返回0，代表对端执行了close操作
    - 异常断开：进程崩溃、网络中断，TCP层无法自动感知，必须靠应用层心跳检测
  - 终极公式
    - 网络程序 = socket文件描述符 + 内核双缓冲区 + IO模型 + 传输层协议 + 应用层自定义协议
~~~

## 底层最核心本源：一切网络通信 = 内核缓冲区 + 文件描述符

### 第一公理

Linux 万物皆文件，网络套接字 socket 本质是一种特殊文件描述符 fd。 进程无法直接操控网卡硬件，所有收发数据全部依托内核两块缓冲区完成中转：

1. 发送缓冲区（内核态）：进程调用`write/send`，数据从用户内存拷贝到内核发送缓冲区，函数即可返回；后续内核网卡驱动自动把缓冲区数据发往对端。
2. 接收缓冲区（内核态）：网卡收到对端数据包，硬件中断把数据存入内核接收缓冲区；进程调用`read/recv`时，再将内核缓冲区数据拷贝到用户程序内存。

> 本质：网络编程就是对 socket 这个特殊 fd，完成读缓冲区、写缓冲区的文件 IO 操作。

## TCP 通信第一本质：面向连接、可靠、字节流、双工管道

### 面向连接

通信前必须通过三次握手在两端内核建立专属连接结构体，记录五元组（源 IP、源端口、目的 IP、目的端口、协议），作为两端缓冲区的绑定标识；通信结束必须四次挥手正常断开连接。 无连接（UDP）：无握手无连接结构体，每次数据包自带五元组，发完即丢弃上下文。

### 可靠传输（TCP 核心设计目标）

内核协议栈自动完成 4 项可靠性保障，完全不需要用户代码手动处理：

1. 应答 ACK：对方收到数据必须回确认报文，未确认的数据内核自动重传；
2. 去重：重复抵达的数据包内核直接丢弃；
3. 乱序重组：无序到达的分片数据包，内核按序号排序拼接后存入接收缓冲区；
4. 流量控制：根据对端接收缓冲区剩余容量，动态调整发送速率，避免对方缓冲区溢出。

### 字节流特性

TCP 没有数据包边界，仅看作一串连续无分隔的字节数据流； 用户程序读写仅操作字节流，粘包、拆包问题根源就来自字节流无边界，必须由应用层手动设计分包协议（长度头、分隔符、固定包体）。

### 全双工

同一个 socket fd 同时拥有读、写两块独立内核缓冲区，两端可同时收发数据，互不阻塞干扰。

## Socket 编程极简本源模型（C/S 架构第一范式）

### 服务端（被动等待连接）四步固定逻辑

1. `socket()`：创建套接字 fd，生成内核 socket 对象；
2. `bind()`：将 socket 绑定本机固定 IP + 端口，让客户端能定位到本机进程；
3. `listen()`：设置监听队列，内核创建半连接队列、全连接队列，存放握手完成的 TCP 连接；
4. `accept()`：阻塞取出全连接队列中已完成三次握手的连接，返回新的专属通信 fd；原监听 fd 永远只负责接新连接，不收发业务数据。

### 客户端（主动发起连接）三步固定逻辑

1. `socket()`：创建客户端套接字 fd；
2. `connect()`：向服务端 IP + 端口发起三次握手，内核完成连接建立；
3. 直接使用该 fd 调用 send/recv 收发数据。

## 阻塞 IO 默认底层原理（Linux socket 默认行为）

1. recv/read 阻塞：内核接收缓冲区无任何数据时，进程被内核挂起休眠，直到有数据抵达缓冲区或连接断开，函数才返回；
2. send/write 阻塞：内核发送缓冲区已满，进程休眠，直到缓冲区腾出足够空间写入用户数据；
3. accept 阻塞：全连接队列为空，没有新客户端握手完成，进程休眠等待新连接。

> 阻塞 IO 短板：单线程只能串行处理事件，一处阻塞整个程序卡死，由此演化出 IO 多路复用（select/poll/epoll）作为高并发核心方案。

## IO 多路复用第一性原理

单个进程 / 线程，同时监视多个 fd（监听 socket + 海量通信 socket），由内核批量告知哪些 fd 就绪（可读 / 可写 / 异常），程序只针对就绪 fd 执行 IO 操作，避免逐个 fd 阻塞等待。

### 三者本质区别

1. select：位图存储监视 fd，有最大 fd 数量上限；每次调用都要拷贝 fd 集合到内核，内核线性遍历所有 fd 查找就绪项，低效。
2. poll：结构体数组存 fd，无数量硬上限；依旧每次全量拷贝、内核线性轮询遍历，性能无本质提升。
3. epoll（Linux 独有最优方案）： 

   - 内核维护红黑树存放待监视 fd，仅在`epoll_ctl`增删 fd 时拷贝一次；
   - 就绪 fd 存入内核就绪链表，调用`epoll_wait`仅拷贝就绪事件，无需遍历全部 fd；
   - 支持水平触发 LT（默认）、边缘触发 ET，是 Linux 高并发网络服务（Nginx、Redis）底层唯一 IO 模型。

## TCP 必懂底层本质规则（面试核心本源）

### 四次挥手本质

TCP 是全双工，收发两个方向可以单独关闭：

- 主动关闭方发 FIN：代表我方不再发送数据，但依旧可以接收对方剩余数据；
- 被动方回复 ACK：确认收到关闭请求；
- 被动方发送 FIN：自身也不再发送数据；
- 主动方回复 ACK，连接彻底销毁。

### TIME_WAIT 存在的核心目的

主动断开连接一方会进入`TIME_WAIT`状态固定等待 2MSL 时长，两大底层必要性：

1. 保证最后一次 ACK 报文一定能送达对方，防止对方因没收到 ACK 重发 FIN 导致端口资源错乱；
2. 隔绝旧连接滞留的延迟数据包，避免新复用端口的连接收到旧连接残留报文。

### 端口不能重复绑定根源

默认条件下，处于 TIME_WAIT 状态的端口不允许 bind 复用；可通过`setsockopt`设置端口复用属性`SO_REUSEADDR`，解决服务端快速重启无法绑定端口问题。

### 缓冲区与返回值逻辑

- `send`成功返回写入字节数，仅代表数据进入内核发送缓冲区，绝不代表对方程序已经收到数据；
- 对方进程正常 close (fd) 关闭 socket：己方 recv 返回 0，代表 TCP 连接正常关闭；
- 对方进程异常崩溃、断网：内核无法正常挥手，recv 会长期阻塞，必须依靠心跳包 + 超时机制由应用层判定断开。

## UDP 第一性原理

1. 无连接：没有握手、没有连接结构体，每个数据包独立封装五元组；
2. 不可靠：内核无重传、无应答、无乱序重组，数据包丢包、乱序完全由应用自行处理；
3. 自带数据包边界：一次 sendto 对应一个独立 UDP 报文，recvfrom 一次读完一个完整包，不存在粘包；
4. 服务端仅需`socket→bind→recvfrom/sendto`，无需 listen、accept。

## 所有网络编程的终极第一公式

网络程序 = socket 文件描述符 + 内核双缓冲区 + IO 模型（阻塞 / 非阻塞 / 多路复用） + 应用层协议

1. 底层硬件与协议栈：Linux 内核 TCP/IP 协议栈封装网卡操作，用户态完全不用操控硬件；
2. 系统调用层：socket/bind/listen/accept/connect/read/write/send/recv 全部是对特殊文件的 IO 控制；
3. 业务层：TCP 字节流必须自定义协议分包，UDP 按需做可靠性封装；
4. 并发层：单进程单连接→多进程 fork→多线程 pthread→IO 多路复用 epoll 是 Linux 网络并发架构演进唯一主线。

## 一句话终极总纲

Linux 网络编程，本质就是借助 socket 文件描述符，通过系统调用读写内核网卡缓冲区，由内核 TCP/IP 协议栈完成跨主机的数据传输与连接管理。

### 网络技术发展简史

1. ARPANET 时代 ARPANET 是现代互联网的雏形，诞生于 20 世纪 60 年代，最早实现了分组交换技术，奠定了计算机网络的技术基础，是互联网的技术源头。
2. 早期低速网络 依托电话线实现低速组网，各个厂商采用私有通信标准，不同品牌设备之间互通性差，网络体系混乱。
3. TCP/IP 协议诞生 TCP/IP 协议族的出现统一了网络通信标准，成为互联网通用的 “普通话”，实现了跨设备、跨系统、跨厂商的互联互通，是 Linux 内核网络栈的核心基础。
4. OSI 模型发布 ISO 组织推出 OSI 开放系统互连七层模型，成为网络分层设计的理论参考标准，规范了网络技术的学习与设计思路。

### 网络编程并发模型演进

随着网络业务规模扩大，服务端的并发处理能力不断迭代，经历了四个核心阶段：

1. 单进程阻塞 IO 模型 同一时间只能处理一个客户端连接，后续连接必须排队等待，IO 操作阻塞时整个程序挂起。优点是逻辑简单易于实现；缺点是并发能力极差，仅适合教学演示，无法用于实际生产环境。
2. 多进程 / 多线程并发模型 每接入一个新客户端连接，就 fork 一个子进程或创建一个子线程，由独立执行流专门处理该连接的 IO 与业务逻辑。优点是实现简单，连接之间相互隔离，能支撑中等规模并发；缺点是进程 / 线程的创建、销毁、上下文切换开销大，海量连接下系统资源会快速耗尽。
3. IO 多路复用模型 单个进程 / 线程同时监控大量文件描述符，由内核批量返回就绪的连接，程序仅针对就绪的连接执行 IO 操作。无需为每个连接创建独立执行流，极大降低了资源开销，是当前 Linux 高并发网络服务的核心底层方案。
4. 事件驱动异步 IO 模型 基于 IO 多路复用 + 回调机制，所有业务逻辑都以事件回调的形式执行，进一步提升单进程的并发处理效率，代表实现有 Nginx、Node.js。

### 网络分层设计核心思想

将复杂的端到端通信拆解为多层独立功能，每层专注解决一类问题，是网络技术的核心设计思想。

- 解耦性：每层职责单一，内部实现升级迭代不影响其他层，降低系统复杂度
- 标准化：层与层之间通过标准接口交互，不同厂商的硬件、软件只要遵循标准就能互通
- 封装与解封装： 

  - 发送方：数据自上而下逐层传递，每一层都添加本层的头部信息，称为封装
  - 接收方：数据自下而上逐层传递，每一层都剥掉对应头部，称为解封装
  - 最终交付给应用层程序的，只有原始业务数据

### 2.3 数据完整传输流程示例

以浏览器访问网页为例，数据流转过程：

1. 应用层：浏览器生成 HTTP 请求报文
2. 传输层：添加 TCP 头部，包含源端口、目的端口、序号等信息
3. 网络层：添加 IP 头部，包含源 IP、目的 IP、TTL 等信息
4. 网络接口层：添加 MAC 头部，包含源 MAC、网关 MAC，加上 CRC 校验
5. 物理层：转换为电信号通过网线传输
6. 沿途路由器：逐层解封装到网络层，根据目的 IP 查路由表，重新封装后转发
7. 目标服务器：自下而上逐层解封装，最终将 HTTP 请求交给 Web 服务程序

## 物理层与数据链路层

### 3.1 物理层

#### 核心职能

物理层位于整个网络体系的最底层，负责在电缆、光纤、无线电波等物理介质上，传输原始的比特流（0 和 1 对应的电 / 光 / 无线信号）。 物理层只关注信号的传输质量，不识别任何地址、不解析任何数据内容。

#### 核心技术方向

1. 传输介质

   - 有线介质：双绞线、同轴电缆、光纤（单模光纤传输距离远、速率高；多模光纤成本低、距离近）
   - 无线介质：无线电波、微波、红外线、毫米波
2. 编码与调制

   - 编码：将数字比特转换为数字信号，如曼彻斯特编码、差分曼彻斯特编码
   - 调制：将数字比特加载到模拟载波上，如 QAM 调制、OFDM 调制，Wi-Fi、移动通信均采用调制技术
3. 接口标准 定义接口的引脚定义、电气特性、速率规格、物理尺寸，如 RJ45 以太网接口标准。

### 3.2 数据链路层

数据链路层分为两个子层：MAC 子层（介质访问控制）和 LLC 子层（逻辑链路控制）。

#### 3.2.1 MAC 子层

核心职责：控制设备如何访问共享的物理信道，解决多设备同时发送数据的冲突问题，定义数据帧的封装格式。

1. 介质访问控制机制

   - CSMA/CD（载波监听多路访问 / 冲突检测）：用于传统共享式以太网。发送前先监听信道是否空闲，空闲则发送；发送过程中持续检测冲突，检测到冲突则立即停止发送，发送干扰信号，执行二进制指数退避算法后重试。
   - CSMA/CA（载波监听多路访问 / 冲突避免）：用于 Wi-Fi 无线网络。发送前先监听信道，空闲时先发送 RTS 预约帧，收到 CTS 确认帧后再发送数据，通过预约机制减少冲突。
2. 帧封装 MAC 子层为数据添加源 MAC 地址、目的 MAC 地址的头部，以及 CRC 帧校验序列的尾部，构成完整的以太网帧。

#### 3.2.2 LLC 子层

核心职责：

1. 提供逻辑链路标识（SAP 服务访问点），区分上层的不同协议，将数据准确交付给对应的网络层协议
2. 实现链路层的流量控制与差错恢复机制

### 3.4 MAC 地址详解

1. 定义与格式 MAC 地址（介质访问控制地址）是烧录在网卡 ROM 中的物理地址，共 48 位（6 字节），通常用十六进制冒号分隔表示，例如 `00:1A:2B:3C:4D:5E`。
2. 地址组成

   - 前 24 位：OUI（组织唯一标识符），由 IEEE 统一分配给网卡厂商，标识生产厂商
   - 后 24 位：厂商自定义序列号，每个网卡唯一
   - 组合起来保证全球范围内每个网卡的 MAC 地址唯一
3. 核心特性

   - 硬件属性：出厂固化，一般不可修改
   - 局域网有效：仅在同一个广播域（局域网）内有效，无法跨路由器进行广域网寻址
4. 核心应用场景

   - 局域网数据帧转发：交换机基于 MAC 地址表进行帧转发
   - ARP 地址解析：实现 IP 地址到 MAC 地址的映射
   - 网络安全：MAC 地址白名单、端口安全、接入认证

### 3.5 ARP 与 RARP 协议

#### ARP 协议（地址解析协议）

1. 功能：根据目标 IP 地址，查询对应设备的 MAC 地址，实现 IP 地址到硬件地址的转换，是局域网 IP 通信的底层基础。
2. 工作流程

   1. 主机 A 需要和主机 B 通信，先检查自身 ARP 缓存表，有对应映射则直接使用
   2. 缓存中没有则发送 ARP 广播请求报文：“IP 地址为 192.168.1.2 的设备，请回复你的 MAC 地址”
   3. 局域网内所有主机都收到广播请求，只有 IP 地址匹配的主机 B，单播回复 ARP 应答报文，告知自身 MAC 地址
   4. 主机 A 收到回复后，将 IP-MAC 映射关系存入 ARP 缓存表，后续通信直接查表
3. ARP 缓存 临时存储 IP 与 MAC 的映射关系，有老化时间，超时后自动删除，避免地址变更导致的通信错误。

#### RARP 协议（反向地址解析协议）

功能：根据 MAC 地址解析对应的 IP 地址，主要用于无盘工作站启动时获取自身 IP 地址，目前基本被 DHCP 协议取代。

### 3.6 交换机工作原理

交换机工作在数据链路层，基于 MAC 地址转发数据帧，核心机制是自学习 + 转发：

1. 自学习：收到一个数据帧后，将帧的源 MAC 地址与接收端口做映射，存入 MAC 地址表
2. 转发决策：根据帧的目的 MAC 地址查表 

   - 查表成功：从对应端口单播转发
   - 查表失败：向除接收端口外的所有端口广播泛洪
3. 核心作用：隔离冲突域，每个端口都是独立的冲突域；但所有端口同属一个广播域，无法隔离广播报文。

### 3.7 冲突域与广播域

1. 冲突域 同一网络区域内，两台设备同时发送数据会产生信号冲突，这个区域就是一个冲突域。 

   - 集线器的所有端口同属一个冲突域
   - 交换机的每个端口都是独立的冲突域
2. 广播域 广播报文能够传播覆盖的网络范围，称为广播域。 

   - 交换机、集线器都无法隔离广播域
   - 路由器默认不转发广播报文，可以隔离广播域

## 网络层与 IP 协议

### 4.1 网络层核心职能

网络层负责解决跨网段、跨主机的端到端寻址与路径选择问题，实现数据从源主机到目标主机的跨网络转发，核心设备是路由器。 核心职能包括：

1. 寻址：通过 IP 地址唯一标识全网设备
2. 路由选择：通过路由算法选择最优传输路径
3. 分组转发：根据路由表逐跳转发数据包
4. 分片与重组：数据包超过链路 MTU 时进行分片，到达目的端后重组
5. 差错报告：通过 ICMP 反馈网络错误与状态

### 4.2 IP 协议核心特性

IP（网际协议）是网络层的核心协议，两大核心特性：

1. 无连接：发送数据前不需要建立专用连接，每个数据包独立选路传输
2. 不可靠：不保证数据包一定送达，不保证顺序，不保证不重复，不做差错恢复 可靠性保障完全由上层 TCP 协议实现，IP 协议只负责最高效率的转发。

### 4.4 IPv4 地址体系

#### 4.4.1 地址基础

- 表示方式：点分十进制，例如 `192.168.1.1`
- 本质：32 位二进制整数，分为 4 个 8 位组
- 地址组成：网络号 + 主机号

  - 网络号：标识设备所属的网段，同一网段内所有主机的网络号相同
  - 主机号：标识网段内的具体主机，同一网段内主机号唯一
- 特殊地址：`127.0.0.0/8` 为本地回环地址，用于本机内部进程通信，数据不会流出网卡。

1. 子网掩码核心作用 明确 IP 地址中网络位和主机位的边界，用于判断两个 IP 是否属于同一个网段。  

   - 二进制特征：由连续的 1 和连续的 0 组成，1 对应网络位，0 对应主机位
   - 默认掩码：A 类 `255.0.0.0`，B 类 `255.255.0.0`，C 类 `255.255.255.0`
2. 计算规则 将 IP 地址与子网掩码做按位与运算，得到的结果就是网络地址。 示例计算： 

```c
IP地址：   192.168.1.100 → 11000000.10101000.00000001.01100100
子网掩码： 255.255.255.0 → 11111111.11111111.11111111.00000000
按位与 →  11000000.10101000.00000001.00000000 → 192.168.1.0（网络地址）
```

1. CIDR 无类域间路由 废除传统分类，用「IP / 前缀长度」的方式表示，前缀长度即网络位的位数。 例如 `192.168.1.0/24`，表示前 24 位为网络位，后 8 位为主机位。

#### 4.4.5 子网划分

通过借用主机位作为子网位，将一个大网段拆分为多个小子网，提升 IP 利用率、隔离广播域、便于分级管理。标准计算步骤（以 C 类地址 `192.168.1.0/24` 划分为 4 个子网为例）：

1. 确定子网位数：根据需求子网数，计算需要借用的主机位数 n，满足 `2^n ≥ 子网数`。4 个子网需要 n=2 位。
2. 计算新掩码：新掩码前缀长度 = 原掩码长度 + n → /24 + 2 = /26，对应点分十进制 `255.255.255.192`。
3. 计算块大小：每个子网的地址总数 = `2^(剩余主机位)` = `2^(32-26) = 64` 个地址。
4. 计算可用主机数：每个子网可用主机数 = 地址总数 - 2（减去网络地址和广播地址）→ 64 - 2 = 62 台。

### 4.5 IPv6 协议基础

1. 地址长度：128 位二进制地址，理论地址总数约 `3.4×10^38`，彻底解决 IPv4 地址枯竭的问题。
2. 报文优势：固定 40 字节基本首部，取消首部校验和，简化了路由器处理逻辑，提升转发效率。
3. 地址类型：单播地址、组播地址、任播地址，取消了广播地址，全部用组播替代。
4. 表示方法：冒分十六进制，每 16 位为一组，共 8 组；连续的 0 可以缩写为 `::`，且只能缩写一次。 示例：`2001:0db8:85a3:0000:0000:8a2e:0370:7334` 可简写为 `2001:db8:85a3::8a2e:370:7334`。

### 4.6 路由原理

#### 核心概念

- 路由表：路由器 / 主机中存储的转发规则表，每条规则包含「目标网段、下一跳地址、出接口」三个核心要素。
- 最长匹配原则：当一个目的 IP 匹配多条路由条目时，优先选择前缀长度最长的条目进行转发，保证转发精度。

#### 路由分类



1. 直连路由：路由器接口直接连接的网段，自动生成路由条目，无需手动配置。
2. 静态路由：管理员手动配置的路由条目，适合小型、拓扑稳定的网络；优点是稳定、不占用带宽，缺点是拓扑变化时无法自动更新。
3. 动态路由：通过路由协议自动学习、更新路由表，适合大型、拓扑复杂的网络。 

   - 内部网关协议（IGP）：自治系统内部使用，如 OSPF（链路状态型）、RIP（距离矢量型）
   - 外部网关协议（EGP）：自治系统之间使用，如 BGP，是互联网骨干网的核心路由协议

### 4.7 NAT 网络地址转换

#### 核心作用

实现私网 IP 地址与公网 IP 地址的转换，让大量内网设备共享少量公网 IP 访问互联网，是缓解 IPv4 地址枯竭的核心技术。

#### 常见类型

1. 静态 NAT：私网 IP 与公网 IP 一对一固定映射，适合对外提供服务的内网服务器。
2. 动态 NAT：从公网地址池中动态分配地址进行映射，公网 IP 用完则新设备无法上网。
3. PAT（端口地址转换）：也叫 NAPT，多个私网 IP 映射到同一个公网 IP 的不同端口号，是家用路由器、企业网关的默认工作模式，可同时支持大量内网设备上网。

### 4.8 网络层配套协议

#### ICMP 协议（互联网控制报文协议）

1. 核心功能：传递网络控制消息，如目标不可达、超时、重定向、参数错误等，用于网络诊断与错误反馈。
2. 典型应用

   - `ping` 命令：发送 ICMP 回显请求报文，接收回显应答报文，测试网络连通性与延迟。
   - `traceroute` 命令：基于 TTL 递减 + ICMP 超时消息，追踪数据包从源到目的的完整转发路径。
3. 注意：ICMP 封装在 IP 数据包中传输，属于网络层协议。

#### IGMP 协议（互联网组管理协议）

1. 核心功能：管理组播组成员，主机通过 IGMP 报文向路由器声明加入或离开某个组播组。
2. 作用：路由器根据 IGMP 信息维护组播组成员表，只向有成员的网段转发组播流量，节省带宽。
3. 应用场景：IPTV、直播、视频会议等一对多数据传输场景。

### 5.1 传输层核心定位

网络层负责主机到主机的送达，传输层进一步实现进程到进程的逻辑通信，是用户业务与网络底层的衔接层。 核心职能：

1. 端到端进程通信：通过端口号区分同一主机上的不同应用进程

### 5.4 TCP 传输控制协议

#### 5.4.1 三大核心特性总览

1. 面向连接：通信前必须通过三次握手建立连接，通信结束通过四次挥手正常断开，内核维护完整的连接状态。
2. 可靠传输：通过确认应答、超时重传、排序去重、校验等机制，保证数据准确、有序、完整地送达对端。
3. 流量控制：通过滑动窗口机制，根据接收方的处理能力动态调整发送速率，防止接收方缓冲区溢出。

#### 5.4.2 三次握手与连接建立

##### 握手流程

1. 第一次握手：客户端向服务端发送 SYN 同步报文，携带自身初始序列号 ISN，客户端进入`SYN_SENT`状态。
2. 第二次握手：服务端收到 SYN 后，回复 SYN+ACK 报文，确认客户端的序列号，同时携带自身初始序列号，服务端进入`SYN_RCVD`状态。
3. 第三次握手：客户端收到 SYN+ACK 后，回复 ACK 确认报文，确认服务端的序列号，客户端进入`ESTABLISHED`状态；服务端收到 ACK 后，也进入`ESTABLISHED`状态，连接正式建立。

##### 为什么是三次，不是两次

1. 确认双方的收发能力都正常：三次握手才能让双方都确认「自己发、自己收、对方发、对方收」四个能力都正常。
2. 防止失效的连接请求到达服务端，导致错误建立连接：两次握手的话，过期的 SYN 报文到达服务端，服务端会直接建立连接，浪费资源。
3. 同步双方的初始序列号：TCP 可靠传输依赖序列号，必须让双方确认彼此的初始序列号，三次握手才能完成双向同步。

#### 5.4.3 四次挥手与连接断开

TCP 是全双工通道，两个方向需要独立关闭，因此需要四次交互。

##### 挥手流程

1. 第一次挥手：主动关闭方发送 FIN 结束报文，表示本方不再发送数据，进入`FIN_WAIT_1`状态。
2. 第二次挥手：被动关闭方回复 ACK 确认报文，进入`CLOSE_WAIT`状态；主动方收到 ACK 后进入`FIN_WAIT_2`状态。此时只是关闭了主动方到被动方的方向，被动方仍然可以继续发送数据。
3. 第三次挥手：被动方数据发送完毕后，发送 FIN 结束报文，表示本方也不再发送数据，进入`LAST_ACK`状态。
4. 第四次挥手：主动关闭方回复 ACK 确认报文，进入`TIME_WAIT`状态；被动方收到 ACK 后直接关闭连接；主动方等待 2MSL 时间后，也关闭连接。

#### 5.4.4 TIME_WAIT 状态深度解析

1. 持续时间：2MSL，即两倍的报文最大生存时间，Linux 默认一般为 60 秒。
2. 存在的两个核心目的

   - 保证最后一个 ACK 可靠送达：如果最后一个 ACK 丢失，被动方会重发 FIN 报文，主动方有时间重发 ACK，避免被动方无法正常关闭。
   - 隔绝旧连接的延迟报文：让本次连接产生的所有滞留在网络中的报文全部过期消失，防止下一个复用相同端口的新连接，收到旧连接的残留报文导致数据错误。
3. 工程影响与解决方案

   - 影响：高并发短连接场景下，服务端会产生大量 TIME_WAIT 状态的连接，占用端口与内核资源。
   - 解决方案：通过`setsockopt`设置`SO_REUSEADDR`端口复用选项，允许处于 TIME_WAIT 状态的端口被重新绑定使用。

#### 5.4.5 可靠传输实现机制

TCP 的可靠性完全由内核协议栈自动实现，无需应用层代码处理：

1. 确认应答机制：接收方每收到数据，都要回复 ACK 确认报文，告知发送方已经收到。
2. 超时重传：发送方发出数据后启动定时器，超时未收到 ACK 则自动重传对应的数据。
3. 乱序重组：数据包可能因路由不同而乱序到达，接收方根据序列号重新排序，再交付给应用层。
4. 去重处理：网络中重复到达的数据包，接收方根据序列号直接丢弃。
5. 校验和：TCP 头部包含校验和，检测传输过程中的比特错误，出错则丢弃报文。

#### 5.4.6 流量控制与滑动窗口

1. 核心目的：根据接收方的接收缓冲区剩余空间，动态调整发送方的发送速率，防止发送过快导致接收方缓冲区溢出。
2. 滑动窗口机制

   - 接收方在 TCP 头部的窗口字段中，告知发送方自身接收缓冲区的剩余可用大小。
   - 发送方根据窗口大小，调整自己的发送窗口大小，发送的数据量不能超过接收窗口。
   - 随着数据的发送与确认，窗口整体向前滑动，因此称为滑动窗口。
3. 窗口大小为 0 时，发送方停止发送数据；定期发送窗口探测报文，询问接收方窗口是否更新。

#### 5.4.7 拥塞控制四大算法

流量控制是点对点的控制，拥塞控制是对整个网络承载能力的控制，防止发送过多数据导致网络拥堵。

1. 慢启动：连接建立初期，拥塞窗口从 1 开始指数增长，快速探测网络带宽，直到达到慢启动阈值。
2. 拥塞避免：达到慢启动阈值后，拥塞窗口线性增长，平稳提升发送速率，避免快速填满网络。
3. 快重传：连续收到三次重复的 ACK 确认，立即重传对应丢失的报文，无需等待超时定时器到期。
4. 快恢复：触发快重传时，将拥塞窗口减半，直接进入拥塞避免阶段，避免窗口降到最低，提升传输效率。

#### 5.4.8 字节流特性与粘包拆包

1. 字节流本质：TCP 没有天然的数据包边界，仅将数据看作一串连续的字节流，和读写文件完全一致。
2. 粘包 / 拆包问题

   - 粘包：多次发送的数据，被一次全部读取出来，多个数据包粘在一起。
   - 拆包：一次发送的数据，被分多次读取出来，一个数据包被拆分。
   - 产生原因：TCP 内核缓冲区、MSS 限制、Nagle 算法等。
3. 解决方案：应用层自定义协议实现分包 

   - 固定长度包：每个数据包长度固定，读满指定长度即为一个完整包
   - 长度字段头：数据包头部固定位置存放包体长度，先读长度再读对应长度的数据
   - 特殊分隔符：用特定的字符 / 字符串作为包的边界，读到分隔符即为一个完整包

### 5.5 UDP 用户数据报协议

1. 核心特性

   - 无连接：通信前不需要建立连接，每个数据包独立封装地址信息，发完即释放上下文。
   - 不可靠：没有确认应答、没有重传、没有排序，丢包、乱序都需要应用层自行处理。
   - 面向报文：一次发送对应一个独立的报文，有明确的包边界，不会产生粘包拆包问题。
   - 轻量化：UDP 头部仅 8 字节，开销极小，传输延迟低。
   - 支持广播、组播通信。
2. 适用场景 实时性优先、可容忍少量丢包的场景：直播、语音通话、在线游戏、DNS 查询、网络监控等。

## 应用层与架构模式

### 6.1 应用层核心作用

应用层是分层模型的最顶层，直接面向用户业务，核心职能：

1. 定义应用之间的数据格式、交互规则、命令语义
2. 封装底层网络细节，为用户提供可直接使用的网络服务
3. 协议种类最多，不同业务场景对应不同的应用层协议

### 6.2 经典应用层协议

### 6.3 C/S 架构（Client-Server客户端 - 服务器）

1. 核心模式：客户端安装专用的软件程序，主动向服务器发起请求；服务器集中部署，处理所有客户端的请求并返回结果。
2. 优点

   - 性能更高：客户端可以分担计算、渲染压力，充分利用本地硬件资源
   - 定制化强：可深度优化界面与功能，用户体验更好
   - 功能丰富：可直接调用本地系统与硬件资源，不受浏览器限制
3. 缺点

   - 开发维护成本高：需要为不同平台（Windows、macOS、Android、iOS）分别开发客户端
   - 升级困难：需要用户手动更新客户端版本，版本迭代慢
4. 典型应用：大型网游、桌面办公软件、专业设计工具、即时通讯客户端

### 6.4 B/S 架构（Brower-Server浏览器 - 服务器）

1. 核心模式：浏览器作为统一的客户端，用户通过 HTTP/HTTPS 协议访问服务端，服务端返回页面，浏览器渲染展示。
2. 优点

   - 跨平台：任何设备只要有浏览器就能访问，无需安装客户端
   - 易维护：升级只需要更新服务端代码，用户无感知，全网即时生效
   - 部署简单：仅需部署服务端，客户端零部署成本
3. 缺点

   - 性能受限：复杂计算、渲染都依赖服务端或浏览器，性能弱于原生客户端
   - 功能受限：受浏览器沙箱机制限制，无法直接访问本地系统资源与硬件
4. 典型应用：门户网站、在线办公系统、电商网站、各类 Web 应用

## Socket 编程基础

### 7.1 套接字（Socket）本质

1. 定义：套接字是应用层与 TCP/IP 协议栈之间的抽象编程接口，封装了底层网络的复杂细节，让开发者可以像操作文件一样进行网络通信。
2. Linux 下的本质：遵循 “万物皆文件” 的设计思想，socket 是一种特殊的文件描述符，支持 read、write、close 等通用文件操作。
3. 作用：屏蔽了内核协议栈、硬件网卡的底层差异，为开发者提供统一、易用的网络编程接口。

### 7.2 套接字三大类型

### 7.3 TCP 编程标准流程

#### 7.3.1 服务端（被动监听连接）

1. socket()：创建套接字文件描述符，指定协议族、套接字类型。
2. bind()：将套接字绑定到本机的 IP 地址和端口号；`INADDR_ANY`表示绑定所有网卡地址。
3. listen()：将套接字设置为监听状态，内核创建半连接队列和全连接队列；`backlog`参数指定全连接队列的最大长度。
4. accept()：阻塞等待，从全连接队列中取出一个已经完成三次握手的连接，返回新的专属通信文件描述符。 

> 1. 注意：监听 fd 只负责接收新连接，不参与业务数据的收发；每个客户端连接对应一个独立的通信 fd。

1. send() / recv()：通过通信 fd 进行数据的发送与接收，执行业务逻辑。
2. close()：关闭文件描述符，触发 TCP 四次挥手流程，释放连接资源。

#### 7.3.2 客户端（主动发起连接）

1. socket()：创建客户端套接字文件描述符。
2. connect()：向指定的服务端 IP + 端口发起 TCP 连接请求，内核执行三次握手流程。
3. send() / recv()：连接建立成功后，直接通过该 fd 收发业务数据。
4. close()：关闭套接字，断开连接。

### 7.4 UDP 编程流程

UDP 无需建立连接，编程流程更简单：

- 服务端：`socket()` → `bind()` 绑定端口 → `recvfrom()` 接收数据（可获取对端地址）→ `sendto()` 发送数据 → `close()`
- 客户端：`socket()` → `sendto()` 直接向指定地址发送数据 → `recvfrom()` 接收回复 → `close()`

### 7.5 网络字节序

#### 字节序本质

多字节数据在内存中的存储顺序，分为两种：

1. 大端序：高位字节存放在低地址，低位字节存放在高地址，符合人类书写习惯。 示例：数值 `0x12345678` 内存中存储为 `12 34 56 78`
2. 小端序：低位字节存放在低地址，高位字节存放在高地址。 示例：数值 `0x12345678` 内存中存储为 `78 56 34 12`

#### 网络标准

TCP/IP 协议规定：网络中传输的所有多字节数据，统一使用大端序，称为网络字节序。 目的：解决不同 CPU 架构字节序不一致的问题，保证跨平台通信的数据解析正确。

### 7.6 IP 地址格式转换

实现点分十进制字符串与网络字节序整数之间的互相转换：

1. inet_addr()

   - 功能：将点分十进制的 IP 字符串，转换为网络字节序的 32 位无符号整数
   - 原型：`in_addr_t inet_addr(const char *cp);`
2. inet_ntoa()

   - 功能：将网络字节序的 32 位 IP 整数，转换为点分十进制字符串
   - 原型：`char *inet_ntoa(struct in_addr in);`
   - 注意：返回值指向静态分配的内存，不可重入，多线程环境下不安全。
3. 进阶函数：`inet_pton()` / `inet_ntop()`，同时支持 IPv4 和 IPv6，线程安全，是更推荐的写法。

### 7.7 核心编程注意事项

1. send 返回值的意义`send` 成功返回，仅代表数据成功写入了内核发送缓冲区，绝不代表对端应用程序已经收到数据；后续由内核异步完成发送。
2. 连接关闭的判断

   - 正常关闭：`recv` 返回 0，表示对端正常执行了 close 操作，连接已断开。
   - 异常断开：对端进程崩溃、网络中断、断电等情况，TCP 层无法自动感知，必须由应用层通过心跳包 + 超时机制来检测连接状态。
3. TCP 粘包处理 基于 TCP 的应用，必须在应用层设计自定义协议，通过长度头、分隔符等方式实现分包，不能假设一次 recv 对应一次 send 的数据。

## IO 模型与高并发演进

### 8.1 Unix 标准五大 IO 模型

对于一次 IO 操作，分为两个阶段：等待数据就绪、将数据从内核拷贝到用户态。根据这两个阶段的不同处理方式，分为五种 IO 模型：

1. 阻塞 IO 数据未就绪时，进程挂起阻塞，一直等待数据就绪并拷贝完成后才返回。 优点：逻辑简单；缺点：并发能力极低，一个连接阻塞整个程序。
2. 非阻塞 IO 数据未就绪时，立即返回错误，不阻塞进程；需要程序轮询反复调用。 缺点：大量空轮询浪费 CPU 资源，实际很少单独使用。
3. IO 多路复用 单个线程同时监控大量文件描述符，批量等待数据就绪；有任意 fd 就绪后，再逐个处理 IO。 是高并发网络服务的核心方案，代表实现：select、poll、epoll。
4. 信号驱动 IO 注册信号处理函数，数据就绪时内核发送`SIGIO`信号通知进程。 异步通知机制，但处理逻辑复杂，实际工程应用较少。
5. 异步 IO（AIO） 发起 IO 请求后立即返回，整个 IO 过程（等待数据 + 拷贝到用户态）全部由内核完成，完成后通知进程。 真正的全异步 IO，理论性能最高，但实现复杂度高，Linux 原生支持有限。

### 8.2 IO 多路复用三剑客详解

#### 8.2.1 select

1. 实现机制

   - 用`fd_set`位图结构存储待监控的文件描述符，默认最大支持 1024 个 fd
   - 每次调用都要把 fd 集合从用户态全量拷贝到内核态
   - 内核线性遍历所有 fd，检查哪些 fd 就绪
   - 返回后再全量拷贝回用户态，程序需要遍历所有 fd 才能找出就绪项
2. 缺点

   - fd 数量有硬上限，默认 1024
   - 每次调用都有两次全量拷贝，连接数越多开销越大
   - 内核线性扫描，时间复杂度 O (n)，连接数越多效率越低
   - 每次调用都要重置 fd 集合
3. 优点：跨平台兼容性好，几乎所有系统都支持。

#### 8.2.2 poll

1. 实现机制

   - 用`pollfd`结构体数组存储待监控的 fd，没有数量硬上限
   - 其余机制和 select 基本一致，仍然需要全量拷贝、内核线性遍历
2. 改进点：解决了 select 的 fd 数量上限问题
3. 本质缺陷：性能没有本质提升，连接数多的时候效率依然很低。

#### 8.2.3 epoll（Linux 独有，当前最优方案）

1. 核心数据结构

   - 红黑树：内核中用红黑树存储所有待监控的 fd，增删改查效率高
   - 就绪链表：单独维护一个就绪链表，已经就绪的 fd 会被加入该链表
2. 三大核心接口

   - `epoll_create`：创建 epoll 实例，在内核中建立红黑树与就绪链表
   - `epoll_ctl`：增、删、改待监控的文件描述符，仅操作时拷贝一次数据
   - `epoll_wait`：等待事件，只需要检查就绪链表是否为空，有数据则拷贝就绪事件到用户态
3. 两种触发模式

   - LT 水平触发（默认）：只要 fd 上还有未处理的数据，就会持续通知。编程简单，不易出错，支持阻塞 / 非阻塞 IO。
   - ET 边缘触发：只有状态发生变化时才通知一次，要求程序一次性把数据读完。减少了事件触发次数，效率更高，必须配合非阻塞 IO 使用。
4. 高性能原因

   - 无 fd 数量上限，仅受限于系统资源
   - 无需全量拷贝 fd 集合，仅增删时拷贝，就绪事件拷贝量小
   - 无需线性遍历全部 fd，就绪链表直接获取结果，时间复杂度 O (1)
   - 是 Nginx、Redis 等高性能服务的底层核心 IO 模型。

### 8.3 高并发服务架构演进路径

1. 单进程单连接：串行处理，仅用于教学演示，无实际并发能力。
2. 多进程并发：每来一个连接 fork 一个子进程处理。优点是隔离性好，缺点是进程开销大，无法支撑海量连接。
3. 多线程并发：每来一个连接创建一个线程处理。开销小于多进程，但线程上下文切换依然有成本，并发上限有限。
4. 单线程 Reactor 模式：epoll + 事件循环，单线程处理所有连接的 IO 与业务，代表实现 Redis。优点是无锁、开销极低，缺点是无法利用多核 CPU。
5. 多线程 Reactor 模式：主 Reactor 负责接收新连接，分发给多个子 Reactor 处理 IO，代表实现 Nginx。充分利用多核，是当前主流高性能方案。
6. Proactor 模式：全异步 IO，内核完成整个 IO 后通知业务，理论性能更高，但实现复杂度高。

## 网络编程第一性原理

### 9.1 核心公理

Linux 遵循 “万物皆文件” 的设计思想，网络套接字 socket 本质上是一种特殊的文件描述符。 所有网络通信，本质都是对这个特殊文件描述符的读写操作；进程永远不直接操作网卡硬件，所有数据收发都通过内核缓冲区中转。

### 9.2 内核双缓冲区机制

每个 socket 在内核中都有两个独立的缓冲区：发送缓冲区、接收缓冲区，是网络通信的核心载体。

1. 发送缓冲区

   - 位置：内核空间，每个 socket 独立拥有
   - 写入流程：进程调用`send/write`，将数据从用户态内存拷贝到内核发送缓冲区，系统调用即可返回。
   - 后续流程：内核协议栈 + 网卡驱动异步完成数据封装，通过网卡硬件发送到网络中。
2. 接收缓冲区

   - 位置：内核空间，每个 socket 独立拥有
   - 写入流程：网卡收到网络数据，通过硬件中断处理，将数据存入对应 socket 的内核接收缓冲区。
   - 读取流程：进程调用`recv/read`，将数据从内核接收缓冲区拷贝到用户态内存。
3. 缓冲区的核心价值

   - 解耦：应用层的读写速率与硬件的传输速率解耦，应用无需关心硬件发送节奏
   - 平滑流量：应对突发数据，减少系统调用次数，提升整体效率
   - 协议支撑：TCP 的重传、排序、流量控制、拥塞控制等所有特性，都依赖缓冲区实现

### 9.3 核心底层认知

1. send 成功 ≠ 对端收到`send` 成功返回，只代表数据进入了内核发送缓冲区，不代表数据已经发出，更不代表对端应用程序已经收到。
2. TCP 是字节流，无边界 不要假设一次 recv 对应一次 send 的数据，粘包拆包是 TCP 的固有特性，应用层必须自定义协议分包。
3. 正常关闭与异常断开

   - 正常关闭：对端调用 close，己方 recv 会返回 0，可以优雅处理。
   - 异常断开：进程崩溃、网络中断、断电等情况，TCP 层无法自动感知，必须由应用层实现心跳包 + 超时检测。
4. 内核负责可靠性 TCP 的所有可靠性机制（重传、排序、流量控制等）都由内核协议栈自动完成，应用层代码无需手动处理。

## 网络程序终极公式

网络程序 = socket 文件描述符 + 内核双缓冲区 + IO 模型 + 传输层协议 + 应用层自定义协议

1. 硬件层：网卡负责物理比特流的收发
2. 内核层：TCP/IP 协议栈完成报文封装、路由、可靠性保障、缓冲区管理
3. 系统调用层：socket 接口封装底层逻辑，以文件描述符的形式暴露给用户态
4. 并发层：根据性能需求选择对应的 IO 模型与并发架构
5. 业务层：基于传输层特性，设计应用层协议与业务逻辑

# TCP通信详细

## 一、TCP 与 UDP 核心对比

### 1 TCP 核心特性

- 面向连接：通信前必须三次握手建立专属连接，通信结束四次挥手断开
- 可靠传输：内置 ACK 确认、超时重传、乱序重组、去重、校验机制
- 流量控制 + 拥塞控制：滑动窗口机制，分别控制对端接收能力与全网负载
- 全双工：读写独立内核缓冲区，两端可同时收发
- 头部固定 20 字节，连接维护逻辑复杂，延迟更高适用场景：HTTP/HTTPS 网页、FTP 文件传输、SSH 远程登录、邮件收发等对数据完整性要求高的业务

### 2 UDP 核心特性

- 无连接：无需握手，每个报文独立携带地址信息，发完无连接上下文
- 尽力交付：无重传、无确认，丢包乱序上层自行处理
- 无流量 / 拥塞控制，头部仅 8 字节，开销极低，实时性好适用场景：直播 RTP、DNS 域名查询、在线游戏、VoIP 语音通话

- `AF_INET6`：IPv6 通信
- `AF_UNIX/AF_LOCAL`：本机进程本地套接字通信
- `AF_PACKET`：原始链路层套接字

1. `type` 套接字类型

- `SOCK_STREAM`：TCP 流式套接字
- `SOCK_DGRAM`：UDP 数据报套接字
- `SOCK_RAW`：原始套接字，自定义 IP 报文

1. `protocol` 附加协议，无特殊需求直接填 0，内核自动匹配对应协议

返回值：

成功：返回非负文件描述符 fd；失败：返回 - 1，全局变量 errno 记录错误码

补充知识点：

Linux 一切皆文件，socket 返回 fd 和普通文件 fd 操作方式一致，均可 read/write/close。

### 2 bind () 绑定 IP + 端口到套接字

函数原型：

```c
int bind(int sockfd, const struct sockaddr *addr, socklen_t addrlen);
```

参数：

1. `sockfd`：socket 创建的套接字 fd
2. `addr` 通用地址结构体，IPv4 专用结构体 `struct sockaddr_in`

```c
struct sockaddr_in {
    sa_family_t sin_family;  // 协议族 AF_INET
    in_port_t sin_port;      // 端口号（必须网络序htons转换）
    struct in_addr sin_addr; // IPv4地址
};
struct in_addr {
    uint32_t s_addr; // 32位网络序IP
};
```

1. `addrlen`：地址结构体字节大小，一般填`sizeof(struct sockaddr_in)`

返回值：

成功 0，失败 - 1

补充重点：

1. 端口必须使用`htons()`转网络大端序；IP 用`inet_addr("192.168.1.1")`转换
2. `sin_addr.s_addr = INADDR_ANY` 代表绑定本机所有网卡（0.0.0.0）
3. 只有服务端必须 bind，客户端一般不 bind，操作系统自动分配随机临时端口

### 3 listen () 设置监听状态

原型：

```c
int listen(int sockfd, int backlog);
```

参数：

- sockfd：已 bind 的服务端套接字
- backlog：全连接队列最大长度

底层双队列机制（重点补充）：

1. 半连接队列（SYN 队列）：存放收到 SYN、未完成三次握手的客户端
2. 全连接队列（ACCEPT 队列）：三次握手完全完成，等待 accept 取出的连接 backlog 参数限制全连接队列上限；队列满后新客户端 SYN 会直接丢弃，连接失败

返回值：成功 0，失败 - 1

补充：

listen 只能用于 TCP 流式套接字，UDP 无连接不需要 listen

### 4 accept () 阻塞获取完成握手的连接

原型：

```c
int accept(int sockfd, struct sockaddr *addr, socklen_t *addrlen);
```

参数：

1. sockfd：监听套接字（listen 后的 fd）
2. addr：输出参数，存储客户端 IP、端口，不需要客户端信息传 NULL
3. addrlen：输入输出，传入 addr 缓冲区长度，函数返回时更新客户端地址实际长度，不需要传 NULL

返回值：

成功：返回全新通信 fd（专门和单个客户端收发）；失败 - 1

核心区分（高频考点）：

- 监听 fd（sockfd）：只负责接收新连接，永远不收发业务数据
- accept 返回新 fd：单客户端专属通信通道，读写只能用这个 fd

补充：

默认阻塞调用：全连接队列为空时，进程休眠等待新连接到来；可通过 fcntl 设置非阻塞。

### 5 connect () 客户端发起 TCP 握手

原型：

```c
int connect(int sockfd, const struct sockaddr *addr, socklen_t addrlen);
```

参数：

1. sockfd：客户端 socket 创建的 fd
2. addr：目标服务端 IP + 端口结构体
3. addrlen：结构体大小

返回值：

成功 0（三次握手完成）；失败 - 1（端口未监听、网络不通等）

补充：

1. connect 内部自动完成完整三次握手流程
2. 客户端无需 bind，操作系统自动分配临时端口；若需要固定客户端端口，可手动 bind 后再 connect

### 6 send () 发送数据

**原型：**

```c
ssize_t send(int sockfd, const void *buf, size_t len, int flags);
```

**参数：**

- sockfd：通信 fd（accept 返回 / 客户端 socket fd）
- buf：待发送数据缓冲区
- len：缓冲区字节长度
- flags：控制标志，日常业务填 0（阻塞发送） 

  - `MSG_DONTWAIT`：非阻塞发送
  - `MSG_PEEK`：仅查看缓冲区数据，不取出（send 极少用）

**返回值：**

正数：实际写入内核发送缓冲区字节数；0 代表无数据；-1 发送失败

**关键补充（必背）：**

send 返回成功 ≠ 对方程序收到数据，仅代表数据拷贝到本机内核发送缓冲区，内核后续异步发包。

### 7 recv () 接收数据

原型：

```c
ssize_t recv(int sockfd, void *buf, size_t len, int flags);
```

**参数：**

flags 日常传 0 阻塞读取

返回值：

> 1. 0：读到的数据字节数

1. =0：对端调用 close 正常关闭连接（四次挥手完成）
2. -1：读取出错（网络异常）

补充：

TCP 字节流无边界，单次 recv 不一定读完一次 send 的数据，存在粘包 / 拆包，上层必须自定义协议（长度头 / 分隔符）分包。

### 8 close () 关闭套接字

原型：

```c
int close(int fd);
```

**功能：**

关闭文件描述符，内核自动发起 TCP 四次挥手断开连接，释放 fd 资源

**补充：**

1. 多线程共享 fd 时，close 仅减少 fd 引用计数，计数归 0 才真正断开连接
2. 服务端必须及时 close 客户端通信 fd，否则 fd 耗尽无法新建连接

## 三、TCP 服务端完整执行流程（分步）

1. `socket()` 创建 SOCK_STREAM 流式 TCP 套接字
2. 填充`sockaddr_in`结构体，配置本机监听 IP、端口
3. `bind()` 将 IP 端口绑定到套接字
4. `listen()` 开启监听，创建半连接、全连接队列
5. `accept()` 阻塞等待客户端完成三次握手，返回专属通信 fd
6. 循环`recv()`/`send()` 与客户端交互业务数据
7. 通信结束调用`close()`关闭通信 fd，释放资源

## 四、TCP 客户端完整执行流程（分步）

1. `socket()` 创建 TCP 流式套接字
2. 填充服务端`sockaddr_in`结构体（目标 IP、目标端口）
3. `connect()` 向服务端发起三次握手建立连接
4. `send()`/`recv()` 收发业务数据
5. `close()` 关闭套接字，断开连接

## 五、完整 TCP 三次握手底层流程（结合队列图补充）

### 1 客户端执行 connect () 触发握手

1. 客户端随机生成初始序列号 ISN，发送 SYN 报文
2. 开启重传定时器，等待服务端回复

### 2 服务端处理 SYN 报文

1. 收到 SYN 后，生成自身 ISN，回复 SYN+ACK 报文
2. 将该连接放入半连接（SYN）队列，启动超时定时器

### 3 客户端收到 SYN+ACK

1. 清除重传定时器
2. 回复单独 ACK 确认报文

### 4 服务端收到 ACK

1. 从半连接队列移除该连接
2. 将连接移入全连接队列，等待 accept 函数取出

### 5 accept 工作逻辑

程序调用 accept 时，直接从全连接队列头部取出已完成握手的连接，返回新通信 fd。

### 补充考点：为什么三次握手不能简化为两次？

1. 同步双方收发序列号，保障可靠传输基础
2. 过滤网络中延迟失效的旧 SYN 报文，避免无效连接占用服务端资源
3. 双向验证双方发送、接收能力全部正常

## 六、TCP 四次挥手完整状态流转（配图文字解析）

TCP 全双工，读写通道独立关闭，共四次交互，状态变化：

1. 第一次挥手（客户端主动关闭） 客户端 ESTABLISHED → 发送 FIN 报文 → 进入`FIN_WAIT_1`
2. 服务响应 ACK 服务端收到 FIN，回复 ACK，进入`CLOSE_WAIT`；客户端进入`FIN_WAIT_2` 此时客户端不再发数据，但服务端仍可向客户端发送剩余业务数据
3. 服务端数据发完，发送 FIN 服务端进入`LAST_ACK`状态
4. 客户端回复 ACK 确认 客户端进入`TIME_WAIT`，等待 2MSL 时长再彻底关闭（CLOSED）；服务端收到 ACK 直接释放连接

### TIME_WAIT 两大核心作用（补充）

1. 保证最后一条 ACK 报文能送达服务端，防止服务端超时重发 FIN
2. 等待网络中本次连接所有延迟数据包全部过期，避免新连接收到旧报文干扰

### 工程解决方案

服务端代码添加`setsockopt(fd, SOL_SOCKET, SO_REUSEADDR, &opt, sizeof(opt))`，开启端口复用，快速重启服务不受 TIME_WAIT 限制

## 七、拓展补充 TCP 编程高频问题

1. 粘包问题根源与解决 根源：TCP 字节流无数据包边界，内核缓冲区合并 / 拆分数据 解决方案：数据包头部固定长度字段存储包体长度；或使用特殊分隔符分割报文
2. 半关闭 shutdown () close 直接关闭读写双向通道；`shutdown(fd, SHUT_WR)`可仅关闭发送方向，保留接收，适用于上传完数据仍需等待服务返回的场景
3. 端口占用报错

- 程序未正常 close fd，大量 TIME_WAIT 连接占用端口
- 解决：SO_REUSEADDR 复用端口、合理控制短连接生命周期

1. 全连接队列满后果 backlog 设置过小，大量并发握手时新客户端 SYN 报文丢弃，客户端 connect 超时失败
2. 多进程 / 多线程 TCP 模型 服务端 accept 获取新 fd 后 fork 子进程 / 创建线程单独处理客户端，主线程持续循环 accept 接收新连接

# UDP通信详细

## 一、UDP 基础概述

### 核心定义

UDP（User Datagram Protocol，用户数据报协议）是传输层无连接、不可靠、面向数据报的通信协议，与 TCP 同属传输层，但设计逻辑完全不同。

### UDP vs TCP 核心区别


<table v-pre><tbody><tr><td>特性</td><td>UDP</td><td>TCP</td></tr><tr><td>连接性</td><td>无连接，无需三次握手 / 四次挥手</td><td>面向连接，必须建立连接才能通信</td></tr><tr><td>可靠性</td><td>不可靠，不保证数据到达、不保证顺序、无重传</td><td>可靠，具备确认应答、超时重传、顺序保证</td></tr><tr><td>数据形式</td><td>面向数据报，有明确消息边界</td><td>面向字节流，无天然边界，存在粘包问题</td></tr><tr><td>控制机制</td><td>无流量控制、无拥塞控制</td><td>有完整的流量控制、拥塞控制机制</td></tr><tr><td>资源开销</td><td>极小，仅 8 字节协议头部</td><td>较大，20 字节头部 + 连接状态维护开销</td></tr><tr><td>通信模式</td><td>支持单播、组播、广播</td><td>仅支持单播（一对一）</td></tr></tbody></table>


### UDP 优缺点与适用场景

- 优点：传输速度快、协议开销低、无需维护连接状态、支持一对多通信
- 缺点：丢包不自动重传、数据可能乱序、无流量控制易出现缓冲区满丢包
- 典型场景：实时音视频通话、直播推流、DNS 域名解析、网络游戏状态同步、物联网设备数据上报

## 二、UDP 完整通信流程

UDP 没有 “连接” 的概念，服务端无需监听、等待连接，客户端也无需主动建立连接，双方直接通过「IP + 端口」收发数据报即可。

### 服务端流程（被动接收）

1. 创建套接字：调用 `socket()` 创建 UDP 套接字（类型为 `SOCK_DGRAM`）
2. 绑定地址：调用 `bind()` 绑定固定的 IP 和端口（客户端必须知道该端口才能发送数据）
3. 接收数据：调用 `recvfrom()` 阻塞等待，收到数据后同时获取发送方的地址信息
4. 处理 + 回复：处理业务逻辑，调用 `sendto()` 向发送方回发应答数据
5. 循环通信：重复 3-4 步骤
6. 关闭套接字：调用 `close()` 释放文件描述符资源

### 客户端流程（主动发送）

1. 创建套接字：调用 `socket()` 创建 UDP 套接字
2. 发送数据：直接调用 `sendto()`，指定目标服务器的 IP 和端口，直接发送数据 

   - ✅ 客户端通常不需要 bind：操作系统会自动分配临时端口，无需固定端口
3. 接收回复：调用 `recvfrom()` 等待服务器回发的应答
4. 循环通信：重复 2-3 步骤
5. 关闭套接字：调用 `close()` 释放资源

### 和 TCP 流程的核心差异

- UDP 服务端没有 `listen()`、`accept()`：不需要监听和接收连接
- UDP 客户端没有强制的 `connect()`：不需要主动建立连接（UDP 也可以调用 connect，但仅为地址绑定，无握手过程）
- UDP 收发默认使用 `sendto/recvfrom`，每次发送都要指定目标地址，每次接收都能拿到源地址

### recvfrom：接收 UDP 数据报

<table v-pre><tbody><tr><td>参数</td><td>类型</td><td>作用</td><td>补充说明</td></tr><tr><td>sockfd</td><td>int</td><td>套接字文件描述符</td><td>UDP 通信的套接字 fd</td></tr><tr><td>buf</td><td>void*</td><td>接收缓冲区首地址</td><td>存放收到的数据内容</td></tr><tr><td>len</td><td>size_t</td><td>最大接收字节数</td><td>缓冲区大小，防止内存溢出</td></tr><tr><td>flags</td><td>int</td><td>控制标志</td><td>传0为默认阻塞模式</td></tr><tr><td>src_addr</td><td>struct sockaddr*</td><td>源地址输出参数</td><td>函数执行后，会自动填充发送方的 IP + 端口信息</td></tr><tr><td>addrlen</td><td>socklen_t*</td><td>地址长度（值 - 结果参数）</td><td>传入时指定地址结构体大小，传出时返回实际地址长度</td></tr></tbody></table>

## 四、UDP 三种通信模式

### 单播（Unicast）

**定义：**

一对一通信，一个发送端对应一个接收端，是 UDP 默认的通信模式。

**特点：**

- 目标地址为具体的主机 IP（如 192.168.1.100）
- 无需额外配置，正常调用 sendto 指定目标 IP 即可
- 数据包仅发送给指定的一台主机

**适用场景：**

普通的客户端 - 服务端点对点通信，和 TCP 的通信模式一致，但无连接开销。

#### 完整代码示例

**UDP 服务端代码：**

```c
#include <stdio.h>
#include <arpa/inet.h>
#include <sys/socket.h>
#include <string.h>
#include <unistd.h>

int main()
{
    // 1. 创建UDP套接字：SOCK_DGRAM 对应UDP协议
    int sockfd = socket(AF_INET, SOCK_DGRAM, 0);
    if(sockfd == -1)
    {
        perror("socket创建失败");
        return -1;
    }

    // 2. 绑定本机地址和端口
    struct sockaddr_in server_addr = {0};
    server_addr.sin_family = AF_INET;
    server_addr.sin_port = htons(8888);
    server_addr.sin_addr.s_addr = htonl(INADDR_ANY);

    int ret = bind(sockfd, (struct sockaddr*)&server_addr, sizeof(server_addr));
    if(ret == -1)
    {
        perror("bind绑定失败");
        close(sockfd);
        return -1;
    }
    printf("UDP服务端启动，监听8888端口...\n");

    char buf[128] = {0};
    struct sockaddr_in client_addr;
    socklen_t addr_len = sizeof(client_addr);

    while(1)
    {
        memset(buf, 0, sizeof(buf));
        // 3. 接收数据，同时获取客户端地址信息
        int recv_len = recvfrom(sockfd, buf, sizeof(buf), 0,
                                (struct sockaddr*)&client_addr, &addr_len);
        if(recv_len == -1)
        {
            perror("recvfrom接收失败");
            break;
        }

        printf("客户端[%s:%d]发来：%s\n",
               inet_ntoa(client_addr.sin_addr),
               ntohs(client_addr.sin_port),
               buf);

        // 4. 回显数据，原样发送给客户端
        sendto(sockfd, buf, recv_len, 0,
               (struct sockaddr*)&client_addr, addr_len);
    }

    close(sockfd);
    return 0;
}
```

### 广播（Broadcast）

**定义：**

一对所有通信，数据包发送到同一局域网内的所有主机，所有监听对应端口的主机都能收到。

**广播地址分类：**

1. 受限广播地址：`255.255.255.255`

   - 仅在当前局域网内传播，路由器不会转发该广播包
   - 不知道子网网段时可以使用
2. 定向广播地址：子网主机位全为 1 的地址，如`192.168.1.255`（C 类网段） 

   - 理论上可跨路由器转发，实际绝大多数路由器默认禁用，防止广播风暴
   - 仅在指定子网内生效

**编程要求：**

- 发送端：必须通过`setsockopt`开启`SO_BROADCAST`选项，否则 sendto 会直接报错
- 接收端：无需特殊配置，只需 bind 对应的端口，即可收到广播包

**开启广播代码示例：**

```c
int opt = 1;
setsockopt(sockfd, SOL_SOCKET, SO_BROADCAST, &opt, sizeof(opt));
```

**优缺点：**

- 优点：配置简单，局域网内所有主机可同时接收
- 缺点：所有主机都要处理数据包，占用带宽；容易引发广播风暴；仅支持局域网，无法跨网段

#### 完整代码示例

**广播发送端完整代码：**

```c
#include <stdio.h>
#include <arpa/inet.h>
#include <sys/socket.h>
#include <string.h>
#include <unistd.h>
#include <stdlib.h>

int main()
{
    /************************ 1. 创建UDP套接字 ************************/
    // SOCK_DGRAM 表示数据报套接字，对应UDP协议
    int sockfd = socket(AF_INET, SOCK_DGRAM, 0);
    if (sockfd == -1)
    {
        perror("创建UDP套接字失败");
        return -1;
    }

    /************************ 2. 开启广播权限（核心必写） ************************/
    // 操作系统默认禁止发送广播包，必须通过setsockopt手动开启
    int broadcast_enable = 1; // 1表示开启，0表示关闭
    int ret = setsockopt(sockfd, SOL_SOCKET, SO_BROADCAST, 
                         &broadcast_enable, sizeof(broadcast_enable));
    if (ret == -1)
    {
        perror("开启广播权限失败");
        close(sockfd);
        return -1;
    }

    /************************ 3. 配置广播目标地址 ************************/
    struct sockaddr_in broadcast_addr = {0};
    broadcast_addr.sin_family = AF_INET;                // IPv4协议族
    broadcast_addr.sin_port = htons(8888);              // 广播目标端口，接收端必须监听此端口
    broadcast_addr.sin_addr.s_addr = inet_addr("255.255.255.255"); // 受限广播地址

    char buf[128] = {0};
    socklen_t addr_len = sizeof(broadcast_addr);

    printf("广播发送端启动，输入内容后回车发送（输入quit退出）\n");

    /************************ 4. 循环发送广播数据 ************************/
    while (1)
    {
        memset(buf, 0, sizeof(buf));
        // 从键盘读取一行输入
        fgets(buf, sizeof(buf), stdin);

        // 手动剔除fgets带入的换行符\n
        int i = 0;
        while (buf[i] != '\0')
        {
            if (buf[i] == '\n')
            {
                buf[i] = '\0';
                break;
            }
            i++;
        }

        // 输入quit则退出程序
        if (strcmp(buf, "quit") == 0)
        {
            printf("发送端退出\n");
            break;
        }

        // 发送广播数据包：同网段所有监听8888端口的主机都能收到
        ssize_t send_len = sendto(sockfd, buf, strlen(buf), 0,
                                  (struct sockaddr*)&broadcast_addr, addr_len);
        if (send_len == -1)
        {
            perror("广播发送失败");
            break;
        }
    }

    /************************ 5. 关闭套接字释放资源 ************************/
    close(sockfd);
    return 0;
}
```

```c
            break;
```

**广播编程注意事项**

1. 权限问题：发送端必须开启 `SO_BROADCAST`，否则 `sendto` 会报 `Permission denied` 错误
2. 端口匹配：接收端绑定的端口，必须和发送端目标端口完全一致才能收到数据
3. 跨网段限制：`255.255.255.255` 无法穿过路由器，只能在当前局域网内传播
4. 性能影响：广播会强制网段内所有主机处理数据包，大量广播会引发广播风暴，占用全网带宽

### 组播 / 多播（Multicast）

**定义：**

一对指定多通信，数据包发送到一个组播组，只有加入该组的主机才能收到数据，是广播的优化版本。

组播地址（D 类 IP 地址）

地址范围：`224.0.0.0 ~ 239.255.255.255` 按用途细分：


<table v-pre><tbody><tr><td>地址范围</td><td>用途说明</td></tr><tr><td>224.0.0.0 ~ 224.0.0.255</td><td>预留永久组播地址，供底层网络协议使用例：224.0.0.1 = 本网段所有主机，224.0.0.2 = 本网段所有路由器</td></tr><tr><td>224.0.1.0 ~ 238.255.255.255</td><td>全球可用的公用组播地址</td></tr><tr><td>239.0.0.0 ~ 239.255.255.255</td><td>私有组播地址，局域网内部开发使用，推荐优先选择</td></tr></tbody></table>


**编程要求**

- 发送端：无需特殊配置，直接 sendto 到组播地址 + 对应端口即可
- 接收端：必须调用`setsockopt`加入指定的组播组，否则收不到组播数据

**加入组播组代码示例：**

```c
#include <netinet/in.h>

struct ip_mreq mreq;
mreq.imr_multiaddr.s_addr = inet_addr("239.255.0.1"); // 目标组播地址
mreq.imr_interface.s_addr = htonl(INADDR_ANY);        // 绑定本地网卡

setsockopt(sockfd, IPPROTO_IP, IP_ADD_MEMBERSHIP, &mreq, sizeof(mreq));
```

**优缺点：**

- 优点：比广播高效，仅发送给需要的主机；支持跨路由器转发，可实现广域网多播
- 缺点：配置相对复杂，需要网络设备支持组播协议（IGMP）

#### 完整代码示例

**组播发送端完整代码（带逐行注释）：**

```c

#include <arpa/inet.h>
#include <sys/socket.h>
#include <string.h>
#include <unistd.h>

int main()
{

    if (sockfd == -1)

    {

        fgets(buf, sizeof(buf), stdin);

        // 手动去除换行符
        int i = 0;
        while (buf[i] != '\0')
        {
            if (buf[i] == '\n')
            {
                buf[i] = '\0';
                break;
            }
            i++;
        }

        if (strcmp(buf, "quit") == 0)
        {
            printf("发送端退出\n");
            break;
        }

        // 向组播地址发送数据，所有加入该组的主机都能收到
        ssize_t send_len = sendto(sockfd, buf, strlen(buf), 0,
                                  (struct sockaddr*)&multicast_addr, addr_len);
        if (send_len == -1)
        {
            perror("组播发送失败");
            break;
        }
    }

    close(sockfd);
    return 0;
}
```

```c
#include <arpa/inet.h>
#include <sys/socket.h>
#include <string.h>
#include <unistd.h>
#include <netinet/in.h>

{

    if (sockfd == -1)

        perror("创建UDP套接字失败");
        return -1;

    if (ret == -1)

        close(sockfd);
        return -1;
    }

    char buf[128] = {0};
    struct sockaddr_in sender_addr;
    socklen_t addr_len = sizeof(sender_addr);

    printf("组播接收端启动，已加入组239.255.0.1，监听7777端口...\n");

    /************************ 4. 循环接收组播数据 ************************/
    while (1)
    {
        memset(buf, 0, sizeof(buf));
        ssize_t recv_len = recvfrom(sockfd, buf, sizeof(buf), 0,
                                    (struct sockaddr*)&sender_addr, &addr_len);
        if (recv_len == -1)
        {
            perror("接收组播数据失败");
            break;
        }

        printf("收到来自[%s:%d]的组播：%s\n",
               inet_ntoa(sender_addr.sin_addr),
               ntohs(sender_addr.sin_port),
               buf);
    }

    // 离开组播组（程序退出前可选调用，进程结束系统会自动清理）
    setsockopt(sockfd, IPPROTO_IP, IP_DROP_MEMBERSHIP, &mreq, sizeof(mreq));
    close(sockfd);
    return 0;
}
```

**组播编程注意事项**

1. 接收端必须加组：不调用 `IP_ADD_MEMBERSHIP` 加入组播组，即使端口正确也收不到数据
2. TTL 默认值：组播数据包默认 TTL=1，只能在当前子网传播，跨网段需手动调大
3. 地址规范：普通业务不要使用 `224.0.0.x` 段，该段为系统协议预留，优先用 `239` 私有段
4. 多组支持：一个套接字可以多次调用 `IP_ADD_MEMBERSHIP`，同时加入多个组播组

## 五、UDP 编程核心注意事项（补充重点）

### 面向数据报：无粘包，但会丢包截断

- UDP 一次 `sendto` 对应一次 `recvfrom`，有明确的数据边界，不存在 TCP 的粘包问题
- 如果接收缓冲区大小 < 数据报实际大小，多余的数据会被直接丢弃，不会像 TCP 那样分多次读取
- 多个数据报到达时，按顺序存放在接收缓冲区，recvfrom 一次取一个完整数据报

### 不可靠性的具体表现

- 丢包不重传：数据报在网络中丢失，发送端和接收端都不会收到通知
- 顺序不保证：后发送的数据可能先到达接收端
- 重复不处理：同一个数据报可能被网络重复投递
- 无流量控制：接收缓冲区满了之后，新的数据报直接丢弃，不会通知发送端减速

### UDP 也可以调用 connect ()

UDP 的 `connect()` 不会建立真实连接（没有三次握手），只是让内核记录对端的 IP 和端口：

- 调用 connect 后，可以直接用 `send()`、`recv()` 代替 `sendto()`、`recvfrom()`，不用每次填写地址
- 调用 connect 后，如果目标端口不可达，ICMP 错误会返回给应用层，recv 会返回错误
- 可以多次调用 connect，修改绑定的对端地址

### 接收缓冲区满的处理

UDP 接收缓冲区有大小限制（默认一般为几十 KB），如果短时间大量数据到达，缓冲区溢出后新数据包直接丢弃。 优化方式：通过 `SO_RCVBUF` 选项调大接收缓冲区。

### 核心编程步骤对比表

### 构建流程差异拆解

#### （1）相同的基础流程

三者底层都是 UDP 协议，基础框架完全一致：

1. 创建 `SOCK_DGRAM` 类型的 UDP 套接字
2. 接收端绑定固定端口
3. 用 `sendto` 发送数据、`recvfrom` 接收数据
4. 关闭套接字释放资源

#### （2）核心差异点

- 单播：逻辑最简单，只需要明确知道接收方的 IP 和端口，点对点传输，是 UDP 的默认模式。
- 广播：发送端多一步开启广播权限，目标地址换成广播地址；接收端无需额外配置，端口匹配就能收到。
- 组播：接收端多一步加入组播组的操作，目标地址换成组播地址；发送端无需加组，直接向组地址发送即可。

## 一、阻塞 IO & 非阻塞 IO（函数完整参数）

### 1. 阻塞 IO：recv

原型

```c
ssize_t recv(int sockfd, void *buf, size_t len, int flags);
```

- `sockfd`：TCP 连接套接字 fd
- `buf`：接收缓冲区
- `len`：缓冲区最大读取字节
- `flags`：0 代表默认阻塞读取

调用示例

```c
char buf[1024] = {0};
ssize_t ret = recv(conn_fd, buf, sizeof(buf), 0);
```

### 2. 非阻塞 IO：fcntl

原型

```c
int fcntl(int fd, int cmd, ... /* arg */);
```

- `fd`：待设置的套接字
- `cmd=F_GETFL`：获取原有文件标志
- `cmd=F_SETFL`：设置文件标志
- 可变参数`arg`：叠加`O_NONBLOCK`开启非阻塞

完整代码

```c
int flag = fcntl(sockfd, F_GETFL, 0);
fcntl(sockfd, F_SETFL, flag | O_NONBLOCK);
```

#### 非阻塞 recv 循环逻辑

```c
while(1)
{
    ssize_t n = recv(sockfd, buf, sizeof(buf), 0);
    if(n > 0) { /* 处理数据 */ }
    else if(n == 0) { break; } // 对端关闭
    else if(errno != EAGAIN) { perror("错误"); break; }
    usleep(1000); // 降低CPU占用
}
```

## 二、IO 多路复用（select /poll/epoll 完整参数 + 详解）

### 2.1 select（基础多路复用）

头文件

```c
#include <sys/select.h>
#include <sys/time.h>
```

完整函数原型

```c
int select(
    int nfds,                // 1. 最大fd + 1
    fd_set *readfds,         // 2. 读事件集合，NULL不监听
    fd_set *writefds,        // 3. 写事件集合，NULL不监听
    fd_set *exceptfds,       // 4. 异常带外数据，NULL不监听
    struct timeval *timeout  // 5. 超时结构体，NULL永久阻塞
);
```

配套结构体

```cpp
struct timeval {
    time_t tv_sec;    // 秒
    suseconds_t tv_usec; // 微秒
};
```

fd_set 操作宏（完整参数）

```c
FD_ZERO(&set);                    // 清空集合
FD_SET(fd, &set);                 // 添加fd
FD_CLR(fd, &set);                 // 删除fd
FD_ISSET(fd, &set);               // 判断是否就绪
```

缺点

1. 每次调用重置 fd_set，循环需重复添加所有 fd
2. 最大 fd 限制`FD_SETSIZE=1024`
3. 内核线性遍历所有 fd，海量连接性能差

### 2.2 poll（改良版多路复用）

头文件

```c
#include <poll.h>
```

pollfd 结构体

```c
struct pollfd {
    int fd;         // 监视的文件描述符
    short events;   // 输入：需要监听的事件
    short revents;  // 输出：内核返回就绪事件
};
```

函数完整原型

```c
int poll(
    struct pollfd *fds,  // 1. pollfd数组首地址
    nfds_t nfds,         // 2. 数组有效元素个数
    int timeout          // 3. 等待毫秒，-1永久阻塞
);
```

常用事件


<table v-pre><tbody><tr><td>事件</td><td>作用</td></tr><tr><td>POLLIN</td><td>读就绪（有数据 / 新连接）</td></tr><tr><td>POLLOUT</td><td>写就绪（发送缓冲区有空位）</td></tr><tr><td>POLLHUP</td><td>连接挂断，客户端关闭</td></tr><tr><td>POLLERR</td><td>套接字发生错误</td></tr></tbody></table>


优点：

无 1024 上限，无需每次重置集合；缺点：内核仍线性遍历全部 fd。

### 2.3 epoll（Linux 高性能多路复用，重点补充）

epoll 是 Linux 专属，解决 select/poll 线性遍历的性能缺陷，适合十万、百万级高并发连接，Nginx、Redis 底层均使用 epoll。

#### 三大核心 API：epoll_create、epoll_ctl、epoll_wait

### 1）epoll_create 创建 epoll 实例

头文件

```c
#include <sys/epoll.h>
```

原型

```c
int epoll_create(int size);
```

- 参数`size`：早期内核用于提示监听 fd 数量，现代内核已废弃，填任意正数（如 1024）
- 返回值：epoll 文件描述符（epfd），失败返回 - 1

使用示例

```c
int epfd = epoll_create(1024);
if(epfd == -1) { perror("epoll_create"); return -1; }
```

### 2）epoll_ctl 注册 / 修改 / 删除 fd 事件（核心）

原型

```c
int epoll_ctl(
    int epfd,               // 1. epoll实例fd
    int op,                 // 2. 操作类型：EPOLL_ADD/EPOLL_MOD/EPOLL_DEL
    int fd,                 // 3. 要操作的目标fd
    struct epoll_event *event // 4. 事件结构体，存储fd+监听事件
);
```

op 操作类型

1. `EPOLL_CTL_ADD`：新增 fd 到 epoll 监听
2. `EPOLL_CTL_MOD`：修改已存在 fd 的监听事件
3. `EPOLL_CTL_DEL`：从 epoll 中移除 fd

epoll_event 结构体：

```c
struct epoll_event {
    uint32_t events;    // 需要监听的事件
    epoll_data_t data;  // 存储fd/自定义数据
};
// epoll_data_t联合体
typedef union epoll_data {
    void *ptr;
    int fd;         // 常用：保存文件描述符
    uint32_t u32;
    uint64_t u64;
} epoll_data_t;
```

常用监听事件


<table v-pre><tbody><tr><td>事件</td><td>含义</td></tr><tr><td>EPOLLIN</td><td>读就绪：缓冲区有数据 /listen fd 有新连接</td></tr><tr><td>EPOLLOUT</td><td>写就绪：发送缓冲区空闲</td></tr><tr><td>EPOLLERR</td><td>套接字错误，自动触发</td></tr><tr><td>EPOLLHUP</td><td>对端关闭连接</td></tr><tr><td>EPOLLET</td><td>边缘触发 ET（默认水平 LT）</td></tr></tbody></table>


完整注册示例（把监听 fd 加入 epoll）

```c
struct epoll_event ev;
ev.data.fd = listen_fd;
ev.events = EPOLLIN; // 监听读事件
epoll_ctl(epfd, EPOLL_CTL_ADD, listen_fd, &ev);
```

### 3）epoll_wait 阻塞等待就绪事件

原型

```c
int epoll_wait(
    int epfd,                // 1. epoll实例fd
    struct epoll_event *events, // 2. 输出数组，存放就绪事件
    int maxevents,           // 3. 数组最大容量
    int timeout              // 4. 超时毫秒，-1永久阻塞
);
```

返回值

> - 0：就绪 fd 个数

- 0：超时无事件
- -1：调用失败

使用示例

```c
struct epoll_event events[1024];
// 最多一次接收1024个就绪事件，永久阻塞
int n = epoll_wait(epfd, events, 1024, -1);
for(int i = 0; i < n; i++)
{
    int fd = events[i].data.fd;
    if(events[i].events & EPOLLIN)
    {
        // fd可读，处理accept/recv
    }
}
```

epoll 两种触发模式：

1. LT 水平触发（默认） 只要缓冲区有数据，每次 epoll_wait 都会持续通知； 优点：代码简单；缺点：若读不完数据会反复触发，建议搭配非阻塞 fd。
2. ET 边缘触发 EPOLLET 仅数据第一次到达时通知一次，必须一次性读完缓冲区所有数据； 性能更高，强制 fd 设置`O_NONBLOCK`，循环 recv 直到 EAGAIN。

epoll 核心优势：

1. 内核采用红黑树存储监听 fd，就绪链表仅返回活跃 fd，无需遍历全部连接
2. 无 1024 文件描述符上限，支持百万并发
3. 用户态与内核态共享事件内存，拷贝开销极小

### 2.4 select/poll/epoll 对比表


<table v-pre><tbody><tr><td>特性</td><td>select</td><td>poll</td><td>epoll</td></tr><tr><td>fd 上限</td><td>默认 1024</td><td>无上限</td><td>无上限</td></tr><tr><td>内核遍历方式</td><td>遍历 0~maxfd 全部 fd</td><td>遍历整个 pollfd 数组</td><td>仅遍历就绪链表</td></tr><tr><td>性能</td><td>千级连接尚可，万级卡顿</td><td>万级连接性能下滑</td><td>十万 / 百万高并发最优</td></tr><tr><td>内存拷贝</td><td>每次调用拷贝完整 fd 集合</td><td>每次拷贝数组</td><td>仅拷贝就绪事件</td></tr><tr><td>触发模式</td><td>仅水平触发 LT</td><td>仅水平触发 LT</td><td>LT/ET 边缘触发可选</td></tr><tr><td>跨平台</td><td>全平台通用</td><td>全平台通用</td><td>Linux 专属</td></tr></tbody></table>


IO 多路复用通用执行流程：

1. 应用程序：把需要监听的 fd + 事件注册到 select/poll；
2. 调用多路复用函数，进程阻塞进入内核；
3. 内核轮询所有 fd，等待任意 fd 触发读 / 写 / 异常事件；
4. 有事件触发，内核返回就绪 fd 数量；
5. 用户层遍历所有 fd，判断哪个 fd 就绪；
6. 对就绪 fd 执行`accept/recv/send`IO 操作；
7. 循环回到第二步继续监听。

补充：非阻塞搭配多路复用：

多路复用检测到 fd 就绪后，建议将 fd 设置为非阻塞； 若缓冲区数据一次读不完，循环 recv 直到`EAGAIN`，避免残留数据（水平触发特性）。

## 三、服务器两大模型

### 循环服务器（单进程串行处理）

**定义：**

同一时刻只能处理一个客户端请求，处理完当前客户端，才会接收下一个客户端。

**TCP 循环服务器特点：**

存在两处阻塞：`accept()`、`recv()`

- 客户端 A 连接后，阻塞在`recv`等待 A 的数据；
- 此时新客户端发起连接，`accept`无法执行，新连接排队等待；
- A 断开后，才会重新执行 accept 接待下一个客户端。

**UDP 循环服务器特点：**

仅一处阻塞：`recvfrom()` UDP 无连接，每收到一个数据包立刻处理，天然能响应多个客户端发来的数据，属于伪并发（单线程串行处理数据包）。

**优缺点：**

✅ 优点：代码最简单，无进程 / 线程资源开销；

❌ 缺点：无法同时服务多个客户端，长连接场景会阻塞全部业务，无生产使用价值。

### 并发服务器（同时处理多个客户端）

同一时刻可以同时响应、处理多个客户端连接，分为 3 种主流实现方案：

1. 多线程并发服务器
2. 多进程 (fork) 并发服务器
3. IO 多路复用单进程并发服务器

## 四、三种并发服务器详细实现

### 方案 1：多线程并发 TCP 服务器

**实现原理：**

- 主线程：只负责`accept()`接收新客户端连接；每拿到一个新通信 fd，创建子线程；
- 子线程：独立处理单个客户端的`recv/send`读写，线程结束自动关闭通信 fd；
- 线程间资源共享：监听 fd、全局变量主线程子线程均可访问。

**完整流程：**

1. 主线程创建 socket → bind → listen；
2. while (1) 循环调用 accept 阻塞等待新连接；
3. accept 返回 connect_fd，调用`pthread_create`创建子线程；
4. 子线程函数：循环 recv/send，客户端断开后 close (connect_fd)，线程退出；
5. 主线程继续循环等待下一个新连接。

**优缺点：**

✅ 优点：创建线程开销远小于进程；线程共享地址空间，传参简单； ❌ 缺点：上万连接会创建大量线程，占用大量栈内存；线程同步加锁复杂；线程崩溃可能影响整个进程。

### 方案 2：多进程 fork 并发服务器

**实现原理：**

主进程负责监听、接收新连接；`fork()`创建子进程单独处理客户端，父子进程地址空间完全隔离。

**完整流程：**

1. 主进程创建 listen_fd → bind → listen；
2. while (1) accept 阻塞等待新连接；
3. 收到新连接调用 fork ()； 

   - 父进程：关闭本次 connect_fd，回到循环继续 accept；
   - 子进程：关闭继承的 listen_fd（无需监听），循环 recv/send 处理客户端；客户端断开后 close (connect_fd)，调用 exit () 退出子进程。

**优化方案：预 fork 模型（Apache 服务器采用）：**

程序启动时预先创建一批子进程，所有子进程共享监听 socket，新连接到达时由空闲子进程直接 accept，减少运行时 fork 开销，搭配`SO_REUSEPORT`实现负载均衡。

**优缺点：**

✅ 优点：进程完全隔离，单个客户端逻辑崩溃不会影响其他客户端和主进程；无线程同步锁问题； ❌ 缺点：fork 创建进程开销大；进程间通信复杂（管道 / 共享内存）；大量连接会占用大量内存。

### 方案 3：IO 多路复用单进程并发服务器（高并发首选）事件驱动

**实现原理：**

仅一个主线程 / 进程，通过 select/poll/epoll 同时监听「监听 socket + 所有客户端通信 socket」； 哪个 fd 就绪就处理哪个，无需创建进程 / 线程，资源占用极低。

**标准流程（select 版）：**

1. 创建 listen_fd、bind、listen；
2. 初始化 fd_set 集合，把 listen_fd 加入监听集合；
3. while (1) 循环： 

   1. 调用 select 阻塞等待任意 fd 就绪；
   2. 遍历所有 fd，判断是否就绪： 
   
      - 如果是 listen_fd 就绪：调用 accept 获取新 connect_fd，将新 fd 加入 fd_set；
      - 如果是普通客户端 fd 就绪：调用 recv 读取数据，处理业务，若客户端断开则 close (fd) 并从集合移除；

**优缺点：**

✅ 优点：单进程，无进程 / 线程切换开销；支持海量并发连接；内存占用极低； ❌ 缺点：所有业务串行执行，单个客户端耗时操作会阻塞全部连接；复杂业务需要搭配多线程 / 多进程。

### 关键踩坑补充

1. select 每次循环会清空 fd_set，必须每次循环重新`FD_SET`所有 fd；
2. fork 子进程必须关闭 listen_fd，否则监听 fd 引用计数不会归零，程序无法正常退出；
3. 多路复用搭配非阻塞 fd，防止一次 recv 没读完数据，产生粘包 / 数据残留；
4. 多线程需要分离线程或回收线程资源，避免产生僵尸线程；多进程需要`waitpid`回收僵尸子进程；
5. UDP 天然是 “单进程多路复用”，不需要 accept，只需要 recvfrom 循环处理数据包。

### 适用场景选型建议

1. 课堂练习、简单工具：循环阻塞服务器；
2. 千级以内并发、开发简单：多线程服务器；
3. 追求隔离稳定、不怕资源开销：多进程 fork；
4. 高并发、上万连接、高性能网关：IO 多路复用 epoll。

# TCP/IP协议分析

## 一、常见协议头完整解析（IP 首部 + TCP 首部，字段深度补充）

### IPv4 IP 首部（固定最小 20 字节，带选项最大 60 字节，4 字节对齐）

逐字段完整扩充说明：

1. 版本号 (4bit) 取值 4=IPv4，6=IPv6；网卡、路由器通过此字段区分 IP 协议版本，不匹配直接丢弃数据包。
2. 首部长度 IHL (4bit) 单位是 4 字节，最小值 5（5×4=20 字节，无自定义选项），最大值 15；若数值不是 5，代表头部携带 IP 选项，用于路由记录、时间戳等扩展功能。
3. 服务类型 TOS (8bit) 分为优先级 3bit、延迟 / 吞吐量 / 可靠性 / 开销 4bit、保留 1bit；现代网络拓展为 DSCP 差分服务，用于 QoS 流量调度，音视频业务优先降低延迟，文件传输优先保证吞吐量。
4. 总长度 (16bit) 整个 IP 数据包总字节（IP 头部 + TCP/UDP 头部 + 应用载荷），最大值 65535；以太网 MTU=1500，超过会触发 IP 分片。
5. 标识 ID (16bit) 同一大报文拆分出的所有分片共享同一个 ID，接收端依靠 ID 识别属于同一原始报文，完成分片重组；每发送一个完整 IP 报文，内核自动自增 ID。
6. 标志位 (3bit) bit0：保留恒 0；bit1 (DF)：DF=1 禁止分片，数据包超 MTU 时直接丢弃并返回 ICMP 不可达；bit2 (MF)：MF=1 代表当前分片后还有后续分片，最后一片 MF=0。
7. 片偏移 (13bit) 标识当前分片数据在原始完整报文中的偏移位置，单位 8 字节；接收端根据偏移按顺序拼接分片。
8. TTL 生存时间 (8bit) 数据包每经过一台路由器，TTL 数值减 1；TTL 变为 0 时路由器直接丢弃报文，并向发送方发送 ICMP 超时报文；Linux 默认 TTL=64，Windows=128，路由器 = 255。`traceroute`工具依靠 TTL 递减原理追踪路由节点。
9. 上层协议号 (8bit) 6=TCP，17=UDP，1=ICMP，2=IGMP；内核通过此字段把 IP 数据交给对应传输层协议处理。
10. 首部校验和 (16bit) 仅校验 IP 头部所有二进制，不含 TCP/UDP 数据；路由器转发时每跳重新计算校验和，头部出错直接丢弃报文，不重传。
11. 源 IP (32bit)、目的 IP (32bit) 32 位二进制 IPv4 地址，标记发送 / 接收主机；组播、广播报文目的地址为特殊网段。
12. 可变选项 + 填充位 可选扩展功能，最多 40 字节；若选项长度无法让 IP 头总长度为 4 的整数倍，末尾填充 0 补齐对齐。

### TCP 首部（最小 20 字节，带选项最大 60 字节，4 字节对齐）

逐字段扩充说明：

1. 源端口 16bit / 目的端口 16bit 端口范围 0\~65535；0\~1023 知名系统端口，1024\~49151 注册端口，49152\~65535 客户端临时端口；操作系统依靠端口区分同一主机上多个网络进程。
2. 序列号 Seq (32bit) TCP 是字节流，每个字节分配唯一序号；连接建立时随机生成初始序列号 ISN，防止旧连接残留报文干扰新连接；发送数据时，Seq 代表本段报文第一个字节的编号，用于乱序重排、丢包重传。
3. 确认号 Ack (32bit) 只有 ACK 标志置 1 时生效；数值 = 对方上一条 Seq + 对方已成功接收的字节总数，代表期望接收对方下一个字节的序号；双向通信双方各自维护独立的 Seq/Ack 序列。
4. 数据偏移 (4bit) TCP 头部长度，单位 4 字节，最小 5（20 字节基础头部）；存在 MSS、窗口扩大、时间戳等选项时数值变大。
5. 保留位 (6bit) 协议预留，默认全部置 0，新版本 TCP 扩展标志会复用该区域。
6. 6 位核心标志位 URG/ACK/PSH/RST/SYN/FIN

   - URG：紧急指针有效，紧急数据优先跳过缓冲区直接交给应用层，多用于 Ctrl+C 中断指令；
   - ACK：确认标志，除三次握手第一条 SYN 包外，所有 TCP 报文必须置 1；
   - PSH：推送标志，告知接收内核不要缓存数据，立刻向上交付应用程序；
   - RST：连接重置，报文异常、端口未监听、半连接卡死时强制断开链路，无四次挥手；
   - SYN：同步标志，三次握手建立连接专用，携带 ISN 初始序列号；
   - FIN：结束标志，四次挥手释放连接，代表本方不再发送数据。
7. 滑动窗口 Window (16bit) 流量控制核心，告知发送端本机接收缓冲区剩余容量；发送端发送数据总量不能超过窗口值，避免接收缓冲区溢出丢包；配合窗口扩大选项可突破 65535 上限。
8. TCP 校验和 (16bit) 校验范围：TCP 头部 + TCP 业务数据 + 12 字节 IP 伪首部（源 IP、目的 IP、协议、TCP 长度）；可同时校验 IP 层和传输层数据完整性，出错直接丢弃报文。
9. 紧急指针 Urgent Pointer (16bit) URG 标志生效时使用，偏移量标记紧急数据最后一个字节位置，区分普通数据与紧急数据。
10. 可变选项 + 填充位 最常用选项：MSS 最大报文段长度、Window Scale 窗口扩大、Timestamp 时间戳（用于 RTT 往返时间计算、防序号绕回）、SACK 选择性确认（丢包时仅重传丢失分片，无需重传全部数据）；末尾填充 0 保证头部 4 字节对齐。

### TCP/IP 四层封装完整流程（补充每层硬件、内核行为）

发送端从上到下逐层封装，接收端从下到上逐层解封装：

1. 应用层：业务自定义数据（HTTP、Redis、自定义私有协议），可自行添加消息头部；调用`send()`/`write()`将数据交给内核传输层。
2. 传输层 TCP：内核添加 TCP 首部，生成 TCP 报文段；根据 MSS 拆分大数据，缓存小包等待合并（Nagle 算法）。
3. 网络层 IP：内核添加 IP 首部，封装为 IP 数据报；报文超过 MTU 时执行 IP 分片，填充 TTL、校验和、源 / 目的 IP。
4. 数据链路层以太网：添加 14 字节以太网头部（源 MAC、目标 MAC、上层协议类型 0x0800 代表 IP）、4 字节 CRC 校验尾部，组成完整以太网帧；网卡将二进制比特流发送到物理网线。补充关键参数 MTU&MSS 以太网标准 MTU=1500 字节（单帧最大承载字节）；IP 头 20 字节 + TCP 头 20 字节，标准 MSS=1460 字节；单次发送载荷超过 1460 字节会触发 TCP 分段，进而产生拆包现象。

## 三、TCP 粘包、拆包完整原理、诱因、根治方案（大幅扩充）

### 三种报文现象详细定义

- 正常包：应用层一次`send`发送一条完整消息，内核一次 TCP 报文传输，接收端单次`recv`读取完整数据，消息边界清晰；
- 粘包：多次连续`send`的多条独立消息，被 TCP 内核缓冲区合并为单个 TCP 报文，单次`recv`读出多条未分割的业务数据；
- 拆包：单次`send`发送超大业务数据，超出 MSS 限制，TCP 自动拆分多个分段发送，接收端需要多次调用`recv`才能拼接出一条完整消息。

### 四大核心成因（底层机制扩充）

1. TCP 核心属性：面向无边界字节流（根本原因） TCP 协议只负责传输连续二进制字节序列，内核不会记录应用层`send`调用的消息边界；内核收发缓冲区仅存储字节，无消息分割标记，这是 UDP 不存在粘拆包、TCP 独有该问题的本质区别。UDP 是面向数据报，一次 sendto 对应一个独立报文，天然保留消息边界。
2. 发送端缓冲区 + Nagle 算法自动合并小包 Nagle 算法默认开启，优化网络小包带宽损耗：若当前连接存在未收到 ACK 确认的报文，内核缓存后续小块数据，等待 200ms 延迟或 ACK 到达后合并发送；高频短指令场景会大量触发粘包；可通过`setsockopt(fd, IPPROTO_TCP, TCP_NODELAY, &opt, sizeof(opt))`关闭算法，消除小包合并，但会增加网络小包数量。
3. 发送数据长度超过 MSS 触发 TCP 分段（拆包主要来源） 单次发送业务数据大于 1460 字节标准 MSS，TCP 传输层自动拆分多个分段，分批交给 IP 层发送；接收端内核分次推送数据到应用缓冲区，单次 recv 只能读到部分数据，形成拆包。
4. 接收端读取速度慢，内核缓冲区堆积多条报文 应用层业务处理耗时、循环 recv 读取间隔过长，多条 TCP 报文滞留在内核接收缓冲区；下一次 recv 调用会一次性读取缓冲区全部字节，多条消息拼接在一起，产生粘包。补充额外诱因：网络延迟、路由分片、操作系统内核缓冲区大小限制，会加剧粘拆包现象。

### 四类工业级解决方案（优缺点、适用场景、代码逻辑扩充）

#### 方案 1：固定长度报文

约定每条消息占用固定字节，数据不足末尾填充`\0`占位；接收端每次精准读取固定长度字节，读到即完整单条消息。

- 优点：解析逻辑最简单，无复杂编解码；
- 缺点：变长数据会浪费带宽，超大消息无法适配；
- 适用：嵌入式硬件简单指令、短固定消息设备通信。

#### 方案 2：唯一分隔符分割（文本协议主流）

每条完整消息末尾添加全局唯一分隔符，如`\n`、`\r\n`；接收端循环读取字节流，缓冲区扫描匹配分隔符，切割出独立消息，剩余未完整数据缓存下次继续解析。

- 优点：天然支持变长文本数据；
- 缺点：二进制数据正文需要转义分隔符，增加解析开销；分隔符冲突会导致报文解析错乱；
- 适用：HTTP、日志传输、聊天文本、Shell 交互。

#### 方案 3：长度前缀法（线上项目通用最优方案）

标准报文格式：4 字节网络序大端长度头 + 可变长业务数据体 发送逻辑：先计算业务数据字节长度，用`htonl()`转为网络序写入前 4 字节，再拼接业务数据发送； 接收逻辑：先读取 4 字节长度头，`ntohl()`转换为主机序获取数据长度，再精准读取对应长度字节，直接得到完整消息，无粘拆包干扰。

- 优点：支持任意二进制数据，无需转义，解析效率高，适配所有业务场景；
- 缺点：需要简单封装编解码函数；
- 适用：游戏服务器、RPC 框架、数据库私有协议、高并发长连接服务。

#### 方案 4：短连接一问一答模式

单次业务交互新建 TCP 连接，收发完成立刻`close()`关闭套接字；每条连接仅传输一条业务消息，内核缓冲区无多条数据堆积，天然规避粘包。

- 优点：无需处理消息边界，逻辑极简；
- 缺点：频繁创建销毁连接，三次握手、四次挥手带来巨大性能损耗，并发量极低场景可用；
- 适用：低频查询工具、单次请求脚本。

### 补充辅助优化（仅缓解，无法根治粘拆包）

1. 开启`TCP_NODELAY`关闭 Nagle 算法，取消小包合并，减少粘包概率，适合实时游戏、控制指令；
2. 调大内核`SO_RCVBUF`/`SO_SNDBUF`收发缓冲区，减少缓冲区溢出分片；
3. 多路复用搭配非阻塞 IO，快速读取缓冲区全部数据，避免数据堆积； ⚠️ 重要提醒：上述优化只能降低粘包出现概率，无法彻底解决，生产环境必须搭配长度前缀 / 分隔符 / 定长协议做消息边界分割。

# TFTP协议

## 一、TFTP 基础整体介绍

TFTP 全称简单文件传输协议（Trivial File Transfer Protocol），基于 UDP 传输层实现，默认服务端口 69。

### 核心特性补充

1. 无连接、无认证、无加密，协议极简，代码实现难度极低；
2. 传输单位固定 512 字节数据块，采用停等 ARQ 机制（每发一块等待 ACK 确认，超时重传）；
3. 仅支持文件上传、下载，不支持目录查看、删除、权限管理等复杂操作；
4. 无用户名密码校验，适合嵌入式设备、路由器、BIOS 无盘系统固件刷机场景；
5. 缺点：不可靠、传输速度慢、无安全机制，公网禁止直接使用。

### 底层依赖

全程使用`sendto/recvfrom`收发数据，UDP 天然自带消息边界，不存在粘包拆包问题。

## 二、TFTP 5 种报文格式完整拆解（全部字段补充说明）

所有报文前 2 字节统一为操作码（大端网络字节序），区分报文类型。

### RRQ 读请求包（操作码 = 1，客户端→服务器）

报文结构：2 字节操作码 + 文件名字符串 + 0 分隔符 + 传输模式字符串 + 0 分隔符

- 文件名：需要下载的文件名称，ASCII 字符串，不能包含路径；
- 模式：两种标准模式 

  1. `octet`：二进制模式（固件、程序、压缩包，项目通用）；
  2. `netascii`：文本模式，自动转换换行符，极少使用；
- 末尾两个`\0`字符串结束标记，用于分割字段。 作用：客户端发起文件下载请求，服务器收到后分配临时端口，开始分块下发文件。

### WRQ 写请求包（操作码 = 2，客户端→服务器）

报文结构与 RRQ 完全一致，仅操作码为 2。 作用：客户端发起文件上传请求，服务器分配临时端口，等待客户端发送文件数据块。 补充：服务器需提前开启对应目录写权限，否则直接返回 ERROR 差错包。

### DATA 数据包（操作码 = 3，数据发送方→接收方）

报文结构：2 字节操作码 + 2 字节块编号 + 最多 512 字节文件数据

1. 块编号：16 位大端无符号整数，从 1 开始自增，每一块编号唯一；
2. 数据载荷：单块最大 512 字节； 

   - 若文件末尾不足 512 字节，代表文件传输结束；
   - 恰好 512 字节则后续还有数据块； 传输规则：发送一块 DATA 后必须等待对方返回对应块号 ACK，超时未收到 ACK 则重传当前数据块。

### ACK 确认包（操作码 = 4，接收方→发送方）

报文结构：2 字节操作码 + 2 字节块编号 作用：确认收到对应编号的数据块，告知对方可以发送下一块；

- 下载场景：客户端收到 DATA 块，回复同块号 ACK；
- 上传场景：服务器收到 DATA 块，回复同块号 ACK。 特殊规则：WRQ 请求收到后，服务器直接返回块号 0 的 ACK，代表允许上传，客户端才可发送块 1 数据。

### ERROR 差错包（操作码 = 5，任意一方均可发送）

报文结构：2 字节操作码 + 2 字节差错码 + 错误描述字符串 + \0 结束符

#### 标准差错码含义补充

0：未定义错误； 1：文件不存在（RRQ 请求的文件找不到）； 2：权限不足（WRQ 无写入权限、文件只读）； 3：磁盘空间不足； 4：非法 TFTP 操作报文； 5：未知传输 ID（端口不匹配，TFTP 临时端口校验失败）； 6：文件已存在（上传同名文件不覆盖时报错）； 7：无该用户（TFTP 无登录机制，极少用到）。 收到 ERROR 报文直接终止本次文件传输流程。

## 三、TFTP 完整通信流程深度补充（结合流程图）

### 前置端口规则

1. TFTP 服务固定监听69 端口，仅接收 RRQ/WRQ 读写请求；
2. 服务器收到读写请求后，自动随机生成临时 UDP 端口，后续所有 DATA/ACK/ERROR 报文全部走临时端口，69 端口只负责新建传输任务；
3. 客户端全程使用自身固定临时端口，全程不变。

### 文件下载流程（RRQ 流程）

1. 客户端（临时端口 5678）向服务器 69 端口发送 RRQ 读请求（文件名 + octet 模式）；
2. 服务器创建传输任务，分配临时端口 1234；
3. 服务器从文件读取前 512 字节，组装块 1 DATA 包，发送至客户端 5678；
4. 客户端收到块 1 DATA，校验块号无误后，回复块 1 ACK；
5. 服务器收到 ACK，读取下 512 字节组装块 2 DATA 发送，循环往复；
6. 若最后一块数据长度＜512 字节，客户端接收后回复 ACK，双方判定传输完成，流程结束；
7. 任意报文超时无 ACK，发送方自动重传当前块，重传多次失败则报错退出。

### 文件上传流程（WRQ 流程）

1. 客户端向服务器 69 端口发送 WRQ 写请求；
2. 服务器分配临时端口 1234，回复块 0 ACK，代表允许上传；
3. 客户端收到 0 号 ACK 后，发送块 1 DATA（前 512 字节文件）；
4. 服务器写入文件，返回块 1 ACK；
5. 客户端继续发送块 2、块 3… 直到最后不足 512 字节的数据块；
6. 服务器回复最后一块 ACK，上传完成，关闭文件。

### 超时重传机制补充（TFTP 可靠性核心）

TFTP 无 TCP 确认、滑动窗口，依靠超时重传保证可靠：

1. 发送 DATA 报文后启动计时器（标准超时 5s）；
2. 超时未收到对应块 ACK，直接重传当前 DATA 块；
3. 连续多次重传无响应，判定连接断开，终止传输。

## 四、简易 TFTP 客户端 / 服务器开发完整实现步骤扩充

### 项目整体目标

基于 UDP 实现完整 TFTP 程序，支持客户端文件上传、文件下载，遵循标准 TFTP 报文格式与停等重传机制。

### 分步开发完整流程

1. 创建 UDP 套接字 使用`socket(AF_INET, SOCK_DGRAM, 0)`创建，客户端无需 bind，服务端绑定 69 端口； 服务端注意：69 是知名端口，Linux 运行需要 sudo 管理员权限。
2. 封装 RRQ/WRQ 请求报文 按协议拼接 2 字节操作码、文件名字符串、分隔符 \0、模式字符串 \0，使用`sendto`发送至服务器 69 端口。
3. 服务端处理读写请求，分配临时端口 收到 RRQ/WRQ 后，新建子进程 / 线程处理本次传输，主进程继续监听 69 端口； 子进程重新创建 UDP 套接字绑定随机临时端口，后续数据传输全部使用该 fd。
4. 文件分块收发逻辑（核心）

   - 读文件：每次读取 512 字节，组装 DATA 包发送，阻塞等待 ACK；
   - 写文件：收到 DATA 包，提取块号与数据，追加写入本地文件，回复 ACK；
   - 判断结束条件：DATA 包数据长度＜512 即传输完毕。
5. 异常处理补充 捕获文件打开失败、磁盘满、非法报文，组装 ERROR 差错包发送给对端； 实现超时重传逻辑，使用`setsockopt`或 alarm 定时器实现超时检测。
6. 传输完成收尾 客户端收到最后一块数据 ACK / 服务器收到最后一块数据 ACK，关闭文件描述符、UDP 套接字，结束本次传输。

## 五、TFTP 补充拓展知识点

1. TFTP 与 FTP 核心区别

   - TFTP：UDP、极简、无账号密码、仅上传下载、无目录操作、速度慢，用于嵌入式刷机；
   - FTP：TCP、支持登录、分控制通道 + 数据通道、支持目录管理、功能完整，通用文件传输。
2. 块编号溢出处理 块编号为 16 位（最大值 65535），超大文件传输时编号会循环归零，两端需兼容循环块号校验。
3. 安全缺陷 无身份验证，任何人只要知道 IP 和文件名即可下载 / 覆盖文件，仅允许内网隔离环境使用，公网必须防火墙屏蔽 69 端口。
4. 单文件串行传输 TFTP 单条传输通道同一时间只能处理一个文件块，无法并行传输，大文件传输效率远低于 TCP 协议。
5. 端口校验机制 服务器仅响应本次传输分配的临时端口发来的报文，其他端口发来的 DATA/ACK 全部丢弃并返回 ERROR（未知 TID 差错码 5），防止多客户端串包干扰。
