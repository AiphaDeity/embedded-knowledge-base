# Linux 多进程多线程编程 · 第一性原理
## 一、并发底层本质与核心定义
### 1. 并发的物理本质
#### 单核CPU：时间片轮转，逻辑并发
#### 多核CPU：真正物理并行
### 2. 操作系统核心职责
#### 资源隔离
#### 调度分配
### 3. 第一性核心定义
#### 进程：资源分配的最小单位
##### 本质：独立的资源容器
##### 独有：虚拟地址空间、文件描述符表、信号配置
#### 线程：CPU调度的最小单位
##### 本质：进程内部的一条执行流
##### 独有：线程栈、寄存器上下文、TLS、errno
##### 共享：进程地址空间、文件描述符、信号处理函数

## 二、多进程编程核心原理
### 1. 核心特质：地址空间隔离
#### 优势：故障隔离强，稳定性与安全性高
#### 代价：进程间无法直接通信，IPC成本高
### 2. fork() 底层本质：写时复制（COW）
#### 初始状态：父子进程映射同一份物理内存，标记只读
#### 触发时机：任意一方修改内存时，才复制对应物理页
#### 衍生结论
##### fork实际开销远小于全量内存复制
##### 父子共享文件描述符（内核态资源）
### 3. 进程生命周期本质
#### 运行态/就绪态：争夺CPU时间片
#### 阻塞态：等待IO/信号/锁，主动让出CPU
#### 僵尸进程：已退出执行，父进程未调用wait回收PCB
#### 孤儿进程：父进程先退出，被init/systemd收养
### 4. IPC 进程间通信分类逻辑
#### 内核中转类
##### 原理：用户态→内核态→用户态，两次数据拷贝
##### 代表：管道、消息队列、Socket、信号
##### 特点：安全通用，开销中等
#### 共享内存类
##### 原理：多进程虚拟地址映射同一块物理内存
##### 代表：shm共享内存、mmap内存映射
##### 特点：速度最快，无内置同步，需配合信号量
### 5. 多进程核心权衡
#### 优势：高稳定性、强故障隔离、安全性好
#### 劣势：上下文切换开销大、IPC复杂且成本高

## 三、多线程编程核心原理
### 1. 核心特质：共享地址空间的轻量级执行流
#### Linux本质：轻量级进程（LWP），每个线程对应独立task_struct
#### 线程间共享资源
##### 虚拟地址空间（全局变量、堆内存）
##### 文件描述符表
##### 信号处理函数、UID/PID
#### 每个线程独有资源
##### 线程栈（用户态栈）
##### 寄存器上下文
##### 线程ID（TID）
##### 线程局部存储（TLS）
##### errno变量
### 2. 线程安全的本质
#### 竞态条件（Race Condition）
##### 定义：多线程同时访问共享资源且存在写操作，结果依赖调度时序
##### 根源：高级语言一行代码对应多条CPU指令，切换可发生在指令间
#### 原子性
##### 定义：操作不可被打断，要么全部执行，要么完全不执行
##### 线程安全核心：保证临界区操作的原子性
### 3. 多线程核心权衡
#### 优势：上下文切换开销小、数据共享方便、通信成本极低
#### 劣势：无地址隔离，单线程崩溃导致全进程退出；线程安全问题复杂

## 四、同步互斥机制底层原理
### 1. 互斥锁（mutex）
#### 本质：内核维护的「标志位 + 等待队列」
#### 机制：原子操作抢锁，失败则进入等待队列阻塞
#### Linux实现：基于futex，无竞争时仅用户态操作，开销极低
### 2. 自旋锁（spinlock）
#### 本质：加锁失败时循环忙等，不阻塞让出CPU
#### 适用场景：锁持有时间极短的场景（内核态常用）
#### 取舍：用CPU时间换取上下文切换的开销
### 3. 条件变量（condition variable）
#### 本质：内核维护的等待队列，用于线程间事件通知
#### 强制规则：必须与互斥锁配合使用
#### 配合原因：保证「检查条件 + 进入等待队列」的原子性，避免丢失唤醒
### 4. 信号量（semaphore）
#### 本质：内核维护的「计数器 + 等待队列」
#### 典型用法
##### 计数=1：等价于互斥锁
##### 计数=N：实现生产者-消费者模型同步
### 5. 工具选型逻辑
#### 临界区互斥：首选互斥锁
#### 事件等待与通知：搭配条件变量
#### 资源计数、多线程步调同步：选信号量
#### 极短临界区内核场景：选自旋锁

## 五、死锁的第一性原理
### 1. 死锁本质：资源分配形成闭环，所有线程永久阻塞
### 2. 四个必要条件（缺一不可）
#### 互斥条件：资源同一时间只能被一个线程持有
#### 持有并等待：线程已持有资源，又在等待其他线程的资源
#### 不可剥夺：资源只能由持有者主动释放，不可被强行抢占
#### 循环等待：线程间形成首尾相接的资源等待链条
### 3. 解决思路：打破任意一个必要条件
#### 打破循环等待：统一加锁顺序（工程最常用）
#### 打破持有并等待：一次性申请全部所需资源
#### 打破不可剥夺：支持资源抢占、超时自动释放
#### 打破互斥：无锁编程（实现难度高）

## 六、学习实践与选型原则

从操作系统最底层的资源管理与 CPU 调度本质出发，拆解进程、线程的核心定义，所有 API、现象、问题都是底层机制的必然产物。你已有 Linux 基础与 IO 编程基础，我们直接从「为什么会有进程 / 线程」的根源讲起。

## 一、总纲：并发的底层本质

所有多进程、多线程技术，都围绕两个核心事实展开：

1. 物理限制：单个 CPU 核心同一时刻只能执行一条指令流，所谓「并发」是操作系统通过时间片轮转让多个执行流交替运行，制造「同时执行」的假象；多核 CPU 才能实现真正的「并行」。
2. 操作系统核心职责：资源隔离 + 调度分配。需要管理的核心资源包括：CPU 时间、内存地址空间、IO 设备（文件、网络、外设等）。

### 第一性定义

- 进程：操作系统资源分配的最小单位。本质是一个「独立资源容器」—— 拥有完整独立的虚拟地址空间、独立的文件描述符表、独立的信号处理配置，容器内至少包含一条执行线程。
- 线程：操作系统 CPU 调度的最小单位。本质是「进程内部的一条执行流」—— 它寄生在进程的资源容器中，共享进程的地址空间与 IO 资源，仅拥有自己独立的栈、寄存器上下文、线程局部存储。

> 所有后续知识都可以回归这两个定义：僵尸进程、线程安全、IPC 开销、死锁…… 无一不是「资源隔离粒度」与「调度单位」的衍生结果。

## 二、多进程编程第一性原理

### 进程的核心特质：地址空间隔离

每个进程都拥有独立的虚拟地址空间，由操作系统通过 MMU（内存管理单元）映射到不同的物理内存页。

- 好处：一个进程的野指针、崩溃不会影响其他进程，稳定性、安全性极强。
- 代价：进程间无法直接访问对方内存，所有数据交互必须通过内核中转或共享物理内存，这就是进程间通信（IPC）复杂度高、开销大的根源。

### 2. `fork()` 的底层本质：写时复制（COW）

很多人误以为`fork`会完整复制整个进程地址空间，这是错误的。Linux 的`fork`基于写时复制（Copy-On-Write） 机制：

1. `fork`后，父子进程的虚拟地址空间映射到同一份物理内存，内核将所有内存页标记为「只读」。
2. 只有当父子任意一方尝试修改内存时，内核才会复制对应的物理页，给修改方分配独立的物理内存。

> 衍生结论：
> 
> - `fork`的实际开销远小于直觉，无内存修改时几乎没有额外内存成本。
> - 父子进程共享打开的文件描述符（文件表位于内核空间，不属于进程地址空间），因此`fork`后父子操作同一个 fd 会相互影响。

### 进程生命周期的本质

进程所有状态变化，本质都是内核调度器对「CPU 时间」和「资源等待」的管理：

- 运行态 / 就绪态：争夺 CPU 时间片，由调度器按策略切换。
- 阻塞态：主动放弃 CPU，等待 IO 完成、信号或锁资源。
- 僵尸进程：进程已退出执行（代码停止运行），但父进程未调用`wait/waitpid`回收其内核 PCB（进程控制块），导致 PID、退出状态等内核资源无法释放。本质是「内核数据结构未被父进程认领」。
- 孤儿进程：父进程先退出，子进程被`init/systemd`收养，最终会被自动回收，不存在资源泄漏。

### IPC 的第一性分类逻辑

所有进程间通信，本质都是打破地址空间隔离的手段，按实现路径分为两类：

> 补充：信号本质是「软件中断」，是内核向进程发送的异步事件通知，不属于数据传输类 IPC。

### 多进程的核心权衡

- 优势：地址空间隔离带来的高稳定性、高安全性，故障隔离能力强。
- 劣势：进程上下文切换开销大（需要切换页表、刷新 TLB、保存全量寄存器）；IPC 复杂且成本高。

## 三、多线程编程第一性原理

### 线程的核心特质：共享地址空间的执行流

Linux 下的线程本质是轻量级进程（LWP），内核为每个线程维护独立的`task_struct`（PCB），调度器以线程为单位进行 CPU 调度。

#### 资源归属划分

- 所有线程共享：进程的虚拟地址空间（全局变量、堆内存）、文件描述符表、信号处理函数、用户 ID / 进程 ID。
- 每个线程独有：线程栈（用户态栈，默认几 MB 大小）、寄存器上下文、线程 ID（TID）、线程局部存储（TLS）、`errno`变量。

> 这就是线程安全问题的根源：绝大多数资源都是共享的，多线程同时修改共享资源就会出现竞态。

### 线程安全的本质：竞态条件与原子性

#### 竞态条件（Race Condition）

多个线程同时访问共享资源，且至少有一个线程执行写操作，最终结果完全依赖于线程的调度时序（CPU 切换时机），结果不可预测。

#### 底层根源：指令非原子性

高级语言的一行代码，对应 CPU 的多条指令。例如`i++`对应 3 条 CPU 指令：

1. 从内存读取`i`的值到寄存器
2. 寄存器内数值 + 1
3. 将结果写回内存

线程切换可能发生在这 3 步的任意一步之间，导致数据覆盖、结果错误。线程安全的本质，就是保证临界区操作的原子性。

### 同步互斥工具的底层原理

所有同步工具，都是内核提供的「原子性保障」或「时序协调」机制：

#### （1）互斥锁（mutex）

- 本质：内核维护的「标志位 + 等待队列」。
- 机制：加锁时通过原子操作尝试占用标志位；成功则进入临界区；失败则将当前线程放入等待队列，阻塞并让出 CPU。解锁时恢复标志位，唤醒等待队列中的线程。
- 优化：Linux 的`pthread_mutex`基于`futex`实现，无竞争时仅在用户态完成原子操作，无需陷入内核，开销极低。

#### （2）自旋锁（spinlock）

- 本质：加锁失败时不阻塞，循环空转（忙等）直到获取锁。
- 取舍：用 CPU 时间换取上下文切换的开销，仅适合锁持有时间极短的场景（如内核临界区），用户态极少使用。

#### （3）条件变量（condition variable）

- 本质：内核维护的「等待队列」，用于线程间的事件通知，必须与互斥锁配合使用。
- 为什么必须配 mutex？：「检查等待条件」和「进入等待队列」必须是原子操作，否则会出现「丢失唤醒」—— 条件在检查后、入队前被修改并发送唤醒信号，线程永久等待。

#### （4）信号量（semaphore）

- 本质：内核维护的「计数器 + 等待队列」。
- 能力：计数初始为 1 时等价于互斥锁；计数初始为 0/N 时可实现线程间同步（生产者 - 消费者模型）。

### 死锁的第一性原理

死锁的本质是资源分配形成闭环，同时满足 4 个必要条件，缺一不可：

1. 互斥条件：资源只能被一个线程持有，不能共享。
2. 持有并等待：线程已持有至少一个资源，又在等待其他线程持有的资源。
3. 不可剥夺：资源不能被强行抢占，只能由持有者主动释放。
4. 循环等待：线程间形成首尾相接的资源等待链条。

> 解决死锁的唯一思路：打破任意一个必要条件。工程中最常用的是打破「循环等待」（统一加锁顺序），其次是打破「持有并等待」（一次性申请所有资源）。

### 多线程的核心权衡

- 优势：线程上下文切换开销小（无需切换页表、刷新 TLB）；共享数据方便，通信成本几乎为 0。
- 劣势：无地址空间隔离，一个线程崩溃（野指针、栈溢出）会导致整个进程退出；线程安全问题复杂，极易出现隐蔽 bug。

## 四、学习与实践的第一性原则

### 学习顺序：先本质，后 API

不要上来就背函数接口，按以下路径逐层深入：

1. 打底：巩固虚拟内存、地址空间、内核态 / 用户态、系统调用、上下文切换的底层概念。
2. 多进程：先理解写时复制、进程状态、IPC 分类逻辑，再学习`fork`、`wait`、`exec`、各类 IPC 的 API。
3. 多线程：先理解共享 / 独有资源、竞态条件、原子性，再学习线程创建 / 回收 API，最后逐个吃透互斥锁、条件变量、信号量的机制与适用场景。

### 实践验证：用代码印证原理

每学一个概念，写极简代码验证底层现象：

- 验证竞态：启动 10 个线程各对全局变量加 10000 次，观察结果不等于 100000 的现象，加锁后再验证结果正确。
- 验证写时复制：`fork`后打印父子进程中同一个变量的虚拟地址（相同），修改其中一方后再打印值（不同），印证虚拟地址相同但物理内存已分离。
- 验证死锁：写两个线程按相反顺序加两把锁，复现死锁现象，再调整加锁顺序解决。
- 用`strace`跟踪程序，观察`fork`、`pthread_create`底层都调用了`clone`系统调用，印证 Linux 线程是轻量级进程。

### 最终判断框架

遇到技术选型时，回归本质判断：

- 优先需要故障隔离、稳定性 → 选多进程（如 Nginx、Chrome）
- 优先需要高并发、低开销、数据共享频繁 → 选多线程（如大多数业务后端、计算密集型程序）

# 进程基础

## 一、认识进程

### 核心知识点

1. 进程定义

   - 本质：程序在操作系统中的一次执行过程，是系统资源分配和调度的基本单位
   - 内核实体：每启动一个程序，内核会创建一个 `task_struct` 结构体（进程控制块 PCB），存储进程的所有运行信息（状态、PID、内存指针等）
   - 生命周期：进程执行结束后，PCB 由内核回收；异常崩溃时内核也会自动清理资源
2. 调度基础：时间片轮转

   - 就绪态进程会进入运行队列，内核为每个进程分配毫秒级时间片
   - 单核 CPU 通过时间片轮转交替执行不同进程，实现逻辑并发；多核 CPU 可实现物理并行
3. 进程四大核心特征

   - 动态性：动态产生、动态消亡，是程序的执行过程
   - 并发性：多个进程可同时被调度，宏观上呈现并行效果
   - 独立性：独立运行、独立分配资源的基本单位，地址空间相互隔离
   - 异步性：进程执行速度不可预知，以各自独立的节奏推进

### 补充拓展

- 进程 vs 线程：进程是资源分配最小单位，线程是 CPU 调度最小单位；一个进程内可包含多个线程，线程共享进程的地址空间和资源
- Linux 调度器：默认使用 CFS（完全公平调度器），按优先级和虚拟运行时间分配 CPU 时间，保证调度公平性
- 并发 vs 并行：并发是宏观同时运行、微观交替执行（单核场景）；并行是微观上真正同时执行（多核场景）

## 二、程序与进程的关系

### 核心知识点


<table v-pre><tbody><tr><td>对比维度</td><td>程序 (Program)</td><td>进程 (Process)</td></tr><tr><td>本质</td><td>静态的指令集合，是存储在磁盘上的可执行文件</td><td>程序的动态执行过程，是程序运行时的实例</td></tr><tr><td>存在形式</td><td>静态长期存储，以文件形式保存在磁盘中</td><td>具备动态生命周期，程序启动时创建，执行结束后销毁</td></tr><tr><td>资源占用</td><td>仅占用磁盘存储空间，不消耗系统运行时资源</td><td>占用 CPU、内存、文件句柄、网络端口等系统资源</td></tr><tr><td>状态属性</td><td>无运行状态，仅为指令 + 数据的静态集合</td><td>具备多种运行状态，会随系统调度动态变化</td></tr><tr><td>独立性</td><td>多个程序文件相互独立，彼此无直接关联</td><td>每个进程拥有独立的地址空间，默认不共享数据</td></tr><tr><td>示例</td><td>磁盘上的 chrome.exe 可执行文件</td><td>双击启动后，正在运行的浏览器窗口进程</td></tr></tbody></table>


1. 二者关联

   - 对应关系：一个程序可以对应多个进程（如打开多个浏览器窗口）；一个进程只能对应一个程序
   - 逻辑关系：程序是进程的「模板」，进程是程序的「运行态」；程序的指令逻辑决定进程的行为
   - 内存共享：同一程序的多个进程共享只读的代码段，各自拥有独立的数据段
   - 生命周期解耦：关闭进程不影响磁盘上的程序文件；删除程序文件后，已启动的进程可继续运行（直到需要加载依赖文件时出错）

### 补充拓展

- 为什么删除程序文件后进程还能运行：程序执行时会将代码和数据加载到内存中，磁盘文件只是持久化存储的镜像；运行过程中若不读取新的文件资源，删除磁盘文件不影响内存中的执行
- 代码段共享的底层：多个进程虚拟地址空间的代码段，通过 MMU 映射到同一块物理内存，大幅节省物理内存开销
- 进程实例：每启动一次程序就生成一个进程实例，多个实例相互独立，互不影响

## 三、进程组成与运行属性

### 核心知识点

#### 1. 进程三大组成部分

进程在内存中由进程控制块 (PCB)、文本段 (代码段)、数据段三部分构成。

##### (1) 进程控制块（PCB，`task_struct`）

- 定位：操作系统管理进程的核心数据结构，每个进程对应唯一的 PCB
- 作用：记录进程的所有关键信息，是操作系统感知进程存在的唯一标志
- 存储内容：进程标识符、进程状态、内存管理信息、资源占用信息、寄存器上下文、文件描述符表、信号配置等

##### (2) 文本段（代码段）

- 存储内容：程序编译后生成的可执行机器指令
- 属性：只读，防止进程意外修改自身指令
- 共享性：同一程序的多个进程可共享同一份代码段，节省内存
- 大小固定：进程运行期间代码段大小不会改变

##### (3) 数据段

存储进程运行时的所有数据，按初始化状态和可修改性分为四类：

- 初始化数据段：存储已初始化的全局变量、静态变量
- 未初始化数据段（BSS 段）：存储未初始化的全局变量、静态变量，程序加载时自动清零
- 堆（Heap）：动态内存分配区域，由程序员手动申请 / 释放（malloc/free），从低地址向高地址增长
- 栈（Stack）：存储函数参数、局部变量、函数调用上下文，由系统自动分配释放，从高地址向低地址增长

#### 2. 虚拟地址与物理地址映射

- 虚拟地址空间：每个进程都拥有独立的虚拟地址空间，进程只能访问自己的虚拟地址
- 物理地址：实际的内存硬件地址
- 映射机制：通过 MMU（内存管理单元） 将虚拟地址转换为物理地址
- 32 位 Linux 地址空间划分： 

  - 用户空间：0\~3GB，进程可直接访问，每个进程独立
  - 内核空间：3\~4GB，所有进程共享，仅内核可访问
- 交换分区（Swap）：磁盘上的一块空间，物理内存不足时，内核将不常用的内存页换出到 Swap，需要时再换入内存，扩展可用内存容量

#### 3. Linux 进程三大类型

##### (1) 交互进程

- 定义：由 Shell 启动，需用户终端交互的进程
- 特点：依赖终端，通常前台运行，生命周期与用户操作绑定
- 示例：终端执行的命令、图形界面程序

##### (2) 批处理进程

- 定义：无需实时交互，按预设任务自动后台运行的进程
- 特点：优先级较低，通过脚本 / 任务调度工具启动
- 示例：定时备份脚本、批量数据处理任务

##### (3) 守护进程（Daemon）

- 定义：系统启动时自动运行的后台进程，独立于终端，随系统启停
- 特点：脱离终端，长期运行，提供持续系统服务
- 示例：systemd、sshd、nginx 服务进程

#### 4. 进程基础状态（6 种）


<table v-pre><tbody><tr><td>状态标识</td><td>状态名称</td><td>说明</td></tr><tr><td>R</td><td>运行态 / 可运行态</td><td>正在 CPU 上执行，或在就绪队列中等待调度</td></tr><tr><td>S</td><td>可中断睡眠态</td><td>等待某事件完成（如 IO、信号），可被信号唤醒</td></tr><tr><td>D</td><td>不可中断睡眠态</td><td>等待关键硬件操作完成，不能被信号中断，保证数据完整性</td></tr><tr><td>T</td><td>停止态</td><td>收到暂停信号（SIGSTOP）或被调试器暂停，可通过 SIGCONT 恢复</td></tr><tr><td>Z</td><td>僵尸态</td><td>进程已终止执行，但 PCB 未被父进程回收，仍占用 PID 资源</td></tr><tr><td>X</td><td>死亡态</td><td>进程彻底终止，所有资源全部释放，瞬间状态，无法观测</td></tr></tbody></table>


核心状态转换路径：

- 运行态 → 可中断 / 不可中断睡眠态：进程等待资源或 IO，主动放弃 CPU
- 睡眠态 → 运行态：等待的事件完成，被唤醒进入就绪队列
- 运行态 → 停止态：收到 SIGSTOP 等暂停信号
- 停止态 → 运行态：收到 SIGCONT 恢复信号
- 运行态 → 僵尸态：进程执行结束调用 exit ()，等待父进程回收
- 僵尸态 → 死亡态：父进程调用 wait/waitpid 回收 PCB 资源

#### 5. 进程附加状态标记

ps/top 命令中状态列的附加字符，补充说明进程属性：

- `+`：前台进程组，与当前终端直接关联，可接收终端输入
- `l`：多线程进程，包含多个轻量级进程（LWP）
- `N`：低优先级进程，nice 值为正数
- `<`：高优先级进程，nice 值为负数
- `s`：会话首进程，管理整个会话的进程组
- `L`：进程持有文件锁或资源锁

#### 6. 进程 PID（进程标识符）

- 定义：操作系统为每个进程分配的唯一数字编号，是进程的身份标识
- 规则： 

  - 取值为≥0 的整数，实际从 1 开始分配，0 号为特殊系统进程
  - 系统可创建的进程总数有上限，通过 `sysctl kernel.pid_max` 查看
- 查看方式： 

  - 每个进程对应 `/proc/[PID]` 目录（proc 虚拟文件系统）
  - 目录内 `status` 文件存储进程详细信息（PID、名称、状态等）

#### 7. 特殊 PID 进程


<table v-pre><tbody><tr><td>PID</td><td>进程名称</td><td>核心作用</td></tr><tr><td>0</td><td>idle（swapper）</td><td>系统第一个进程，空闲时占用 CPU，是所有进程的祖先</td></tr><tr><td>1</td><td>init（systemd）</td><td>由 0 号进程创建，负责系统初始化、启动服务、回收孤儿进程</td></tr><tr><td>2</td><td>kthreadd</td><td>内核线程管理进程，负责创建、调度所有内核级线程</td></tr></tbody></table>


### 补充拓展

#### 1. 进程地址空间完整布局（32 位，从低地址到高地址）

- 保留区：0 地址附近，禁止访问，用于捕获空指针
- 代码段（.text）：只读，存储机器指令
- 数据段：初始化数据段（.data）、未初始化数据段（.bss）
- 堆区：动态内存分配，向上增长
- 共享库映射区：加载动态链接库，如 shturl.
- 栈区：函数调用栈，向下增长
- 内核空间：高地址 1GB，所有进程共享

#### 2. 栈和堆的核心区别


<table v-pre><tbody><tr><td>对比项</td><td>栈</td><td>堆</td></tr><tr><td>分配方式</td><td>系统自动分配释放</td><td>程序员手动申请释放</td></tr><tr><td>增长方向</td><td>从高地址向低地址增长</td><td>从低地址向高地址增长</td></tr><tr><td>空间大小</td><td>固定大小（默认几 MB）</td><td>空间大，受限于物理内存 + Swap</td></tr><tr><td>分配效率</td><td>极高，直接移动栈指针</td><td>较低，需查找空闲内存块</td></tr><tr><td>存储内容</td><td>局部变量、函数参数、返回地址</td><td>动态分配的内存，如 malloc 申请的空间</td></tr><tr><td>安全性</td><td>不会产生内存碎片</td><td>频繁申请释放易产生内存碎片</td></tr></tbody></table>


#### 3. 僵尸进程深入说明

- 成因：子进程先于父进程退出，父进程未调用 wait ()/waitpid () 获取子进程退出状态，内核无法释放子进程的 PCB
- 危害：仅占用 PID 和 PCB 结构体，不占用内存等其他资源；但大量僵尸进程会耗尽系统 PID，导致无法创建新进程
- 解决方法： 

  1. 父进程主动调用 wait ()/waitpid () 回收（根本解决）
  2. 杀死父进程，使子进程变为孤儿进程，由 1 号 init/systemd 收养并自动回收
  3. 父进程注册 SIGCHLD 信号处理函数，子进程退出时内核自动发信号，在处理函数中调用 wait 回收

#### 4. 孤儿进程说明

- 定义：父进程先退出，子进程还在运行，该子进程即为孤儿进程
- 归宿：内核会将孤儿进程的父进程设置为 1 号 init/systemd 进程，由 1 号进程负责回收其资源
- 特点：不会造成资源泄漏，是安全的

#### 5. 进程组与会话

- 进程组：多个相关进程的集合，共享同一个进程组 ID（PGID）；可向整个进程组发送信号；进程组首进程的 PID=PGID
- 会话：多个进程组的集合，一个会话对应一个控制终端；会话首进程通常是 Shell 程序；一个会话可包含一个前台进程组和多个后台进程组

#### 6. /proc 文件系统补充

- 虚拟文件系统，所有内容由内核动态生成，不占用磁盘空间
- 常用文件： 

  - `/proc/cpuinfo`：CPU 硬件信息
  - `/proc/meminfo`：内存使用信息
  - `/proc/version`：内核版本信息
  - `/proc/[pid]/fd`：进程打开的所有文件描述符
  - `/proc/[pid]/maps`：进程地址空间映射情况

## 五、进程的创建（fork 函数）

### 核心知识点

#### 1. fork 函数基础

- 头文件：

```c
#include <sys/types.h>
#include <unistd.h>
```

- 函数原型：`pid_t fork(void);`
- 功能：复制当前进程，创建一个新的子进程
- 返回值（一次调用，两次返回）： 

  - 父进程中：返回值 > 0，值为子进程的 PID
  - 子进程中：返回值 = 0
  - 创建失败：返回 -1，设置 errno

#### 2. 写时拷贝（Copy-On-Write, COW）

fork 创建子进程时，不会立即复制父进程的全部内存，而是采用写时拷贝机制：

- 读操作：父子进程的虚拟地址映射到同一块物理内存，内存标记为只读，双方共享访问
- 写操作：任意一方尝试修改内存时，内核才会复制对应的物理内存页，分配给修改方，双方各自拥有独立的内存副本
- 优势：大幅降低 fork 的内存开销，提高进程创建效率，避免无意义的内存拷贝

#### 3. 父子进程的继承关系

子进程会继承父进程的大部分资源：

- 继承：代码段、数据段、堆、栈、文件描述符表、信号处理方式、工作目录、用户 ID / 组 ID、环境变量、文件权限掩码
- 不继承：PID、PPID、挂起的信号集合、文件锁、定时器

### 补充拓展

#### 1. fork 底层实现

- Linux 中 fork 本质是调用`clone()`系统调用实现的
- clone 通过参数控制父子进程共享资源的程度： 

  - fork：共享虚拟内存的页表（写时复制），不共享地址空间
  - 线程（pthread_create）：共享整个虚拟地址空间、文件描述符表、信号处理等
- 结论：Linux 下的线程本质是「轻量级进程（LWP）」，每个线程对应内核中一个独立的 task_struct

#### 2. fork 执行特点

- 调用一次，返回两次：父进程和子进程各返回一次
- 执行顺序：fork 之后父子进程的执行顺序不确定，由操作系统调度器决定
- 代码执行：子进程从 fork 调用之后的代码开始执行，不会从头执行整个程序

#### 3. fork 与文件 IO 的注意事项

- 父子进程共享文件描述符表：fork 后，父子进程的相同文件描述符指向同一个内核文件表项，共享文件偏移量
- 问题：若父子进程同时向同一个文件写数据，会因为共享偏移量导致数据交错、覆盖
- 解决：父子进程独立打开文件（各自拥有独立的文件表项和偏移量），或加同步锁

#### 4. 常见 fork 面试考点

- 僵尸进程、孤儿进程的成因与解决
- 写时复制的原理与优势
- fork 后父子进程的资源共享与差异
- fork 的返回值逻辑，两次返回的理解
- fork 创建 N 个子进程，总进程数计算

## 实战练习：多进程实现文件分块拷贝

> 对应课程练习需求：父子进程协同拷贝文件，父进程拷前半段，子进程拷后半段，目标文件与源文件完全一致

### 实现思路

1. 前置准备：打开源文件，获取文件总大小，创建目标文件
2. 进程创建：调用 fork 创建子进程
3. 分块逻辑： 

   - 父进程：从文件起始位置开始，拷贝前 1/2 大小的数据
   - 子进程：从文件 1/2 位置开始，拷贝后 1/2 大小的数据
4. 关键处理： 

   - 父子进程各自独立打开源文件和目标文件，避免共享文件偏移量
   - 使用`lseek()`函数精准定位读写位置
   - 处理边界：单次读取数据量超过剩余待拷贝长度时，只拷贝剩余长度
5. 资源回收：父进程调用`waitpid()`等待子进程结束，避免僵尸进程

### 参考代码

```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/types.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <wait.h>

#define BUF_SIZE 4096  // 缓冲区大小

int main(int argc, char *argv[]) {
    if (argc != 3) {
        printf("用法：%s 源文件 目标文件\n", argv[0]);
        exit(1);
    }

    // 获取源文件总大小
    struct stat st;
    if (stat(argv[1], &st) == -1) {
        perror("stat error");
        exit(1);
    }
    off_t file_size = st.st_size;
    off_t half_size = file_size / 2;

    pid_t pid = fork();
    if (pid == -1) {
        perror("fork error");
        exit(1);
    }

    if (pid > 0) { // 父进程：拷贝前半段
        // 父进程独立打开文件
        int src_fd = open(argv[1], O_RDONLY);
        int dest_fd = open(argv[2], O_WRONLY | O_CREAT | O_TRUNC, 0644);
        if (src_fd == -1 || dest_fd == -1) {
            perror("open error");
            exit(1);
        }

        // 定位到文件开头
        lseek(src_fd, 0, SEEK_SET);
        lseek(dest_fd, 0, SEEK_SET);

        char buf[BUF_SIZE];
        off_t remain = half_size;  // 剩余待拷贝长度
        ssize_t read_len;

        while (remain > 0) {
            // 每次读取不超过缓冲区大小和剩余长度
            size_t read_size = remain < BUF_SIZE ? remain : BUF_SIZE;
            read_len = read(src_fd, buf, read_size);
            if (read_len == -1) {
                perror("read error");
                exit(1);
            }
            if (read_len == 0) break;

            write(dest_fd, buf, read_len);
            remain -= read_len;
        }

        close(src_fd);
        close(dest_fd);

        // 等待子进程结束，回收资源
        waitpid(pid, NULL, 0);
        printf("文件拷贝完成\n");

    } else { // 子进程：拷贝后半段
        // 子进程独立打开文件
        int src_fd = open(argv[1], O_RDONLY);
        int dest_fd = open(argv[2], O_WRONLY | O_CREAT, 0644);
        if (src_fd == -1 || dest_fd == -1) {
            perror("open error");
            exit(1);
        }

        // 定位到文件中间位置
        lseek(src_fd, half_size, SEEK_SET);
        lseek(dest_fd, half_size, SEEK_SET);

        char buf[BUF_SIZE];
        off_t remain = file_size - half_size;
        ssize_t read_len;

        while (remain > 0) {
            size_t read_size = remain < BUF_SIZE ? remain : BUF_SIZE;
            read_len = read(src_fd, buf, read_size);
            if (read_len == -1) {
                perror("read error");
                exit(1);
            }
            if (read_len == 0) break;

            write(dest_fd, buf, read_len);
            remain -= read_len;
        }

        close(src_fd);
        close(dest_fd);
        exit(0);
    }

    return 0;
}
```

### 注意事项

1. 必须独立打开文件：若共享父进程的文件描述符，会因为共享文件偏移量导致读写位置错乱
2. 边界处理：文件大小为奇数时，后半段长度 = 总长度 - 半长，避免少拷贝或多拷贝
3. 父进程必须等待子进程：否则子进程退出后会变成僵尸进程
4. 权限设置：创建目标文件时指定权限 0644，避免文件权限异常

## 进程号获取函数

用于获取进程自身或父进程的唯一标识，是进程管理的基础接口。

### getpid()

- 头文件：`#include <sys/types.h>` `#include <unistd.h>`
- 函数原型：`pid_t getpid(void);`
- 功能：获取当前进程的进程号（PID）
- 返回值：当前进程的 PID，调用永远成功
- 补充： 

  - `pid_t` 本质是 `int` 类型的重定义，专门用于表示进程 ID
  - PID 是内核管理进程 PCB 的唯一标识，系统通过 PID 定位进程

### getppid()

- 头文件：`#include <sys/types.h>` `#include <unistd.h>`
- 函数原型：`pid_t getppid(void);`
- 功能：获取当前进程的父进程的进程号（PPID）
- 返回值：父进程的 PID，调用永远成功

### 代码示例

```c
#include <stdio.h>
#include <sys/types.h>
#include <unistd.h>

int main() {
    pid_t pid = fork();
    if (pid == 0) {
        printf("子进程：PID=%d，父进程PPID=%d\n", getpid(), getppid());
    } else if (pid > 0) {
        printf("父进程：PID=%d，子进程PID=%d\n", getpid(), pid);
    }
    return 0;
}
```

## 进程退出函数

用于主动终止进程，分为「标准库退出」和「系统调用退出」两类，行为差异是高频考点。

### exit () —— C 标准库函数

- 头文件：`#include <stdlib.h>`
- 函数原型：`void exit(int status);`
- 功能：正常终止当前进程，将退出状态 `status` 返回给父进程
- 参数：`status` —— 退出状态码，仅低 8 位有效（等价于 `status & 0377`），有效范围 0\~255 

  - 标准宏：`EXIT_SUCCESS`（值为 0，正常退出）、`EXIT_FAILURE`（值为 1，异常退出）
- 执行流程（核心）： 

  1. 按逆序执行所有通过 `atexit()` 注册的退出回调函数
  2. 刷新所有标准 IO 缓冲区，关闭打开的文件流
  3. 释放用户态资源，最终调用 `_exit()` 进入内核终止进程

### \_exit () —— 系统调用

- 头文件：`#include <unistd.h>`
- 函数原型：`void _exit(int status);`
- 功能：立即终止当前进程，直接陷入内核释放资源，将 status 返回父进程
- 特点：不执行任何用户态清理工作，不刷新 stdio 缓冲区、不调用 atexit 回调

### 核心对比：exit vs \_exit


<table v-pre><tbody><tr><td>对比维度</td><td>exit()</td><td>_exit()</td></tr><tr><td>所属层级</td><td>C 标准库函数</td><td>Linux 系统调用</td></tr><tr><td>用户态清理</td><td>完整执行（刷新缓冲区、关闭流、调用 atexit）</td><td>无任何清理，直接进入内核</td></tr><tr><td>适用场景</td><td>普通程序正常退出</td><td>子进程紧急退出、避免复制缓冲区副作用</td></tr><tr><td>底层关系</td><td>最终内部会调用 _exit ()</td><td>内核原生进程终止接口</td></tr></tbody></table>


### 补充拓展

1. return 与 exit 的区别

   - `return` 是 C 语言关键字，用于函数返回；仅在 `main` 函数中 `return n` 等价于 `exit(n)`
   - 普通函数中 `return` 只是函数返回，不会终止整个进程；`exit` 在任意位置调用都会终止整个进程
2. atexit () 退出回调

   - 原型：`int atexit(void (*func)(void));`
   - 功能：注册进程退出前的回调函数；进程通过 `exit` 正常退出时，会按注册的逆序执行所有回调
   - 注意：`_exit` 退出不会执行这些回调
3. 经典易错示例

```c
printf("hello world"); // 无换行符，内容滞留在用户态缓冲区
_exit(0); // 直接退出，不刷新缓冲区，终端无输出
// 替换为 exit(0) 则会刷新缓冲区，正常输出内容
```

## 资源回收函数

子进程退出后，内核会保留 PCB 结构（存放退出状态等信息），必须由父进程主动回收，否则会产生僵尸进程。

### wait()

- 头文件：`#include <sys/types.h>` `#include <sys/wait.h>`
- 函数原型：`pid_t wait(int *wstatus);`
- 功能：父进程阻塞等待任意一个子进程终止，回收子进程内核资源，并获取子进程退出状态
- 参数：`wstatus` —— 输出型参数，用于存放子进程的退出状态信息 

  - 传 `NULL`：不关心退出状态，仅回收资源
  - 传有效地址：将状态信息写入该地址，需通过专用宏解析
- 返回值： 

  - 成功：返回被回收子进程的 PID
  - 失败：返回 - 1（如当前进程没有子进程）

### waitpid()

- 头文件：`#include <sys/types.h>` `#include <sys/wait.h>`
- 函数原型：`pid_t waitpid(pid_t pid, int *wstatus, int options);`
- 功能：功能更强大的进程回收接口，支持指定回收目标、设置阻塞模式，还可捕获子进程暂停 / 恢复状态
- 参数详解：

#### ① pid —— 指定等待的子进程范围


<table v-pre><tbody><tr><td>pid 取值</td><td>含义</td></tr><tr><td>&gt; 0</td><td>等待 PID 为指定值的单个特定子进程</td></tr><tr><td> -1</td><td>等待任意一个子进程，功能等价于 wait ()</td></tr><tr><td>0</td><td>等待和当前进程同属一个进程组的任意子进程</td></tr><tr><td>&lt; -1</td><td>等待进程组 ID 等于 pid 绝对值的任意子进程</td></tr></tbody></table>


#### ② wstatus —— 子进程退出状态，用法与 wait 完全一致

#### ③ options —— 控制选项，支持按位或组合


<table v-pre><tbody><tr><td>选项常量</td><td>作用</td><td>典型应用场景</td></tr><tr><td>0</td><td>阻塞等待，同 wait 的默认行为</td><td>常规子进程同步、批处理任务</td></tr><tr><td>WNOHANG</td><td>非阻塞等待：指定子进程未退出时，函数立即返回 0，不阻塞</td><td>父进程轮询监控子进程，同时处理自身任务</td></tr><tr><td>WUNTRACED</td><td>捕获子进程暂停状态：子进程收到暂停信号时也会返回</td><td>进程调试、任务暂停管理</td></tr><tr><td>WCONTINUED</td><td>捕获子进程恢复状态：子进程收到 SIGCONT 恢复运行时也会返回</td><td>跟踪进程完整生命周期</td></tr></tbody></table>


- 返回值：

  - 成功：返回状态发生变化子进程的 PID
  - 设置`WNOHANG`且无子进程状态变化：返回 0
  - 调用失败：返回 - 1

### 退出状态解析宏（wait/waitpid 通用）

`wstatus` 不能直接读取数值，必须通过系统定义的宏解析：

#### ① 子进程正常退出

- `WIFEXITED(wstatus)`：子进程正常终止（exit/\_exit/main 返回）时，返回真
- `WEXITSTATUS(wstatus)`：仅当 WIFEXITED 为真时有效，返回子进程的退出状态码（低 8 位）

#### ② 子进程被信号终止

- `WIFSIGNALED(wstatus)`：子进程被信号杀死时，返回真
- `WTERMSIG(wstatus)`：仅当 WIFSIGNALED 为真时有效，返回导致终止的信号编号
- `WCOREDUMP(wstatus)`：仅当 WIFSIGNALED 为真时有效，子进程终止时生成 core 转储文件则返回真

#### ③ 子进程状态暂停 / 恢复（需对应 options 选项）

- `WIFSTOPPED(wstatus)`：子进程被暂停时返回真（需开启 WUNTRACED）
- `WSTOPSIG(wstatus)`：返回导致进程暂停的信号编号
- `WIFCONTINUED(wstatus)`：子进程恢复运行时返回真（需开启 WCONTINUED）

### 补充拓展

1. wait 与 waitpid 对比


<table v-pre><tbody><tr><td>对比维度</td><td>wait()</td><td>waitpid()</td></tr><tr><td>等待范围</td><td>只能等待任意子进程</td><td>可指定 PID、指定进程组</td></tr><tr><td>等待模式</td><td>只能阻塞</td><td>支持阻塞 / 非阻塞（WNOHANG）</td></tr><tr><td>状态捕获</td><td>仅捕获子进程退出</td><td>可捕获退出、暂停、恢复三种状态</td></tr><tr><td>灵活性</td><td>功能简单单一</td><td>功能强大，适配更多场景</td></tr></tbody></table>


1. 批量回收多个子进程 父进程有 N 个子进程时，需要循环调用 wait/waitpid 回收所有子进程，否则会产生多个僵尸进程。 非阻塞回收示例：

```c
// 循环非阻塞回收所有已退出的子进程
while (waitpid(-1, NULL, WNOHANG) > 0);
```

1. 僵尸进程与孤儿进程的处理

   - 僵尸进程：必须由父进程调用 wait/waitpid 回收；杀死父进程可让 init 进程领养后自动回收
   - 孤儿进程：父进程先退出，子进程被 init（PID=1）领养，最终由 init 自动回收，无资源泄漏风险

## 文件描述符重定向函数

`dup` 和 `dup2` 用于复制文件描述符，本质是让两个不同的 fd 指向同一个内核文件表项，是实现 Shell IO 重定向的核心底层接口。

### dup()

- 头文件：`#include <unistd.h>`
- 函数原型：`int dup(int oldfd);`
- 功能：复制已有的文件描述符 `oldfd`，返回一个全新的文件描述符
- 分配规则：新 fd 采用「最小未使用」原则，自动分配当前可用的最小编号
- 返回值： 

  - 成功：返回新的文件描述符
  - 失败：返回 - 1，设置 errno

### dup2 () —— 开发更常用

- 头文件：`#include <unistd.h>`
- 函数原型：`int dup2(int oldfd, int newfd);`
- 功能：将 `oldfd` 复制到指定的 `newfd` 编号上
- 执行逻辑： 

  1. 若 `newfd` 已经处于打开状态，会先自动静默关闭 newfd
  2. 将 oldfd 复制到 newfd，两个 fd 指向同一个内核文件
  3. 特殊情况：若 oldfd 和 newfd 相等，直接返回 newfd，不执行关闭操作
- 返回值：成功返回 newfd，失败返回 - 1

### 补充拓展

1. 底层原理 复制后的两个文件描述符，指向内核中同一个文件表项，因此共享：

   - 文件读写偏移量
   - 文件状态标志（只读、只写、追加等） 但两个 fd 本身是独立的，关闭其中一个不会影响另一个的可用性。
2. 经典应用：标准输出重定向 把标准输出（fd=1）重定向到文件，是 Shell 中 `>` 重定向符号的底层实现：

```c
#include <stdio.h>
#include <unistd.h>
#include <fcntl.h>

int main() {
    int fd = open("output.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
    dup2(fd, 1); // 将标准输出1重定向到fd指向的文件
    close(fd);    // 原fd已完成使命，关闭释放
    printf("这条内容会写入文件，而不是输出到终端\n");
    return 0;
}
```

1. dup2 的原子性优势 dup2 中「关闭 newfd + 复制 oldfd」是原子操作，中间不会被打断；如果手动 `close(newfd)` + `dup(oldfd)`，在多线程环境下可能出现竞态，中间 fd 编号被其他线程占用。

## 进程程序替换函数 —— exec 函数族

exec 函数族的核心作用：用一个全新的程序替换当前进程的执行映像，进程 PID 保持不变，代码段、数据段、堆、栈全部替换为新程序的内容。

> 通常配合 fork 使用：父进程 fork 创建子进程，子进程调用 exec 执行外部程序，这就是 Shell 执行命令的核心原理。

### 命名规律（记忆核心）

### 核心特性

- 成功无返回：exec 调用成功后，当前进程代码被完全替换，原程序中 exec 之后的代码永远不会执行
- 失败返回 - 1：只有调用失败（如找不到文件、权限不足）才会返回，因此 exec 后通常直接跟错误处理逻辑
- 继承属性：替换后进程的 PID、PPID、UID、GID、工作目录、文件描述符（默认）都会保留 

> - 注：若文件描述符设置了 `FD_CLOEXEC` 标志，exec 执行时会自动关闭该 fd

### 代码示例

#### 示例 1：execlp 执行 ls 命令

```c
#include <stdio.h>
#include <unistd.h>

int main() {
    printf("执行 ls -l 命令\n");
    // 等价于 Shell 中执行 ls -l
    execlp("ls", "ls", "-l", NULL);
    // 调用成功的话，下面代码永远不会执行
    perror("execlp 执行失败");
    return 1;
}
```

#### 示例 2：execvp 数组传参

```c
#include <stdio.h>
#include <unistd.h>

int main() {
    char *argv[] = {"ls", "-l", "-a", NULL};
    execvp("ls", argv);
    perror("execvp 执行失败");
    return 1;
}
```

### 补充拓展

1. Shell 执行命令的完整流程

   1. Shell 进程调用 `fork()` 创建子进程
   2. 子进程根据命令参数做 IO 重定向（`dup2` 实现）
   3. 子进程调用 `exec` 函数族，替换为对应的命令程序
   4. 父进程调用 `wait/waitpid` 阻塞等待子进程执行结束，回收资源
   5. 子进程结束后，父进程继续接收下一条命令输入
2. exec 与 fork 配合的意义 单独 fork 只能执行和父进程相同的代码逻辑，配合 exec 才能运行外部的、完全独立的程序，是 Linux 多进程编程的核心模式。
3. 常见易错点

   - 参数列表必须以 `NULL` 结尾，否则会出现内存越界访问错误
   - 第一个参数（argv [0]）约定为程序名，虽然可自定义，但建议和实际程序保持一致
   - 自定义环境变量数组也必须以 NULL 结尾

## 整体知识串联：进程生命周期完整 API 流程

1. 创建进程：`fork()` 复制进程地址空间，产生父子两个独立执行流
2. 获取标识：`getpid()` / `getppid()` 获取进程与父进程 ID
3. IO 重定向：`dup()` / `dup2()` 调整文件描述符指向，实现输入输出重定向
4. 程序替换：`exec` 函数族替换子进程执行逻辑，运行外部程序
5. 进程退出：子进程调用 `exit()` / `_exit()` 终止执行
6. 资源回收：父进程调用 `wait()` / `waitpid()` 回收子进程 PCB，避免产生僵尸进程

# 特殊进程

Linux 系统中基于进程生命周期与资源管理机制，衍生出三种典型特殊进程：孤儿进程、僵尸进程、守护进程。三者本质都是普通进程的特殊状态 / 形态，均围绕「父子进程关系」「资源回收」「终端关联」三个核心逻辑产生。

---

## 孤儿进程（Orphan Process）

### 【核心定义】

父进程先于子进程终止退出，该子进程就会成为孤儿进程；失去父进程后，内核会自动将其交由 1 号进程（init/systemd） 收养，成为 1 号进程的子进程。

### 【产生原因】

1. 父进程意外崩溃、被强制终止（如 `kill -9` 杀死父进程）
2. 父进程主动退出，但未等待子进程执行完成
3. 终端关闭时，Shell 进程退出，其启动的后台子进程变为孤儿

### 【核心特点】

1. 仍能正常运行，完整执行自身代码逻辑，功能不受影响
2. PPID（父进程 ID）变为 1，由 init/systemd 统一管理
3. 退出时由 1 号进程自动调用 wait 回收资源，不会变成僵尸进程

### 【影响与性质】

- 属于系统正常保护机制的产物，无任何危害
- 避免了子进程成为 “无主进程”，保障资源最终被正确回收
- 典型应用：守护进程的创建第一步，就是主动制造孤儿进程脱离原父进程

### 【底层原理补充】

当父进程退出时，内核会遍历该父进程的所有子进程，执行「领养逻辑」：将子进程的父进程指针指向 1 号进程。Linux 中 1 号进程的核心职责之一就是回收所有孤儿进程，因此孤儿进程退出后不会残留 PCB。

### 【代码示例：创建孤儿进程】

```c
#include <stdio.h>
#include <unistd.h>
#include <stdlib.h>

int main() {
    pid_t pid = fork();
    if (pid == 0) {
        // 子进程：循环打印PID和PPID
        while (1) {
            printf("子进程运行，PID=%d，PPID=%d\n", getpid(), getppid());
            sleep(2);
        }
    } else if (pid > 0) {
        // 父进程：1秒后退出，子进程变为孤儿
        printf("父进程运行，PID=%d，1秒后退出\n", getpid());
        sleep(1);
        printf("父进程退出\n");
        exit(0);
    }
    return 0;
}
```

> 运行验证：父进程退出后，子进程的 PPID 会变为 1（或 systemd 对应的 PID），且持续运行。

## 僵尸进程（Zombie Process）

### 【核心定义】

子进程已经终止执行（代码停止运行），但父进程未调用 `wait()` / `waitpid()` 读取子进程的退出状态，导致内核无法释放子进程的进程控制块（PCB），该进程就会进入僵尸态，成为僵尸进程。

### 【产生原因】

根本原因：子进程退出后，父进程未执行资源回收操作 常见场景：

1. 父进程长期运行（如服务器程序），忽略了子进程退出的处理
2. 父进程逻辑漏洞，忘记调用 wait/waitpid
3. 父进程在执行其他任务，没有及时处理子进程退出事件

### 【核心特点】

1. 进程已终止，不再执行任何代码，无运行实体
2. 仅保留内核 PCB 结构体，存储 PID、退出状态、资源统计等信息
3. `ps` 命令查看状态为 `Z`（僵尸态），进程名后常标注 `<defunct>`
4. 无法通过信号杀死（包括 `kill -9`），因为进程已经停止运行

### 【危害】

1. PID 资源耗尽：系统 PID 号是有限资源（默认最大值 32768，可通过`/proc/sys/kernel/pid_max`查看），大量僵尸进程会占满 PID，导致无法创建新进程
2. 内核内存泄漏：每个 PCB 占用内核空间内存，大量僵尸进程会浪费内核内存资源

> 注意：僵尸进程不占用用户态内存（代码段、数据段、堆栈等已释放），仅占用内核态的 PCB 资源

### 【处理方式】

#### 预防方案（根本解决）

- 主动等待回收：父进程中调用 `wait()` 或 `waitpid()`，阻塞 / 轮询回收子进程
- 信号异步回收（工程最常用）：父进程注册 `SIGCHLD` 信号处理函数，子进程退出时内核会自动向父进程发送 SIGCHLD 信号，在处理函数中调用`waitpid`批量回收所有已退出的子进程 

```c
// SIGCHLD信号回收示例
void sigchld_handler(int sig) {
    // 循环非阻塞回收所有已退出子进程
    while (waitpid(-1, NULL, WNOHANG) > 0);
}
// 主函数中注册信号
signal(SIGCHLD, sigchld_handler);
```

#### 事后清除（应急处理）

- 杀死父进程：僵尸进程的父进程终止后，僵尸进程会变为孤儿进程，被 1 号进程收养并自动回收 PCB
- 注意：直接对僵尸进程执行 `kill -9` 完全无效

### 【底层原理补充】

Linux 进程退出分为两个阶段：

1. 第一阶段：释放用户态所有资源（代码、数据、堆、栈、文件描述符等），进入僵尸态
2. 第二阶段：父进程读取退出状态后，内核释放 PCB 结构体，进程彻底消失 设计僵尸态的初衷：是为了让父进程能够获取子进程的执行结果、资源使用情况等信息。

### 【代码示例：产生僵尸进程】

```c
#include <stdio.h>
#include <unistd.h>
#include <stdlib.h>

int main() {
    pid_t pid = fork();
    if (pid == 0) {
        // 子进程：1秒后退出
        printf("子进程PID=%d，即将退出\n", getpid());
        sleep(1);
        exit(0);
    } else if (pid > 0) {
        // 父进程：不回收，循环休眠，子进程变为僵尸
        printf("父进程PID=%d，持续运行，不回收子进程\n", getpid());
        while (1) sleep(1);
    }
    return 0;
}
```

> 运行验证：执行 `ps aux | grep 程序名` 可看到子进程状态为 `Z`，标注 `<defunct>`。

## 守护进程（Daemon Process）

### 【核心定义】

运行在系统后台、独立于控制终端、长期稳定运行的特殊进程，用于持续提供系统服务或功能，是 Linux 后台服务的标准实现形态。

> 命名惯例：守护进程名称通常以 `d` 结尾，如 `sshd`、`httpd`、`systemd`、`crond`、`nginx`

### 【核心特点】

1. 脱离控制终端：不与任何终端绑定，终端关闭 / 登录注销都不会影响其运行
2. 后台长期运行：随系统启动而启动，系统关闭才终止，生命周期和系统一致
3. 父进程为 1 号：启动后脱离原父进程，被 init/systemd 收养
4. 运行环境干净：工作目录通常为根目录，标准 IO 重定向到`/dev/null`，不受用户环境影响
5. 状态通常为可中断睡眠态（`S`），等待事件触发

### 【应用场景】

所有需要长期后台运行的系统服务：网络服务、定时任务、日志服务、硬件监控等。

### 【守护进程创建标准流程（7 步）】

每一步都有明确的设计目的，不可省略：

### 【核心 API 详解】

#### setsid () 函数

- 头文件：`#include <sys/types.h>` `#include <unistd.h>`
- 原型：`pid_t setsid(void);`
- 功能：创建一个全新的会话，调用进程成为新会话的首进程，同时成为新进程组的组长
- 返回值：成功返回新会话 ID；失败返回 - 1
- 调用前提：调用进程不能是进程组组长，这也是第一步必须 fork 后父进程退出的原因

#### chdir () 函数

- 头文件：`#include <unistd.h>`
- 原型：`int chdir(const char *path);`
- 功能：修改调用进程的当前工作目录为指定路径
- 返回值：成功返回 0，失败返回 - 1

#### umask () 函数

- 头文件：`#include <sys/types.h>` `#include <sys/stat.h>`
- 原型：`mode_t umask(mode_t mask);`
- 功能：设置进程的文件权限掩码，影响新创建文件的默认权限
- 权限计算： 

  - 文件实际权限 = `~mask & 0666`
  - 目录实际权限 = `~mask & 0777`
- 返回值：总是成功，返回设置前的旧掩码值

### 【完整代码示例：创建守护进程】

```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/types.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <signal.h>

int create_daemon() {
    // 第一步：fork子进程，父进程退出
    pid_t pid = fork();
    if (pid < 0) return -1;
    if (pid > 0) exit(0); // 父进程直接退出

    // 第二步：创建新会话，脱离终端
    if (setsid() < 0) return -1;

    // 第三步：修改工作目录为根目录
    if (chdir("/") < 0) return -1;

    // 第四步：设置权限掩码为0
    umask(0);

    // 第五步：关闭所有文件描述符
    int max_fd = getdtablesize(); // 获取进程最大文件描述符数
    for (int i = 0; i < max_fd; i++) {
        close(i);
    }

    // 第六步：重定向标准输入输出错误到/dev/null
    int fd = open("/dev/null", O_RDWR);
    if (fd < 0) return -1;
    dup2(fd, 0); // 标准输入
    dup2(fd, 1); // 标准输出
    dup2(fd, 2); // 标准错误
    close(fd);

    return 0;
}

int main() {
    if (create_daemon() != 0) {
        perror("创建守护进程失败");
        exit(1);
    }

    // 守护进程核心业务：每秒写日志到文件（示例）
    FILE *fp = fopen("/tmp/daemon_test.log", "a");
    if (!fp) exit(1);
    
    while (1) {
        fprintf(fp, "守护进程运行中，PID=%d\n", getpid());
        fflush(fp);
        sleep(2);
    }

    fclose(fp);
    return 0;
}
```

> 运行验证：程序启动后终端会直接返回，进程在后台运行，可通过`ps aux`查看 PID，查看`/tmp/daemon_test.log`验证运行状态。

### 【补充：daemon () 库函数】

Linux 标准库提供了现成的守护进程创建函数 `daemon()`，封装了上述标准流程：

- 头文件：`#include <unistd.h>`
- 原型：`int daemon(int nochdir, int noclose);`
- 参数： 

  - `nochdir`：为 0 则修改工作目录为`/`，非 0 则不修改
  - `noclose`：为 0 则重定向标准 IO 到`/dev/null`，非 0 则不修改
- 返回值：成功返回 0，失败返回 - 1

## 高频面试 / 考点总结

1. Q：kill -9 能杀死僵尸进程吗？为什么？ A：不能。僵尸进程已经终止执行，没有运行实体，无法接收和处理信号；其残留的只有内核 PCB，必须由父进程回收，或交由 1 号进程回收。
2. Q：孤儿进程会变成僵尸进程吗？ A：不会。孤儿进程由 1 号进程收养，1 号进程会自动调用 wait 回收其退出后的 PCB，因此不会产生僵尸。
3. Q：守护进程创建为什么要 fork 两次？（部分实现会二次 fork） A：第二次 fork 是可选优化，目的是防止进程重新打开控制终端。因为只有会话首进程才能打开控制终端，二次 fork 后子进程不再是会话首进程，彻底杜绝关联终端的可能。
4. Q：僵尸进程的危害是什么？ A：主要是 PID 资源泄漏，大量僵尸进程会占满系统 PID 号，导致无法创建新进程；同时会占用少量内核内存。
5. Q：SIGCHLD 信号的作用是什么？ A：子进程退出时，内核会自动向父进程发送 SIGCHLD 信号；父进程可以注册该信号的处理函数，在函数中异步回收子进程资源，是工程中避免僵尸进程的标准方案。

# 进程间通信

## 一、Linux IPC 整体概述

Linux 进程间通信（Inter-Process Communication, IPC）继承了 Unix 的技术体系，主要分为三大类：

1. 传统 Unix IPC：无名管道、有名管道、信号
2. System V IPC：消息队列、共享内存、信号量集，由内核维护，通过键值（key）标识
3. BSD IPC：套接字（Socket），支持跨主机通信

核心本质：进程拥有独立地址空间，必须通过内核中转或共享物理内存的方式打破地址隔离，实现数据交互。

---

## 二、无名管道（Pipe）

### 核心定义

无名管道是内核维护的半双工字节流缓冲区，只能用于有亲缘关系的进程（父子、兄弟进程）间通信，依赖 fork 后文件描述符的继承实现。

- 内核缓冲区默认大小：64KB
- 本质：伪文件，不占用磁盘空间，仅存在于内核内存中
- 不可寻址：不支持 lseek 随机读写，只能顺序读写

### 核心 API

```c
#include <unistd.h>
int pipe(int pipefd[2]);
```

- 功能：创建管道，返回两个文件描述符 

  - `pipefd[0]`：读端，用于从管道读取数据
  - `pipefd[1]`：写端，用于向管道写入数据
- 返回值：成功返回 0，失败返回 - 1 并设置 errno

### 读写特性


<table v-pre><tbody><tr><td>场景</td><td>行为</td></tr><tr><td>管道空，写端存在</td><td>读操作阻塞，等待数据写入</td></tr><tr><td>管道空，写端全部关闭</td><td>读操作立即返回 0（读到文件结束符）</td></tr><tr><td>管道满，读端存在</td><td>写操作阻塞，等待数据被读取腾出空间</td></tr><tr><td>管道满，读端全部关闭</td><td>写操作触发SIGPIPE信号，进程默认终止（管道破裂）</td></tr></tbody></table>


### 补充说明

- 原子性：写入数据量小于`PIPE_BUF`（4096 字节）时，写操作保证原子性，不会被其他进程打断
- 半双工：数据只能单向流动；若需双向通信，需创建两个管道
- 生命周期：随进程存在，所有持有管道描述符的进程退出后，管道资源被内核回收

---

## 三、有名管道（FIFO）

### 核心定义

有名管道（命名管道）是在文件系统中存在实体文件的管道，突破了无名管道只能亲缘进程通信的限制，支持任意进程间通信。

- 内核缓冲区默认大小：64KB
- 半双工通信，同样不支持 lseek 随机访问
- 文件类型：p（管道文件），磁盘上仅存 inode，无实际数据块

### 核心 API

```c
#include <sys/types.h>
#include <sys/stat.h>
// 创建有名管道文件
int mkfifo(const char *pathname, mode_t mode);
```

- `pathname`：管道文件路径
- `mode`：文件权限，最终权限 = `mode & ~umask`
- 返回值：成功返回 0，失败返回 - 1

```c
#include <unistd.h>
// 删除文件链接（通用文件操作，也用于删除管道文件）
int unlink(const char *pathname);
```

### 读写特性

- 打开阻塞：默认以只读 / 只写方式打开时，会阻塞等待另一端（写 / 读）打开 

  - 只读打开：阻塞直到有进程以写方式打开
  - 只写打开：阻塞直到有进程以读方式打开
- 非阻塞模式：以`O_NONBLOCK`打开时 

  - 只读打开：无写端时也立即成功返回
  - 只写打开：无读端时直接返回失败，errno 设为 ENXIO
- 数据读写规则与无名管道完全一致

### 适用场景

同一主机内无亲缘关系的进程间简单数据交互，嵌入式系统中低延迟的进程控制指令传输。

---

## 四、信号（Signal）

### 核心定义

信号是 Linux 内核提供的异步事件通知机制，是软件层面对中断的模拟；可由内核、进程、用户终端发送给进程，用于通知进程发生了某类事件。

- 信号是最短的 IPC 方式，仅传递信号编号，不携带额外数据
- 进程对信号的三种处理方式：默认处理、忽略、捕捉（自定义处理函数）

### 核心 API

#### （1）信号注册

```c
#include <signal.h>
typedef void (*sighandler_t)(int);
sighandler_t signal(int signum, sighandler_t handler);
```

- `handler` 取值： 

  - `SIG_IGN`：忽略该信号
  - `SIG_DFL`：使用系统默认处理
  - 函数指针：自定义信号处理函数
- 返回值：成功返回旧的处理函数指针，失败返回`SIG_ERR`

#### （2）发送信号

```c
#include <sys/types.h>
#include <signal.h>
// 给指定PID进程发信号
int kill(pid_t pid, int sig);
```

- `pid` 取值： 

  - `>0`：发送给 PID 对应的单个进程（最常用）
  - `=0`：发送给当前进程所属进程组的所有进程
  - `=-1`：发送给所有有权限操作的进程（init 除外）
  - `<-1`：发送给进程组 ID 等于`-pid`的所有进程

```c
#include <signal.h>
// 给自身发送信号
int raise(int sig);
```

### 补充知识

- 不可靠信号（1-31 号）：不支持排队，短时间内多次发送同一信号，可能只响应一次；信号处理执行完后，处理方式可能重置为默认（不同系统实现有差异）
- 可靠信号（34-64 号，实时信号）：支持排队，发送多少次就响应多少次，不会丢失
- 9 号 SIGKILL 和 19 号 SIGSTOP：是特殊信号，既不能被捕捉，也不能被忽略，是内核保证进程可被强制终止 / 暂停的最后手段

## 五、消息队列（Message Queue）

### 核心定义

System V IPC 的一种，是内核维护的消息链表，进程通过消息队列标识符（msqid）访问；消息自带类型标识，支持按类型读取，无需按顺序接收。

- 优势：解决了管道只能传输无格式字节流、必须顺序读取的问题
- 生命周期：随内核，进程退出后消息队列依然存在，需手动删除或系统重启

### 通用前置：ftok 生成键值

System V IPC 都需要通过 key 值标识资源，不同进程通过同一个 key 获取同一个 IPC 资源。

```c
#include <sys/types.h>
#include <sys/ipc.h>
key_t ftok(const char *pathname, int proj_id);
```

- `pathname`：必须是一个已存在且可访问的文件路径
- `proj_id`：项目 ID，仅低 8 位有效（0-255）
- 原理：通过文件的 inode 号 + proj_id 计算生成唯一 key
- 返回值：成功返回 key 值，失败返回 - 1

### 核心 API

#### （1）创建 / 获取消息队列

```text
#include <sys/types.h>
#include <sys/ipc.h>
#include <sys/msg.h>
int msgget(key_t key, int msgflg);
```

- `key`：ftok 生成的键值，`IPC_PRIVATE`表示创建仅亲缘进程可用的私有队列
- `msgflg`：创建标志 + 权限位 

  - `IPC_CREAT`：不存在则创建，存在则返回已有 id
  - `IPC_EXCL`：配合 IPC_CREAT 使用，存在则创建失败报错
- 返回值：成功返回消息队列 ID（msqid），失败返回 - 1

#### （2）发送消息

```c
int msgsnd(int msqid, const void *msgp, size_t msgsz, int msgflg);
```

- 消息结构体格式（必须自定义，首成员为 long 类型）： 

```c
struct msgbuf {
    long mtype;     // 消息类型，必须大于0
    char mtext[1];  // 消息正文，可自定义大小和类型
};
```

- `msgsz`：消息正文的字节数（不包含 mtype）
- `msgflg`： 

  - `0`：阻塞模式，队列满时阻塞等待
  - `IPC_NOWAIT`：非阻塞，队列满时立即返回失败

#### （3）接收消息

```c
ssize_t msgrcv(int msqid, void *msgp, size_t msgsz, long msgtyp, int msgflg);
```

- `msgtyp`：接收消息的类型 

  - `=0`：接收队列中第一条消息（先进先出）
  - `>0`：接收队列中第一条类型等于 msgtyp 的消息（最常用）
  - `<0`：接收类型小于等于 msgtyp 绝对值的、类型最小的第一条消息
- 返回值：成功返回实际读到的正文字节数，失败返回 - 1

#### （4）控制消息队列

```c
int msgctl(int msqid, int cmd, struct msqid_ds *buf);
```

- 常用`cmd`： 

  - `IPC_RMID`：删除消息队列，此时 buf 传 NULL 即可
  - `IPC_STAT`：获取队列属性，存入 buf
  - `IPC_SET`：设置队列属性

### 特点

- 消息有类型、有格式，可按优先级读取
- 自带同步机制，读写均可阻塞
- 存在系统上限：消息总数、单条消息最大长度、队列总字节数均有限制

## 六、共享内存（Shared Memory）

### 核心定义

System V IPC 中效率最高的通信方式；内核申请一块物理内存区域，让多个进程的虚拟地址空间映射到同一块物理内存，进程可直接读写该内存，无需内核数据拷贝。

- 优势：零内核拷贝，速度最快，适合大数据量交互
- 劣势：本身不提供同步互斥机制，多进程同时读写会产生竞态，需配合信号量 / 互斥锁使用
- 生命周期：随内核，需手动删除

### 核心 API

#### （1）创建 / 获取共享内存

```c
#include <sys/ipc.h>
#include <sys/shm.h>
int shmget(key_t key, size_t size, int shmflg);
```

- `size`：共享内存大小，必须是 PAGE_SIZE（4KB）的整数倍
- `shmflg`：创建标志 + 权限位，同 msgget
- 返回值：成功返回共享内存 ID（shmid），失败返回 - 1

#### （2）映射共享内存到进程地址空间

```c
#include <sys/types.h>
#include <sys/shm.h>
void *shmat(int shmid, const void *shmaddr, int shmflg);
```

- `shmaddr`：指定映射的虚拟地址，传 NULL 则由系统自动分配（推荐）
- `shmflg`： 

  - `0`：默认，读写权限
  - `SHM_RDONLY`：只读权限
- 返回值：成功返回映射后的内存首地址，失败返回`(void *)-1`

#### （3）解除映射

```c
int shmdt(const void *shmaddr);
```

- 功能：将共享内存与当前进程地址空间解绑
- 注意：解除映射不等于删除共享内存，只是当前进程无法再访问

#### （4）控制共享内存

```c
int shmctl(int shmid, int cmd, struct shmid_ds *buf);
```

- 常用`cmd`： 

  - `IPC_RMID`：标记删除共享内存（真正删除在所有进程都解除映射后）
  - `IPC_STAT` / `IPC_SET`：获取 / 设置属性

### 补充原理

- 共享内存通过修改进程页表，让不同进程的虚拟页指向同一个物理页框，实现内存共享
- 因为直接操作用户态内存，无需陷入内核做数据拷贝，因此速度远高于管道、消息队列
- 注意事项：多进程读写必须做同步，否则会出现数据混乱；进程退出前必须解除映射，避免内存泄漏

---

## 七、信号量集（Semaphore Set）

### 核心定义

System V IPC 的一种，用于实现进程间的同步与互斥，本身不传输数据，仅通过计数器控制资源访问；一个信号量集可包含多个信号量，各自独立工作。

- 本质：内核维护的计数器 + 等待队列
- 核心操作：P 操作（申请资源，计数器 - 1）、V 操作（释放资源，计数器 + 1），均为原子操作

### P/V 操作逻辑

- P 操作（申请）：计数器减 1 

  - 减后 ≥ 0：申请成功，进程继续执行
  - 减后 < 0：申请失败，进程阻塞进入等待队列
- V 操作（释放）：计数器加 1 

  - 加后 > 0：无等待进程，仅增加资源计数
  - 加后 ≤ 0：有进程等待，唤醒等待队列中的一个进程

### 核心 API

#### （1）创建 / 获取信号量集

```c
#include <sys/types.h>
#include <sys/ipc.h>
#include <sys/sem.h>
int semget(key_t key, int nsems, int semflg);
```

- `nsems`：信号量集中信号量的个数
- 返回值：成功返回信号量集 ID（semid），失败返回 - 1

#### （2）控制信号量集

```c
int semop(int semid, struct sembuf *sops, size_t nsops);
```

- `semnum`：操作第几个信号量（从 0 开始编号）
- 常用`cmd`： 

  - `SETVAL`：设置单个信号量的初始值，需传第四个参数（联合体）
  - `GETVAL`：获取单个信号量的当前值
  - `IPC_RMID`：删除整个信号量集，此时 semnum 参数无效
  - `IPC_STAT` / `IPC_SET`：获取 / 设置属性

#### （3）P/V 操作

```c
int semop(int semid, struct sembuf *sops, size_t nsops);
```

- 操作结构体： 

```c
struct sembuf {
    unsigned short sem_num;  // 操作第几个信号量
    short sem_op;             // 操作值：-1=P操作，+1=V操作
    short sem_flg;            // 操作标志
};
```

- `sem_flg`： 

  - `0`：阻塞模式，资源不足时等待
  - `IPC_NOWAIT`：非阻塞，资源不足立即返回
  - `SEM_UNDO`：进程异常退出时，自动回滚该进程对信号量的操作，防止死锁
- `nsops`：本次操作的 sembuf 结构体个数，可一次操作多个信号量

### 补充说明

- 二值信号量：初始值为 1 的信号量，功能等同于互斥锁，保证同一时间只有一个进程访问临界资源
- 计数信号量：初始值大于 1，用于控制同时访问资源的进程数量
- System V 信号量编程相对繁琐，线程间同步更推荐使用 POSIX 无名信号量

# 线程概念

## 一、Linux 线程本质：轻量级进程（LWP）

### 核心定义

Linux 内核中没有真正意义上的 "线程" 结构体，线程本质上是共享资源的轻量级进程（Light Weight Process, LWP）。

- 内核视角：每个线程对应一个独立的`task_struct`（进程控制块），是内核调度的基本单位
- 资源视角：同一进程内的多个线程，共享同一个`mm_struct`（内存地址空间）、`files_struct`（文件描述符表）、`signal_struct`（信号处理表）等核心资源

### 设计思想

进程是 "资源分配的基本单位"，线程是 "CPU 调度的基本单位"；将 "资源" 和 "调度" 解耦：

- 同一个进程内的线程共享内存、文件等资源，减少了切换开销
- 每个线程拥有独立的栈和寄存器上下文，可被独立调度执行

### NPTL 线程库

Linux 标准 POSIX 线程库为 NPTL（Native POSIX Thread Library），是目前主流发行版的默认线程实现：

- 1:1 线程模型：用户态线程与内核轻量级进程一一对应
- 完全遵循 POSIX 标准，接口可移植性强
- 由 glibc 提供，编译时需显式链接`-lpthread`库

---

## 二、线程的资源划分

### 线程间共享资源（进程级）

- 虚拟地址空间（代码段、数据段、堆、共享库映射区）
- 文件描述符表
- 信号处理函数与信号掩码
- 用户 ID、组 ID、进程 ID
- 当前工作目录
- 资源限制（文件大小、进程数等）

### 每个线程独有资源（线程级）

- 线程栈（用户态栈，默认大小通常为 8MB）
- 寄存器上下文（程序计数器、栈指针等）
- 线程 ID（TID，内核中对应轻量级进程 PID）
- 线程局部存储（TLS，Thread Local Storage）
- `errno`变量
- 信号掩码（可独立设置每个线程的信号屏蔽字）
- 调度优先级

---

## 三、线程的状态

Linux 线程作为内核调度单位，状态与进程状态完全一致：

1. 运行态（R）：正在 CPU 上执行，或在就绪队列中等待调度
2. 可中断睡眠态（S）：等待事件完成（如 IO、锁），可被信号唤醒
3. 不可中断睡眠态（D）：等待关键硬件操作，不可被信号打断，保证数据一致性
4. 停止态（T）：收到暂停信号（SIGSTOP/SIGTSTP），暂停执行，可通过 SIGCONT 恢复
5. 僵尸态（Z）：线程已终止，但资源未被回收（结合态线程未被 join）
6. 死亡态（X）：线程彻底销毁，资源全部释放，瞬间状态无法观测

## 五、适用场景

### 优先使用多进程的场景

- 需要强故障隔离：单个模块崩溃不能影响整体（如浏览器标签页、服务器多进程架构）
- 安全性要求高：不同进程权限隔离，避免单个进程漏洞影响全局
- 任务间数据交互少、各自独立运行

### 优先使用多线程的场景

- 高并发服务：如 Web 服务器，大量 IO 等待场景，线程切换开销低
- 数据交互频繁：任务间需要共享大量数据，线程间共享内存效率更高
- CPU 密集型计算：利用多核 CPU 并行计算，提升运算效率
- GUI 程序：后台线程处理耗时任务，主线程负责界面响应，避免界面卡顿

# 多线程相关函数 

## 线程标识函数

### pthread_self

```c
#include <pthread.h>
pthread_t pthread_self(void);
```

- 功能：获取当前线程的线程 ID（POSIX 线程库层面的 ID）
- 返回值：总是成功，返回当前线程的`pthread_t`类型 ID
- 注意： 

  - `pthread_t`是 POSIX 标准定义的线程 ID，属于用户态标识；和内核中 LWP 的 PID 不是同一个概念
  - 仅在同一进程内唯一，不同进程的线程 ID 可能重复
  - 不可直接用`==`判断可移植性，标准用法是调用`pthread_equal`函数比较

---

## 线程创建函数

### pthread_create

```c
#include <pthread.h>
int pthread_create(pthread_t *thread, const pthread_attr_t *attr,
                   void *(*start_routine)(void *), void *arg);
```

### 参数说明

1. `thread`：输出型参数，用于保存新创建线程的唯一标识符，线cehngID
2. `attr`：线程属性结构体指针，传 NULL 则使用默认属性
3. `start_routine`：线程入口函数指针，新线程从该函数开始执行
4. `arg`：传递给线程入口函数的参数，无需传参则设为 NULL

### 返回值

- 成功：返回 0
- 失败：返回非 0 错误码（不会设置 errno），常见错误： 

  - `EAGAIN`：系统资源不足，或线程数达到上限
  - `EINVAL`：线程属性 attr 无效

### 注意事项

1. 线程执行顺序不确定，由内核调度器决定
2. 主线程如果先于子线程退出（调用`pthread_exit`除外），整个进程会终止，所有线程都会退出
3. 传参注意：传递局部变量地址时，需保证线程执行期间变量生命周期未结束，否则会出现野指针
4. 编译必须链接线程库：`gcc 源文件 -o 目标文件 -lpthread`

---

## 线程终止函数

### pthread_exit

```c
#include <pthread.h>
void pthread_exit(void *retval);
```

- 功能：终止当前线程，同时返回退出状态
- `retval`：线程退出状态值，可被`pthread_join`获取；不需要返回值则传 NULL
- 注意： 

  - 线程入口函数中`return`也会终止线程，效果等价于`pthread_exit`
  - 在主线程中调用`pthread_exit`，只会终止主线程，进程不会退出；其他子线程会继续运行，直到所有线程都退出，进程才终止
  - `exit`函数会终止整个进程，任何线程调用`exit`都会导致所有线程退出

### 线程退出的三种方式

1. 线程入口函数执行完毕，通过`return`返回
2. 线程主动调用`pthread_exit`终止自身
3. 被其他线程调用`pthread_cancel`取消

---

## 线程回收机制

线程分为两种状态：结合态（joinable，默认） 和 分离态（detached）。

### 结合态线程与 pthread_join

```c
#include <pthread.h>
int pthread_join(pthread_t thread, void **retval);
```

- 功能：阻塞等待指定的结合态线程结束，回收其资源，并获取线程退出状态
- 参数： 

  - `thread`：要等待的线程 ID
  - `retval`：二级指针，用于接收线程退出状态；不关心则传 NULL
- 返回值：成功返回 0，失败返回非 0 错误码

#### 注意事项

- 一个线程只能被 join 一次，多次 join 会报错
- 只能对结合态线程调用 join；对分离态线程调用 join 会失败
- 如果线程已经退出，调用 join 会立即返回，不会阻塞
- 若结合态线程退出后未被 join，会成为 "僵尸线程"，占用内核资源（task_struct）

### 分离态线程

#### 特点

- 线程终止后，系统自动回收其资源，无需其他线程调用 join
- 无法获取其退出状态，也不能被 join 等待
- 适用于不需要关心线程结束状态的后台任务

#### 设置方式 1：pthread_detach

```c
#include <pthread.h>
int pthread_detach(pthread_t thread);
```

- 功能：将指定线程设置为分离态
- 可由其他线程调用，也可线程自身调用：`pthread_detach(pthread_self())`
- 返回值：成功返回 0，失败返回非 0 错误码

#### 设置方式 2：通过线程属性设置（创建时即分离）

```c
pthread_attr_t attr;
pthread_attr_init(&attr); // 初始化属性结构体
// 设置为分离态
pthread_attr_setdetachstate(&attr, PTHREAD_CREATE_DETACHED);
// 用该属性创建线程
pthread_create(&tid, &attr, start_func, arg);
pthread_attr_destroy(&attr); // 销毁属性结构体
```

### 线程属性相关函数

```c
// 初始化线程属性
int pthread_attr_init(pthread_attr_t *attr);
// 销毁线程属性
int pthread_attr_destroy(pthread_attr_t *attr);
// 设置分离状态
int pthread_attr_setdetachstate(pthread_attr_t *attr, int detachstate);
// 获取分离状态
int pthread_attr_getdetachstate(const pthread_attr_t *attr, int *detachstate);
```

- `detachstate` 取值： 

  - `PTHREAD_CREATE_JOINABLE`：结合态（默认）
  - `PTHREAD_CREATE_DETACHED`：分离态

> 除了分离状态，线程属性还可设置栈大小、栈地址、调度策略、优先级等，开发中一般使用默认属性即可。

## 线程取消机制

### pthread_cancel

```text
#include <pthread.h>
int pthread_cancel(pthread_t thread);
```

- 功能：向指定线程发送取消请求，请求终止该线程
- 返回值：成功返回 0，失败返回非 0 错误码
- 注意：发送请求后立即返回，不会等待线程终止；线程是否终止、何时终止，取决于该线程的取消状态和取消类型

### 取消状态设置

```c
int pthread_setcancelstate(int state, int *oldstate);
```

- `state` 取值： 

  - `PTHREAD_CANCEL_ENABLE`：允许线程被取消（默认状态）
  - `PTHREAD_CANCEL_DISABLE`：禁止线程被取消，取消请求会被暂挂
- `oldstate`：保存旧的取消状态，可为 NULL

### 取消类型设置

```c
int pthread_setcanceltype(int type, int *oldtype);
```

- `type` 取值： 

  - `PTHREAD_CANCEL_DEFERRED`：延迟取消（默认）。线程收到取消请求后，不会立即终止，而是等到下一次调用取消点函数时才会终止
  - `PTHREAD_CANCEL_ASYNCHRONOUS`：异步取消。线程可在任意时刻被立即取消，风险高，极少使用

### 补充：取消点

POSIX 标准规定了一批函数是取消点，线程执行到这些函数时会检查是否有未处理的取消请求，如：

- `read`、`write`、`sleep`、`pthread_testcancel`
- 大多数会阻塞的系统调用

> 编程注意：如果线程中有临界资源操作，被取消可能导致资源未释放，需配合线程清理函数（`pthread_cleanup_push` / `pthread_cleanup_pop`）处理。

## 常见易错点总结

1. 僵尸线程：结合态线程退出后未被 join，会残留 task_struct 资源；大量创建不回收会导致资源泄漏
2. 主线程提前退出：主线程 return 或调用 exit 会导致整个进程退出，所有子线程强制终止；若需等待子线程，应调用 pthread_join
3. 线程传参野指针：给子线程传递局部变量地址，主线程函数返回后变量销毁，子线程访问野指针崩溃
4. 分离态线程不可 join：已设置为分离态的线程，再调用 join 会失败
5. 线程 ID 比较：`pthread_t`在不同系统实现可能不同（可能是数值、可能是结构体指针），不可直接用`==`比较，应使用`pthread_equal`

#  线程的互斥和同步 学习笔记

## 并发基础概念

### 竞态条件（Race Condition）

多个线程同时访问共享资源，且至少有一个线程执行写操作，最终结果依赖于线程调度的时序，结果不确定、不可复现，导致数据错误。

### 临界区（Critical Section）

访问共享资源的代码片段，同一时间只能有一个线程进入执行；保证临界区的原子性，是解决竞态问题的核心。

### 同步与互斥

- 互斥：同一时刻只允许一个线程访问临界资源，解决资源竞争问题
- 同步：多个线程按照约定的顺序执行，解决协作依赖问题

---

## 互斥锁（Mutex）

### 核心定义

互斥锁是实现互斥访问的同步工具，本质是内核维护的 "标志位 + 等待队列"；同一时间只能有一个线程持有锁，其他线程申请锁失败会阻塞等待。

- 保证临界区代码的原子执行
- 是编程中最常用的同步手段

### 核心 API

#### （1）初始化互斥锁

```c
// 阻塞加锁：锁被占用则一直等待
int pthread_mutex_lock(pthread_mutex_t *mutex);
// 非阻塞尝试加锁：锁被占用则立即返回错误
int pthread_mutex_trylock(pthread_mutex_t *mutex);
```

- `attr`：互斥锁属性，传 NULL 使用默认属性
- 返回值：成功返回 0，失败返回非 0 错误码

#### （2）加锁

```c
// 阻塞加锁：锁被占用则一直等待
int pthread_mutex_lock(pthread_mutex_t *mutex);
// 非阻塞尝试加锁：锁被占用则立即返回错误
int pthread_mutex_trylock(pthread_mutex_t *mutex);
```

- `pthread_mutex_trylock` 返回值：成功返回 0，锁已被占用返回`EBUSY`

#### （3）解锁

```c
int pthread_mutex_unlock(pthread_mutex_t *mutex);
```

- 谁加锁谁解锁，一般由持有锁的线程调用
- 解锁后会唤醒等待队列中的一个线程

#### （4）销毁互斥锁

```c
int pthread_mutex_destroy(pthread_mutex_t *mutex);
```

- 锁不再使用时必须销毁，释放资源
- 销毁时必须确保锁处于未锁定状态，且没有线程在等待该锁

### 底层实现与性能

Linux 的互斥锁基于`futex`（快速用户态互斥锁）实现：

- 无竞争时：仅在用户态执行原子操作，无需陷入内核，开销极低
- 有竞争时：才进入内核态，将线程挂入等待队列阻塞
- 因此在锁竞争不激烈的场景下，互斥锁性能非常高

### 互斥锁的类型

- 普通锁（默认）：线程重复加锁会导致死锁
- 检错锁：重复加锁会返回错误，便于调试
- 递归锁：允许同一线程多次加锁，内部维护计数，解锁次数与加锁次数一致时才真正释放锁

### 注意事项

1. 临界区范围尽可能小，只保护真正的共享资源，减少锁竞争
2. 避免在持有锁期间执行耗时操作（如 sleep、IO）
3. 保证所有线程访问共享资源前都加锁，形成统一约定
4. 加锁后必须确保所有退出路径都解锁，否则会导致死锁

## 条件变量（Condition Variable）

### 核心定义

条件变量用于实现线程间的 "等待 - 通知" 机制：当某个条件不满足时，线程主动释放锁并阻塞等待；当条件满足时，其他线程唤醒等待的线程。

- 必须和互斥锁配合使用，本身不提供互斥能力
- 解决 "线程等待特定条件" 的场景，避免忙等（轮询）浪费 CPU

### 核心 API

#### （1）初始化

```c
// 动态初始化
int pthread_cond_init(pthread_cond_t *restrict cond,
                       const pthread_condattr_t *restrict attr);
// 静态初始化
pthread_cond_t cond = PTHREAD_COND_INITIALIZER;
```

#### （2）等待条件

```c
int pthread_cond_wait(pthread_cond_t *restrict cond,
                       pthread_mutex_t *restrict mutex);
```

- 功能：线程阻塞在条件变量上，同时自动释放互斥锁；被唤醒后会自动重新获取互斥锁
- 执行流程： 

  1. 释放持有的 mutex 锁
  2. 阻塞等待，直到被唤醒
  3. 被唤醒后，重新获取 mutex 锁，然后函数返回

> 为什么必须配合互斥锁？ 保证 "检查条件" 和 "进入等待" 是原子操作，避免在检查条件后、进入等待前，条件被其他线程修改并发送通知，导致通知丢失，线程永久等待。

#### （3）唤醒等待线程

```c
// 唤醒至少一个等待在条件变量上的线程
int pthread_cond_signal(pthread_cond_t *cond);
// 唤醒所有等待在条件变量上的线程
int pthread_cond_broadcast(pthread_cond_t *cond);
```

- 注意：唤醒操作不要求必须持有互斥锁，但一般建议在持有锁时调用，保证逻辑严谨

#### （4）销毁

```c
int pthread_cond_destroy(pthread_cond_t *cond);
```

### 重要原则：条件判断必须用 while 循环

```c
// 正确写法
pthread_mutex_lock(&mutex);
while (条件不满足) {
    pthread_cond_wait(&cond, &mutex);
}
// 操作临界资源
pthread_mutex_unlock(&mutex);
```

#### 原因：

1. 惊群效应：`pthread_cond_broadcast`唤醒所有线程，但只有一个能拿到锁，其他线程被唤醒后条件可能仍不满足，需要继续等待
2. 虚假唤醒：操作系统可能在没有线程发送 signal 的情况下唤醒等待线程，属于正常现象
3. 因此被唤醒后必须再次检查条件，不满足则继续等待

### 典型应用场景

生产者 - 消费者模型：

- 生产者：生产数据，缓冲区满则等待；生产完成后通知消费者
- 消费者：消费数据，缓冲区空则等待；消费完成后通知生产者

## 无名信号量（Semaphore）

### 核心定义

POSIX 无名信号量，通过计数器控制资源访问，计数器的值代表可用资源数量；既可实现互斥，也可实现同步。

- 线程间同步：初始化值为 0，实现线程执行顺序控制
- 互斥访问：初始化值为 1，等同于互斥锁
- 多资源并发：初始化值为 N，允许 N 个线程同时访问资源

### 核心 API

#### （1）初始化

```c
#include <semaphore.h>
int sem_init(sem_t *sem, int pshared, unsigned int value);
```

- `sem`：信号量变量地址
- `pshared`：共享方式 

  - `0`：线程间共享（同一进程内的多个线程使用，最常用）
  - 非 0：进程间共享，需将信号量放在共享内存中
- `value`：信号量初始计数值

#### （2）P 操作（申请资源，-1）

```c
int sem_wait(sem_t *sem);
```

- 计数值大于 0：减 1 后立即返回
- 计数值等于 0：阻塞等待，直到其他线程执行 V 操作增加计数

#### （3）V 操作（释放资源，+1）

```c
int sem_post(sem_t *sem);
```

- 计数值加 1，若有线程在等待，则唤醒其中一个
- 该函数是线程安全的，可在信号处理函数中调用

#### （4）销毁

```c
int sem_destroy(sem_t *sem);
```

### 特点

- 功能比互斥锁更丰富，支持计数型同步
- 没有 "锁的持有者" 概念，任何线程都可以执行 V 操作释放资源
- 实现生产者 - 消费者模型比 "互斥锁 + 条件变量" 更简洁

## 死锁

### 死锁定义

多个线程互相持有对方需要的资源，又都在等待对方释放资源，导致所有线程永久阻塞，无法继续执行。

### 死锁产生的四个必要条件

1. 互斥条件：资源同一时间只能被一个线程持有
2. 持有并等待：线程已持有至少一个资源，又在申请其他被持有的资源
3. 不可剥夺：资源只能由持有者主动释放，不能被其他线程强行抢占
4. 循环等待：线程间形成首尾相接的资源等待环路

### 预防死锁的方法

打破四个必要条件中的任意一个即可：

1. 打破循环等待（最常用）：所有线程按照统一的顺序加锁（如按地址从小到大、按 ID 从小到大）
2. 打破持有并等待：一次性申请所有需要的资源，申请不到则全部释放，重试
3. 打破不可剥夺：申请锁失败时，主动释放已持有的所有锁，过段时间重试（配合`trylock`实现）
4. 打破互斥：使用无锁编程，难度高，适用场景有限

### 常见死锁场景

- 同一线程重复加同一把普通锁
- 两个线程按相反顺序加两把锁
- 线程持有锁后，等待条件变量，但忘记释放锁（条件变量 wait 会自动放锁，不会死锁）

---

## 经典同步模型：生产者 - 消费者

### 模型描述

- 生产者线程：生产数据，放入共享缓冲区
- 消费者线程：从缓冲区取出数据消费
- 缓冲区满时，生产者必须等待；缓冲区空时，消费者必须等待

### 基于信号量的实现思路

1. 三个信号量： 

   - `sem_empty`：空位计数，初始值为缓冲区大小 N
   - `sem_full`：满位计数，初始值为 0
   - `sem_mutex`：互斥锁，保护缓冲区操作，初始值为 1
2. 生产者流程： 

   - P (sem_empty) → P (sem_mutex) → 放入数据 → V (sem_mutex) → V (sem_full)
3. 消费者流程： 

   - P (sem_full) → P (sem_mutex) → 取出数据 → V (sem_mutex) → V (sem_empty)

> 注意：互斥锁的 P 操作必须放在资源信号量的 P 操作之后，否则可能导致死锁。
