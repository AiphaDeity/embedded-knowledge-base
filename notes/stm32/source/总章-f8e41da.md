# 学习路线

## 一、学习路线总览

本系列共 13 篇 STM32 控制器笔记，按依赖关系分为 5 个阶段，从底层寄存器一直到系统级应用。建议按编号顺序学习，每一步都完成对应的实践实验后再进入下一步。

| 阶段 | 名称 | 包含编号 | 核心目标 |
|-|-|-|-|
| 1 | 底层基础 | 01–02 | 理解芯片本质，点亮第一个外设 |
| 2 | 系统核心 | 03–05 | 搭建系统运行的骨架（时钟、通信、中断） |
| 3 | 数据传输 | 06–07 | 高效搬运数据，采集模拟信号 |
| 4 | 接口与定时 | 08–10 | 连接外部芯片，精确控制时间 |
| 5 | 高级与安全 | 11–13 | 扩展外部资源，输出模拟信号，保护系统稳定 |

## 二、各阶段详解

### 阶段一：底层基础（01–02）

这一阶段的目标是建立对芯片最底层的认知。汇编让你看懂启动文件和寄存器操作，GPIO 是所有外设的"Hello World"。

**01 汇编**

**核心内容：**ARM 指令集、启动文件（startup）、寄存器级操作、堆栈与函数调用约定、异常向量表。

**实践任务：**手写启动文件、用纯寄存器操作点亮 LED。

**02 GPIO 控制器**

**核心内容：**输入/输出模式、推挽/开漏输出、上拉/下拉输入、复用功能、输出速度与驱动能力。

**实践任务：**LED 闪烁、按键检测与消抖、按键控制 LED。

### 阶段二：系统核心（03–05）

这一阶段搭建系统运行的骨架。时钟是一切外设的脉搏，串口是调试的眼睛，中断是后续所有异步处理的基础。

**03 时钟控制器（RCC）**

**核心内容：**时钟树结构、HSE/HIS/LSE 时钟源、PLL 倍频、系统时钟配置、外设时钟使能、MCO 时钟输出。

**实践任务：**配置 72MHz 系统时钟、通过 MCO 引脚测量时钟输出。

**04 串口控制器（USART）**

**核心内容：**UART 协议帧格式、波特率计算、查询方式收发、中断方式收发、printf 重定向、硬件流控。

**实践任务：**串口打印调试信息、与上位机双向通信、串口控制 LED。

**05 中断控制器（NVIC/EXTI）**

**核心内容：**NVIC 优先级分组、抢占优先级与响应优先级、EXTI 外部中断线、中断服务函数编写、中断挂起与清除。

**实践任务：**按键触发外部中断、串口接收中断、中断优先级嵌套实验。

### 阶段三：数据传输（06–07）

这一阶段关注数据的高效搬运和模拟信号采集。DMA 解放 CPU，ADC 把真实世界的模拟量接进来，两者常配合使用。

**06 DMA 控制器**

**核心内容：**直接存储器访问原理、通道/数据流配置、源/目标地址增量模式、循环模式与正常模式、传输完成中断、FIFO 阈值。

**实践任务：**串口 DMA 收发、内存到内存数据搬运、DMA+串口空闲中断接收不定长数据。

**07 ADC 控制器**

**核心内容：**12 位逐次逼近型 ADC、单通道/多通道扫描模式、采样时间配置、规则组与注入组、DMA 传输、电压换算公式。

**实践任务：**电位器电压采集、多通道 ADC+DMA 扫描、内部温度传感器读取。

### 阶段四：接口与定时（08–10）

这一阶段学习连接外部芯片的两条主线（I2C、SPI），以及精确控制时间的核心外设（TIM 定时器）。

**08 I2C 控制器**

**核心内容：**I2C 协议时序、起始/停止/应答信号、7 位/10 位地址、主发送/主接收流程、软件模拟 I2C、总线仲裁。

**实践任务：**读写 24C02 EEPROM、读取 SHT30 温湿度传感器、软件 I2C 驱动 OLED。

**09 SPI 控制器**

**核心内容：**SPI 协议、主/从模式、CPOL/CPHA 四种工作模式、全双工通信、片选 NSS、波特率分频、SPI 与 I2S 复用。

**实践任务：**读写 W25Q64 Flash、SPI 驱动 OLED/TFT 屏、读取 BMI160 六轴传感器。

**10 TIM 定时器**

**核心内容：**基本定时器/通用定时器/高级定时器区别、定时中断、PWM 输出、输入捕获、输出比较、编码器接口、死区时间与互补输出。

**实践任务：**PWM 呼吸灯、舵机控制、脉冲宽度测量、电机编码器测速。

### 阶段五：高级与安全（11–13）

前四个阶段打好基础后，这一阶段学习高级外设：扩展外部存储资源、输出模拟信号、保护系统稳定运行。

**11 FSMC 控制器**

**核心内容：**外部存储器扩展原理、地址映射与 Bank 分区、读写时序配置、SRAM/NOR/NAND Flash 支持、LCD 接口模式、数据总线宽度。

**实践任务：**驱动 TFT LCD 并显示字符/图片、外接 SRAM 读写测试。

**12 DAC 控制器**

**核心内容：**12 位数模转换、输出缓冲使能、单通道/双通道、DMA 触发波形生成、噪声波/三角波生成、外部触发源。

**实践任务：**输出可调直流电压、DMA+DAC 生成正弦波、DAC 输出音频信号。

**13 独立看门狗（IWDG）**

**核心内容：**LSI 时钟驱动、预分频系数与重装载值、超时时间计算、键寄存器喂狗、独立看门狗与窗口看门狗对比、调试模式下的行为。

**实践任务：**看门狗超时复位实验、正常喂狗防止系统重启、在主循环和中断中合理喂狗。

## 三、统一学习方法


::: tip

**四步学习循环：**每一个控制器都遵循「读原理 → 看寄存器 → 写代码 → 调实验」的循环。
1. **读原理：**这个控制器解决什么问题？工作机制是什么？在系统中处于什么位置？
2. **看寄存器：**关键寄存器有哪些？每个位什么含义？复位值是什么？
3. **写代码：**先用库函数写一遍，再尝试用寄存器直接配置，加深理解。
4. **调实验：**上板验证，用示波器、串口、LED 或 LCD 观察实际结果。

:::


**阶段间依赖关系**

- **时钟（03）是所有外设的前提：**任何外设使用前都必须先使能其时钟。
- **中断（05）被反复使用：**串口接收、定时器溢出、ADC 转换完成、DMA 传输完成都依赖中断。
- **DMA（06）建议在串口和 ADC 之后深入：**DMA 本身不复杂，但它的价值体现在与其他外设的配合中。
- **TIM（10）是最核心的外设之一：**PWM、定时、测量、电机控制都离不开它，建议多花时间。
- **FSMC（11）和 DAC（12）属于进阶内容：**前面的基础打好后，学起来会很快。

**学习进度建议**

| 阶段 | 建议用时 | 验收标准 |
|-|-|-|
| 阶段一 | 3–5 天 | 能看懂启动文件，能用寄存器和库函数两种方式点灯 |
| 阶段二 | 5–7 天 | 能配置系统时钟，能用串口打印调试，能写外部中断服务函数 |
| 阶段三 | 3–5 天 | 能用 DMA 搬运数据，能用 ADC 采集电压并换算成实际值 |
| 阶段四 | 7–10 天 | 能驱动 I2C 和 SPI 设备，能用 TIM 输出 PWM 和测量脉冲 |
| 阶段五 | 3–5 天 | 能用 FSMC 驱动 LCD，能用 DAC 输出波形，能配置看门狗 |

完成全部 13 篇后，建议做一个综合项目（如智能小车、数据采集系统、简易示波器），把所有控制器串联起来使用，才能真正掌握。

# 关于代码会用到会设计

## 第一阶段：入门阶段——掌握基础，让代码“跑起来”

这个阶段的核心目标不是“写出优雅的代码”，而是“让芯片按照你的预期工作”。

- 你会怎么做：完全依赖 CubeMX 生成的代码，直接在 `main.c` 里重写 `__weak` 弱回调函数（如 `HAL_UART_RxCpltCallback`），所有逻辑都堆在回调函数或 `while(1)` 里。
- 为什么会这样：因为你还不熟悉 HAL 库的代码结构和芯片的工作流程，需要先建立“写代码 → 烧录 → 看现象”的闭环。重写弱函数是最直接、最不容易出错的方式，也是官方例程和绝大多数教程采用的方法，你能找到最多的参考资料和现成代码。
- 这个阶段的标志：你能用串口收发数据、用 PWM 控制电机、用 DMA 搬运数据，但你的代码里可能有多个外设共用同一个回调函数，通过 `if` 判断 `hdma->Instance` 或 `huart->Instance` 来区分是哪个外设触发的。
- 你需要掌握的核心能力：看懂 HAL 库的函数调用链（比如中断是如何从 `USART1_IRQHandler` 一路走到你的回调函数的）、会使用 CubeMX 配置外设、会用逻辑分析仪或串口助手调试数据流。
- 这个阶段正常吗？ 非常正常。很多产品级的代码里也会出现这种写法，只要功能单一、逻辑简单，完全没问题。但如果你发现自己在一个回调函数里写了超过 50 行的 `if-else` 逻辑，那说明你该进入下一阶段了。

---

## 第二阶段：进阶阶段——追求架构，让代码“可维护”

这个阶段的核心目标是“当系统变复杂时，你的代码不会变成一团乱麻”。

- 你会怎么做：主动放弃重写弱函数，改用 `HAL_xxx_RegisterCallback` 将回调函数动态绑定到特定的外设句柄上。你会设计用户配置结构体（如 `UART_User_Config_t`），把回调函数指针和上下文数据（`void *user_data`）封装在一起，实现面向对象式的数据与行为绑定。
- 为什么会这么做：因为当你有两个 UART（比如 UART1 接 GPS，UART2 接 LoRa）时，传统的弱函数方式需要在同一个回调函数里判断 `huart->Instance` 再分别处理，代码耦合严重。而注册回调可以让 `uart1` 绑定 `GPS_Parse` 函数，`uart2` 绑定 `LoRa_Send` 函数，逻辑天然隔离，代码一目了然。
- 这个阶段的标志：你开始关注“分层”和“解耦”。你会把硬件驱动（HAL）、中间层（自己的封装）、应用层（业务逻辑）分开放在不同的 `.c`/`.h` 文件中。你会主动使用 `static` 关键字隐藏内部函数，只暴露必要的 API。你会用 `Parent` 或 `pRxBuffPtr` 等句柄预留字段来挂载用户数据，实现“反向索引”。
- 你需要掌握的核心能力：函数指针的使用、结构体与数据封装、模块化编译（`include` 路径管理）、以及理解 HAL 库中 `RegisterCallback` 的内部实现原理（它本质上是把函数指针存入句柄的某个字段，中断发生时先检查这个字段是否为空）。
- 如何判断自己是否到了这个阶段：当你在新增一个外设实例时，不需要修改核心驱动代码，只需要在应用层新增一个配置结构体并调用注册函数，就能完成功能扩展——如果你能做到这一点，说明你已经具备了初步的系统架构能力。

---

## 第三阶段：决策阶段——权衡取舍，让代码“恰到好处”

这个阶段的核心目标不是“追求某种写法”，而是“在工程约束下，选择最适合当前项目的方案”。

- 你会怎么做：你会根据不同项目场景，灵活选择不同的代码组织方式，甚至在同一项目中混合使用多种模式：

  - 原型验证或内部工具：快速用弱函数重写，不做过度设计。
  - 量产产品：主动采用注册回调，做好模块分层，方便后续维护和多人协作。
  - 低资源芯片（如 F103C8T6，RAM 仅 20KB）：优先考虑代码体积和 RAM 占用，可能会避免使用函数指针（因为它会占用额外 RAM），甚至手写寄存器操作以节省空间。
  - 高可靠性场景（如工业、车载）：可能会彻底禁用动态注册机制，强制使用静态弱函数，因为弱函数在链接时就已经确定，避免了运行时动态绑定的不确定性（如指针被意外篡改），且有利于静态分析工具检查代码路径。
- 这个阶段的核心思维：

  1. “没有银弹”：再优雅的设计也有其代价（RAM 占用、执行效率、调试难度），你需要根据项目实际需求做取舍。
  2. “可读性优先于技巧性”：代码首先是给人读的，其次才是给机器执行的。如果一种写法让你的同事（或三个月后的你）需要花 10 分钟才能理解，那它就是过度设计。
  3. “一致性优先于单一最佳实践”：在一个团队或一个项目中，保持代码风格的统一，远比纠结“哪一种方式更好”重要。如果整个项目都用弱函数，那你应该继续用弱函数；如果项目已经采用了注册回调，那你也应该遵循这个模式。
- 如何判断自己到了这个阶段：当你不再纠结“哪种方式更好”，而是能清晰地列出每种方式的优缺点，并基于项目需求、团队习惯、芯片资源、时间成本等因素做出有理有据的选择时，你就已经具备了真正的工程决策能力。



# 通用代码生成提示词模板

适用于任何外设（DMA、USART、SPI、I2C、TIM等）的“注册回调”思维代码生成。

> “请为STM32【芯片系列】编写一个基于【外设名称】HAL驱动的、遵循‘注册回调’思维的模块化代码。具体要求如下：
> 
> 1. 架构约束： 禁止重写HAL库中预设的\_\_weak弱回调函数（如【弱函数示例】），必须使用HAL库提供的【注册函数名称】接口，将自定义回调函数动态绑定到对应的【句柄类型】上。
> 2. 数据结构设计： 设计一个用户配置结构体，至少包含：① 完成回调函数指针（函数签名需包含句柄或自定义上下文参数）；② 错误回调函数指针；③ 一个用于传递自定义上下文的void\*指针。实现面向对象式的数据封装。
> 3. 接口设计： 提供一个统一的初始化和注册函数，接收【句柄类型】指针、用户配置结构体指针、以及用户自定义的回调函数指针作为参数。在函数内部调用【注册函数名称】分别注册完成和错误回调，并将用户配置结构体地址安全地挂载到【句柄类型】的预留字段（如Parent或私有指针）上。
> 4. 中间层桥接： 实现一个static的中间层回调函数，作为HAL库中断触发和用户业务逻辑之间的桥梁。该函数必须能从【句柄类型】中提取之前挂载的用户配置结构体地址，并安全地调用其中的业务函数指针，实现硬件中断与用户代码的解耦。
> 5. 代码质量要求： 生成独立的头文件(.h)和源文件(.c)，提供详尽的中文注释，解释每个函数的设计意图及数据流向。代码需具备生产级健壮性，包含必要的NULL检查和断言，支持运行时动态切换回调函数而无需修改驱动核心代码。”

**💡 如果你想更“懒”一点（口语化快速版）**

如果不想填那么多占位符，可以直接这样问：

> “请用‘注册回调’的方式（而不是重写\_\_weak弱函数）帮我生成STM32【外设】的驱动。要包含用户配置结构体、注册函数、中间桥接函数、支持运行时动态切换。代码要分层、可复用、有中文注释。”

例如：

> “请用‘注册回调’的方式帮我生成STM32F4的TIM定时器PWM驱动。”

AI会理解你的核心意图，生成符合“注册回调”思维的代码，但它可能会自主决定一些细节（比如结构体字段名、函数命名），不如填空模板精确可控。

**高级工程师应该怎么做？**

在实际工作中，工程师的选择并非“二选一”，而是根据项目阶段和需求灵活切换：

- 快速原型验证阶段：为了快速验证硬件和核心功能，重写弱函数是最快的方式。它无需额外配置，代码直观，是CubeMX的默认做法。很多ST的官方例程也使用这种方式。
- 生产项目与复杂驱动开发：当项目规模变大，需要更好的模块化和可维护性时，注册回调方式会更有优势。它能更好地将底层驱动与上层应用解耦。例如，为两个不同的UART设备编写完全独立的回调函数，代码会更清晰。
- 使用高级外设时的“潜规则”：这是一个重要警告。当你使用 SPI、I2C、USART 等外设的DMA功能时，不要直接使用 `HAL_DMA_RegisterCallback` 去修改DMA的回调。因为HAL库内部已经为这些外设的DMA传输注册了内部回调。如果你强行修改，可能会破坏外设库的内部状态。正确的做法是重写或注册外设级别的回调，例如 `HAL_SPI_TxCpltCallback` 或 `HAL_SPI_RegisterCallback`。
- 高级应用场景：在需要实现双缓冲、数据流处理等复杂功能时，注册回调几乎是必需的技术。例如，利用DMA的半传输完成回调（`HAL_DMA_XFER_HALFCPLT_CB_ID`）可以实现Ping-Pong缓冲，大幅提升数据吞吐率。

**关于外设弱函数重写或注册而不是修改**

- 重写（Override）：全局的、编译时确定的，适合简单场景。
- 注册（Register）：动态的、运行时绑定的，适合复杂场景。
- 修改（Modify）：越界的、危险的，它会破坏HAL内部维护的稳定性

# 嵌入式C编程

STM32 HAL库设计中常用C语言+编译器弱符号扩展（`__weak`）是一种非常核心且精妙的标准做法，它巧妙地利用了编译器和链接器的“弱符号（Weak Symbol）”特性，在保证代码灵活性的同时，维持了底层硬件抽象层（HAL）的完整和稳定。

### 核心机制：什么是“弱符号”？

在C语言中，默认的函数和已初始化的全局变量都是“强符号（Strong Symbol）”。这意味着，在同一个项目中，你不能定义两个同名的函数或变量，否则链接器会报“重复定义（redefinition）”错误。

而 `__weak` 关键字的作用，就是将一个“强符号”转变为“弱符号（Weak Symbol）”。这相当于告诉编译器：“这个定义是‘弱’的，如果其他地方有同名的‘强’定义，就请忽略我，使用那个‘强’的版本。”

因此，链接器在处理符号时遵循 “强符号优先” 的原则：

- 如果只有一个定义（无论强弱），就使用这个定义。
- 如果同时存在强定义和弱定义，链接器会选择强定义，而忽略弱定义。

### HAL库如何运用 `__weak` 实现“默认行为 + 用户定制”？

HAL库正是基于“强符号优先”的规则，大规模运用`__weak`来实现“默认行为 + 用户定制”的设计模式。

具体来说，HAL库会做两件事：

1. 提供默认的“弱”实现：在HAL库的源文件（如 `stm32f4xx_hal_uart.c`）中，用`__weak`关键字提供一个回调函数的默认版本。这个默认实现通常是空的，或者只包含一些基础操作。

```c
// 这是HAL库中的默认实现
__weak void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)
{
  /* 默认是空函数，什么也不做 */
}
```

1. 在中断或事件中调用：在HAL库处理中断的底层代码中，会直接调用这个回调函数。无论用户是否重写，这个调用点都存在，保证了程序在任何情况下都不会因为缺少函数定义而报错。

### 作为用户，你如何“重写”？

当你想在某个事件（比如串口收到数据）发生时执行自己的代码，只需要在你自己工程的任意 `.c` 文件中（如 `main.c`），重新定义一个同名的函数，但注意不要加 `__weak` 关键字。

```c
// 这是你在 main.c 中提供的“强”实现
void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)
{
    // 在这里编写你自己的处理逻辑
    if (huart->Instance == USART1) {
        // 处理USART1接收到的数据
    }
}
```

这样，在整个项目链接时，你提供的“强”版本就会覆盖HAL库中的“弱”版本。这样，你就在无需修改ST官方库文件的情况下，轻松实现了自定义功能。

### 总结：`__weak` 设计模式的优势

这种设计模式在STM32 HAL库中无处不在，包括`HAL_UART_RxCpltCallback`、`HAL_SPI_MspInit`、`HAL_GPIO_EXTI_Callback`等大量函数都采用了这种方式。它带来了几个显著的好处：

- 保持HAL库的完整性：你可以通过升级HAL库来获得新特性或Bug修复，而无需担心自己的修改会被覆盖。
- 按需实现：你只需关注和实现自己需要用到的回调函数，未被使用的函数保持默认的空实现，不会增加代码体积。
- 代码解耦：将硬件层（HAL库）与你的应用逻辑清晰分离，使代码更易于维护和阅读
